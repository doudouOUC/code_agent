Managed Agent
双链路技术方案

以 Java 作为产品控制面并内置 Runtime Broker 模块，以 qwen serve 作为常驻 TS Harness， 保留 Legacy ACP 链路，并将 Workspace、MCP 与本地工具执行下沉到按需启动的 Tool Runtime。 模型首 token 不等待 Runtime，只有真正发生本地 Tool Call 时才形成等待。

00 / FIRST RUNTIME

首版运行条件

v1.10 保留 v1.2 的总体架构、v1.3 的首版取舍、v1.4 的普通工具接线、v1.5 的统一 Session 身份、v1.6 的事件恢复边界和 v1.7 的扩展运行时、v1.8 的 SQL 物化切片，保留 v1.9 Workspace/cwd 契约，新增准入、分发、交互、迁移及容量门槛。Java 在创建前生成全局唯一 RFC UUID， 公共 API、qwen Session Authority、Managed Harness、JSONL 和 Runtime Broker scope 使用完全相同的 sessionId。不得再生成或持久化第二套 Harness Session ID。 首版仍采用单 Java + qwen Sidecar、预发布静态 AgentBundle、Session 独占 Runtime， 复用现有产品 REST/SSE 与正式历史。同 Session 多轮复用环境，Harness 仍可承载多个 Session。

首版只支持普通工具，以 Read、Write、Edit 和前台 Shell 为最小验收集； 自动记忆、子 Agent、后台 Shell 暂不在首版启用；其目标契约在阶段 H 的扩展运行时中定义，不作为当前运行前提。 复用现有配置与 AgentBundle 工具目录表达范围，不新增开关协议。 普通工具所需的审批、输出与文件历史保存、Shell 后代进程的取消清理仍须完成。 该 profile 的初始化和轮次结束不自动启动延期能力；配置要求范围外能力时， 创建前按既有 selector 选择 Legacy，显式要求不兼容的 Managed 则拒绝准入。

租户边界：独立 Spring 参考服务不做终端用户鉴权，但要求 X-Qwen-Tenant-Id 并将它贯穿 Session、Turn、Event 与 Broker scope；本地 WebShell 的 tenant 参数只用于开发代理。生产部署必须由 可信上游鉴权后注入 tenantId。完整多租户授权、配额和跨租户隔离仍是生产门槛。
项目首版要求最小完成边界
Prompt 受理与幂等必需兼容产品入口固定请求 ID，qwen 持久 input + WakeIntent 后才 ACK；阶段 D 公共入口另用 java_durable Profile，必须有命令交付与 operation 对账。
统一 Session 身份必需公共 API、qwen/Harness、JSONL 与 Broker scope 共用 Java 预分配的 RFC UUID；数据库不保存公共 ID 到 Harness ID 的映射。
Broker 调用与查询必需同轮等待、原 execution 查询、门禁映射、取消和实际释放；execute accepted 不等于完成。
AgentBundle必需预发布不可变版本与资源闭包，Harness 离线可读；缺失拒绝准入，Runtime 核验 manifest。
Session 归属与存储必需固定后端、明确持久位置；重启无证明则阻塞，不能新建空 Session 替代。
Runtime 生命周期必需持久创建意图、创建去重、有限启动/idle 期限和容量；取消后迟到 ready 重新校验，释放核验真实退出。
审批与用户问答条件必需已开放工具需要交互时，响应必须经 Java 回到原持久仲裁；不静默自动批准。
跨 Session 共享 Runtime默认关闭独立 ToolSessionBinding、配置/权限/gate/历史及引用计数通过验收后启用。
公开事件接受与 SSE已有 P0/P1 切片源游标、公开序号、Turn 终态和事件在一个事务中提交；同节点提交后直推，溢出或断线从 SQL 补齐。
稳定 Item / Snapshot 物化已有 P1 SQL 切片V2 已加入稳定 itemId/contentPartId、Item/Part、连续物化进度和 Snapshot；批次日志/Outbox 与保留清理仍属 P2，当前逐事件 SQL 行不能作为最终容量形态。

兼容产品入口：最小受理与故障边界

Client stable request ID → Java 持久统一 Session UUID / BackendBinding
                        → qwen 提交 input + WakeIntent → CommitReceipt
                        → Java 返回 accepted
模型推进与 Runtime 预热并行，不等待 Runtime ready。
ACK 丢失：原 ID 查询；started 失联：原执行对账或 recovery_blocked。
取消：先持久请求，再追踪实际停止与资源释放。

qwen Transcript/checkpoint、资源与 Broker Ledger 必须有明确持久保存位置。 Java 单独重启查询原 Sidecar/Runtime；Sidecar 重启核验 writer 与原调用； Pod 替换、卷不可用或旧 owner 不明时，首版不保证自动恢复。 多实例必须先完成原 owner 路由与 provision 竞争控制，自动跨实例接管仍属于 G。

首版使用 A/B/C/E 与 F 的必要验收，完整 D 不阻塞现有产品 API 上的 E 闭环。 方法与字段、Bundle 发布、部署矩阵、生命周期、审批及 M01～M10 验收见 首版运行契约； 这些是目标条件，不表示实现或测试已经完成。

普通工具首版接线

Read / Write / Edit / 前台 Shell 复用现有 TS 工具与权限流程。 本节补齐发布、会话、工具阶段、资源和环境生命周期之间的衔接； 自动记忆、子 Agent、后台 Shell 暂缓；tenantId 已贯穿调用链，完整租户授权语义继续作为生产门槛。

接缝v1.6 沿用决策失败边界
Bundle 发布 / 装载受信步骤复用共享 TS 定义生成不可变包；Java/Sidecar 共享只读目录，staging 校验资源闭包后原子发布。Session 固定 revision/ref；核验构建与模板。缺资源、摘要或版本不符拒绝准入；bundleDigest、toolManifestDigest、Hosted capabilityDigest 分型，不能互相代替。
创建 / PromptJava 创建前固定全局 RFC UUID sessionId、commandId、bundleRef、Workspace storage binding；同一 sessionId 直接交给公共 API、qwen/Harness、JSONL 与 Broker。qwen 持久 header/定义后确认创建，持久 input/WakeIntent 后确认 Prompt；原命令提供只读查询。不得生成第二套 Harness Session ID；ACK 丢失查原 receipt；not_found/过期/owner 不明不是未执行证明，不能换 ID 或空 Session 重跑。
工具阶段control 显式映射原 prepare/confirmation/confirm/preflight 及文件历史；新能力按版本协商，逐操作严格校验；Java 不重写调度与权限。环境 prepare 不代替 invocation build；status/cancel 不创建 execution；改参使旧授权失效，unknown 不重新执行。
结果 bytesRuntime 登记不可变输出；Java 代理授权资源分片；qwen 校验、持久接收完整必要引用后返回 CommitReceipt，再 ACK delivered。下载失败只续读原内容，未转存不得删除唯一副本；ACK 不等于环境可释放。
回收后下一轮持久 Workspace 与 file-history root 独立于计算环境。干净 released 后创建新 binding，挂回同一存储与稳定 history owner；Workspace generation 不变。旧 execution 永远归旧 binding；存储缺失或原执行未知则阻塞，不从 Git clone/空目录伪造恢复。

一轮工具调用的提交顺序

发布 Bundle → 创建 Session → 持久受理 Prompt → 模型先行
  Tool Call → 提交 tool.intent → 等待 Runtime / manifest / activation gate
  → bindHistory → Workspace 工具轮次占用 → beginTurn 起始快照
  → prepareInvocation → 确认 / 原权限仲裁 → confirm（需要时）
  → preflight → Harness 最终 guard → execute → 原执行查询
  → 结果 bytes 持久接收 → result CommitReceipt → ACK delivered
  → 模型继续 → 全部工具结算 → readHistory / 持久备份
  → authority checkpoint + turn.settled → 释放占用 → Runtime idle
  → 干净回收 → 下一轮新 binding 挂回原文件与历史
原 fileHistory.checkpoint(promptId) 确保的是轮次起始快照， 不是轮末持久提交。模型 Final、工具 ACK、Runtime release 分别核验。 Session 独占 Runtime 不等于文件隔离：首版同 Workspace 的工具轮次从起始快照 到 history 提交串行占用；外部文件变更仍按工具原有身份校验处理。

首版验证与参数

验证初值：环境启动 120 秒、idle 5 分钟、每 owner 最多 4 个 Runtime 和 4 个活跃模型 Turn； 有界队列最多 32、等待 60 秒；Session 工具并发 1；前台 Shell 默认 120 秒、上限 600 秒； 审批最长 10 分钟，更短既有预算优先。资源分片最多 1 MiB，单次 RPC/读取空闲期限 30 秒， 长任务用 accepted + 原状态查询；状态轮询 250 ms 至 2 秒并加抖动。 模型、输出总量与存储保留沿用既有有限预算并在启动报告列出实际值， 超时或未知物理退出仍计入容量；这些初值不代表生产容量结论。

M01～M10 加 S01～S08 验证“Edit diff → 审批 → Shell 大输出 → 持久历史 → idle 回收 → 同 Session 下一轮读到修改”，并注入 ACK/下载丢失、存储缺失与取消。 调研锚点、精确字段、封闭操作枚举、资源提交顺序、回收竞争和验收清单见 普通工具首版接线设计。 现有代码已有阶段适配基础；新契约仍待实现和跨进程验收。

01 / OVERVIEW

架构总览

关键判断：新方案不是替换 qwen serve，而是让它继续承担统一会话协议和 TS Agent 内核； 本地模式使用本地 Runtime Provider，托管模式调用 Java Control Plane 内嵌的 Runtime Broker 模块。第一阶段不新增独立 Broker 服务。
02 / SCOPE

目标与边界

本方案要解决

  • 第一次 Prompt 不等待 Runtime Pod 启动。
  • 完整复用 TS Agent Loop、Context、压缩与工具语义。
  • Legacy 和 Managed 在同一系统内渐进迁移。
  • Java统一管理 Runtime 生命周期、路由、配额和审计。
  • Tool Runtime 不持有模型凭证，不接收用户 Prompt。
  • 为后续无状态 Harness 和跨实例恢复保留演进路径。

第一阶段明确不做

  • 不使用 Java 重写完整 Agent Loop。
  • 不把 Legacy Session 原地改为 Managed。
  • 不为每个 Session 创建一个 Harness 进程。
  • 不一次性迁移 Channels、Scheduled Task、Hooks 和全部 MCP。
  • 不承诺外部副作用 exactly-once。
  • 不在第一阶段维护两份权威 Transcript。

06 / FAST PATH

第一次 Prompt 与低 TTFT

兼容产品入口由 Java 转发原请求并预热 Runtime，等 qwen 持久受理才 ACK；阶段 D 的 java_durable 入口先保存 command delivery，语义见 v1.10 契约。Harness 已经持有预发布的版本化 AgentBundle，因此模型调用不依赖 Runtime 在线发现工具。缺少必要配置快照时拒绝 Managed 准入。

08B / WORKSPACE CONTEXT · PLANNED

Workspace 归属与 Session 工作目录

Workspace 是稳定的资源归属，Session 保存相对工作目录，Runtime 负责解析实际挂载路径。 容器重建不能改变 Session 归属；Harness 的进程 cwd、私有日志目录与工具执行 cwd 分开。 旧 daemon 的本地目录路由可复用，但 Hosted 请求必须先经过 Java 的租户授权和持久绑定。

当前实现边界：Java 的 Session DTO 和 SQL 尚无 Workspace 绑定； EmbeddedRuntimeBroker 启动时读取一组全局 workspace 配置。 以下 W0/W1/W2、OpenAPI 新字段与增量 DDL 均为目标设计，未实现前不宣告能力。
字段职责与恢复边界对前端
workspaceId租户内稳定身份；路径相同也不能视为同一资源可见，经授权
workspaceGeneration / workspaceStorageId原工作区版本和持久存储；换代、丢卷不自动替换内部
cwdRelative相对 Workspace 根目录；根为「.」，拒绝越界和 symlink 逃逸可见

contextRevision上下文 CAS 与安装确认；区别于 Runtime/Harness epoch可见

创建与冷恢复

创建时选择已授权 Workspace 与相对 cwd，Java 同事务保存命令和绑定。 缺省只允许显式租户默认值；续轮和重试使用原绑定，不回退到 daemon primary。

09 / RUNTIME LIFECYCLE

Runtime 复用与生命周期

首版默认 Session 独占 Runtime：归属绑定原 Workspace scope、 workspaceGeneration 和 sessionId，同 Session 多轮复用。当前 binding 的 canonicalCwd 是已验证安装快照；可移植归属与 Session cwd 按Workspace 契约解析。 原 workspace 级跨 Session 复用作为可选优化，须先通过逻辑绑定与隔离验收。 Hosted tenantId 来自可信鉴权上下文并贯穿 binding；本地 profile 的 workspace 派生键只作兼容字段，不能冒充已认证租户。

环境 ready 与 activation gate 分开：没有活跃 Turn 时可以预热并保持 gate closed； 实际 Tool Call 仍须安装原 Session/activation 门禁并取得 enable ACK，迟到 ready 不授予执行资格。

absent→ provisioning→ preparing→ ready→ idle→ draining→ released

复用规则

  • 同 key 只允许一个 active provision；外部创建前持久保存 provisionRequestId。
  • 创建结果不明查原请求，无法确认保持待处理，不换 ID 重建。
  • 取消后迟到 ready 重新核验 Session、generation 和需求，无人持有则 draining。
  • Runtime endpoint 不由 Harness 或模型指定。
  • Workspace generation 变化时创建新 Binding。
  • 干净 idle 回收后下一轮可创建新 binding，挂回原持久文件/history，Workspace generation 不变。
  • 旧执行查询仍指向旧 binding；旧环境未知或持久存储缺失则阻塞，不能重放。
  • 启动 deadline、idle 保留时间和容量有界；同 Session 第二、三轮可复用。
  • 跨 Session 共享必须先有独立配置、权限、文件历史、gate 和释放引用计数。

释放规则

  • 有未决副作用时不能直接释放。
  • 旧 generation 先进入 draining。
  • Artifact 唯一副本未转存前不能清理。
  • Cancel ACK 不代表进程树已经退出。
  • 释放必须产生可查询 receipt。

故障场景 处理原则 禁止行为

  • SSE 只发布已提交事件；提交响应丢失先按稳定 batch/command 身份核对。
  • Relay 与消费者按至少一次投递设计，重复发布不能重复追加文本。
  • Snapshot 只覆盖已物化的连续前缀，清理不能制造重放缺口。

职责边界

  • AgentStateStore：业务事务、租约代际、游标、序号和重放。
  • EventTransport：已提交批次的异步至少一次分发。
  • SessionReplayService：拼接 Snapshot、短期日志和实时订阅。
  • SessionArtifactStore：不可变资源及摘要校验，不承担业务租约。
  • Harness 私有 journal 仍是模型上下文权威；公共 Item 不能反向重建它。
不要改成无事务双写：“Harness SSE 同时异步写 MQ 和数据库”无法保证 Session 序号、Turn 终态、源游标与公开事件一致。第一阶段先使用 SQL 可靠接受； 只有持久源日志、fencing、回放和容量数据都证明可行后，才评估 MQ-first 接受路径。

多实例 owner、通知与恢复顺序

任意入口 Java
  → SQL 查询 managed_agent_session_owner
  → 认证内部 RPC 转发 Prompt / Cancel / Approval 到 Harness owner
  → owner 以 ownerGeneration 接受 Harness 事件
  → SQL acceptBatch transaction
      ├─ afterCommit → 本节点 Hub → SSE
      └─ RocketMQ 通知
          ├─ 每 Java 节点独立广播订阅 → 本地活跃 SSE（SQL sequence 补洞）
          └─ 共享物化消费组 → Item / Snapshot

owner 故障
  → 新节点 CAS ownerGeneration + 1
  → 从 SessionArtifactStore 校验 journal/checkpoint/resource closure
  → Broker 按原 executionCallId 核对未决副作用
      ├─ 可证明 → 新 Harness 取得 writer fence 后恢复
      └─ unknown / 资源缺失 → recovery_blocked
  → 旧 generation 的事件、journal 与工具回执全部拒绝

私有 journal segment、checkpoint 和资源闭包保存为不可变 Artifact；SQL 只保存 owner、最新已提交 journalRevision、manifest 引用和摘要。 Pod 临时磁盘与 Runtime generation 目录不能成为恢复所需唯一副本。详细 CAS、 Transport 适配器和恢复 manifest 见 存储与事件设计。

14C / EXTENSION RUNTIME

扩展能力的统一运行模型

MCP、Hooks、Channels、自动化、子 Agent、后台 Shell 与 Monitor 不各自建立调度器和会话真相。它们共用 Session Authority、Runtime Broker、Artifact、Outbox、activation fence 与恢复协议：Harness 始终是唯一模型推进者，Java 持久化产品资源，Tool Runtime 执行物理副作用。

范围说明：以下是阶段 H 的目标设计。当前 Hosted Managed 首版仍只开放 Read、Write、Edit 和前台 Shell；源码中已有 MCP、Hook、Task、 Channel、Schedule、Agent、Shell 与 Monitor 实现，不代表它们已经完成远程 Runtime、持久恢复或多实例验收。

统一 owner 与持久资源

能力 执行 owner 权威记录 关键恢复边界
MCP Harness 使用固定 catalog；Runtime 持有 stdio/HTTP 连接 mcp_configuration / mcp_operation 固定 server revision 与 connection generation；远端结果未知不重发
Hooks Harness 编排；command/HTTP 在 Runtime，prompt 在 Harness hook_registration / hook_execution occurrence/ordinal 去重；async 命令保留物理 owner；once 不恢复资格

一个 Task 读模型

WebShell 统一展示 child、workflow、shell、monitor 和 automation run， 但 Task 只是由领域记录重建的投影。它不保存第二份执行真相，也不暴露 runtimeBindingId、generation、Runtime endpoint、绝对路径、原始 PID 或凭据。

三个完成状态

逻辑运行、物理执行、交付/父接收分别结算。模型完成不能冒充 Channel delivered；子任务 terminal 不能冒充父 consumed；cancel ACK 不能冒充进程退出。

有界日志与通知

Shell 与 Monitor 原始输出写分段 Artifact，公共事件只携带状态、摘要和游标。 高频相同观测先聚合，没有变化时不创建新模型 Turn，避免每行永久膨胀事件表。

后台 Shell 与 Monitor 的差别

后台 Shell

  • 启动后返回持久 process handle，模型可以继续本轮或后续工作。
  • 输出以 Artifact + cursor 读取；运行期间阻止 Runtime idle release。
  • 默认随 Session close 执行 terminate + drain；只有显式 detached 才移交 owner。
  • Runtime 丢失且无法凭 supervisor attach 时进入 recovery_blocked，不重跑命令。

Monitor

  • 持续观察目标并生成单调 observation sequence，不等于定时 Automation。
  • Runtime 聚合/去抖，Authority 接受后按策略生成一个通知 input + WakeIntent。
  • 不占 active Turn，但占进程、日志、monitor quota 与 Runtime hold。
  • 纯观察目标可从定义重建；依赖旧句柄或 offset 时 degraded/blocked。

16 / ACCEPTANCE

核心验收标准

首版运行验收以 M01～M10 为准：慢启动首 token、同轮工具、受理/执行 ACK 丢失、取消/迟到 ready、独占隔离、 重启恢复或准确阻塞、SSE 重连、容量与审批。多副本/共享 Runtime 只在启用时追加门槛。 以下保留 A～H 全量清单；跨租户隔离在生产开放前单独验收，公开序号已有实验切片， 稳定 Item/Snapshot 属于 D，跨实例接管属于 G。

  1. Runtime 人为延迟 15 秒，模型首 token 仍提前返回。
  2. 无 Tool Turn 在 Runtime 未就绪时可以正常完成。
  3. 同一 Turn 的 Tool Call 可以等待 Runtime 后继续。
  4. Legacy 和 Managed Session 在同一 daemon 中同时工作。
  5. Session 冷恢复后仍使用原执行引擎。
  6. Managed 失败不会切换到 Legacy 重试。
  7. Legacy 只能创建新的 Managed continuation。
  8. Runtime started 后断线不会重复执行工具。
  9. Cancel 后根进程和后代进程最终退出。
  10. Harness 崩溃后旧 epoch 的迟到写入被拒绝。
  11. Java重启后可以查询原 executionCallId。
  12. 不同 tenant/workspace 无法复用 RuntimeBinding。
  13. Session 创建、重试、续轮和冷恢复保持原 Workspace；同名空目录、换代或路径越界不能冒充恢复。
  14. 并发 prompt/cwd 变更只有一方准入；安装/ACK/commit 各点崩溃后恢复同一 operation，后台任务保留原 cwd。
  15. 大输出通过 artifactRef 返回，不压垮 SSE 和 Java堆。
  16. 多 Session 共享 Harness 时没有 Context 与权限串扰。
  17. Session 固定 Agent revision，更新 Agent 不改变已有 Session。
  18. 客户端断线后可以通过 eventSequence 续传，并查询相同 Turn 和 Items。
  19. 公共 API 与 qwen/Harness 共用同一个 Session UUID，但不暴露 Runtime endpoint、Pod、ACP attachment、Harness boot/instance 或 Runtime Session ID。
  20. 事务回滚时 Hub 不发布事件；提交成功后同节点 SSE 无需等待数据库轮询。
  21. Hub overflow、断线或跨节点丢通知后按公开 sequence 补齐，不重复或跳过事件。
  22. 两个 Java 实例共享真实 MySQL 时，命令幂等、单活 Turn、序号和终态保持一致。
  23. MCP/Hook 定义更新不改变在途调用，lost ACK 只查询原 operation。
  24. 后台 Shell/Monitor 运行期间 Runtime 不会 idle release，停止后真实进程树退出。
  25. child terminal、父 accepted 与父 consumed 可分别恢复，不重复创建 child 或通知。
  26. Channel/Automation 重投使用原 inputId/runId/deliveryId，未知派发不重跑模型或双发。
