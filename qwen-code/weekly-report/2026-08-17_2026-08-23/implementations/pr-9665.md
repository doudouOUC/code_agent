> PR: [feat(serve): restore ask_user_question HITL on session load/resume](https://github.com/QwenLM/qwen-code/pull/9665)
> 状态：open，未合入 `main`。
> 规模：+1349 / -55，35 个文件

## 解决了什么问题

`ask_user_question` 的待回答状态与 permission `requestId` 只存在于 ACP/daemon 内存。daemon 重启后，load/resume 会把 transcript 尾部未完成提问当作 orphan tool call 补成失败结果；旧 request id 已失效，客户端无法继续投票，模型也只能收到工具失败而不是用户答案。

直接复用通用 `continueLastTurn` 同样不合适：它会合成 error function response，并可能重复 user echo、system reminder、hook 或一次性 worktree notice，改变原回合语义。

## 当前实现方案

当前 open diff 新增默认关闭的 `qwen serve --restore-ask-user-question`。Core 的纯 history scanner 只接受最后一条 model message 全部由结构合法、带 id 的 `ask_user_question` calls 组成；同批混有其它 dangling tool、参数非法或非尾部问题都不命中，继续走现有 orphan repair。

开关启用且 cold load/resume 命中时，ACP replay 跳过这些 call id 的 orphan finalize，并通过私有 restore hint 告知 bridge。bridge 在 session entry 注册和 attach coalescing 完成后，沿受跟踪的 prompt admission path 发起一个 trusted empty prompt；外部 caller 无法伪造私有 meta。Session 不记录新的 user message、不重复 echo/reminder/hook，而是重新执行原 `ask_user_question` function calls，生成新的 `requestId` 并走既有 permission vote。真实答案写成 function response 后，模型继续同一 turn。

取消、超时和 permission channel failure 沿用 stop-after-cancel 语义并发出 conversation-finished telemetry。一次性 worktree notice 不在 restore 空 prompt 中被消费，而是在答案后的模型请求里插入。daemon 启动不会扫描或自动恢复等待会话；不开 flag 时行为保持不变。

## 关键代码路径

- `packages/core/src/core/ask-user-question-restore.ts`：尾部纯 AUQ batch 的结构校验、恢复资格与 call-id 集合。
- `packages/cli/src/acp-integration/session/history-replayer.ts` / `Session.ts`：跳过 orphan finalize、trusted restore turn、重新执行 permission call 与 post-answer continuation。

## 边界与风险

- 当前 open；默认关闭，不是 daemon load/resume 的默认契约。
- 只恢复尾部纯 `ask_user_question` batch，不恢复 exec/edit/其它 permission，也不做 boot-time auto-resume。
- 不持久化旧 request id 或 permission audit ring；恢复会生成新的 request id。
- 未提供 settings.json 开关或 capability tag，operator 与 client 需要带外确认 daemon 启动参数。
