## 解决了什么问题

loopback `qwen serve --open` 主要用于一次性启动本地 Web Shell。若 operator 未配置 bearer，daemon 对同机进程保持无认证；要求每次手工生成和传递 token 又削弱 `--open` 的交互便利。方案需要提高浏览器启动路径的默认安全性，同时不改变 plain serve、headless automation、non-loopback 或显式 token 部署。

## 当前方案

设计提议仅在同时满足 loopback bind、interactive `--open`、Web Shell 可用且没有 CLI/env bearer 时，由 CLI 生成进程生命周期 256-bit token。该 token 直接注入既有 bearer middleware，不新增第二套认证协议；显式 CLI/env token 始终优先。

browser launch URL 通过 fragment 携带 token，服务端和 HTTP access log 看不到 fragment。Web Shell 首次加载后读取 fragment、写入当前 tab 的 `sessionStorage`，再清理地址栏；后续 fetch/SSE 继续使用 `Authorization: Bearer`。新 tab 不自动共享，browser launch 失败时 CLI 输出可恢复的带 fragment URL。`/health` 与 static shell bootstrap 维持必要的 pre-auth 可达，其余 API 仍由 bearer 拦截。

bare `--open` 因此会要求 generated bearer，其他无 token 的 curl/SDK 请求得到 401；需要多客户端共享时必须显式配置 `QWEN_SERVER_TOKEN`。plain `qwen serve`、direct `runQwenServe`、headless/API-only 与 non-loopback 不自动生成 credential。

## 边界与风险

- 当前 docs-only open；token generation、browser handoff 和 Web Shell storage 均未实现。
- 不提供持久 token store、跨 tab 分享、cookie、client identity、独立 revoke 或 SDK discovery。
- fragment 只减少 token 进入 HTTP/server log 的风险；浏览器历史、扩展和本机恶意进程仍属于需单独评估的边界。
- non-loopback 不自动生成 credential；多客户端必须使用显式共享 token。
