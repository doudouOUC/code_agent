## 解决了什么问题

旧的手动退出 Plan mode 提醒只在 UserQuery 和 Cron reminder 装配阶段消费一个共享 pending boolean。这个实现有两个缺口：一是 ACP/daemon direct send、tool-result continuation、steering continuation、hook continuation 和交互式 Agent chat 可能完全收不到提醒；二是 pending 状态被所有 conversation 共享，一个 live conversation 可以在另一个 conversation 看到提醒前把它消费掉。

这会让模型在用户通过 Shift+Tab 或 `session/set_mode` 手动离开 Plan 后，没有收到“当前已经不在 Plan，需要按新模式行动”的明确信号；在多 conversation 或 Agent 场景下，同一个 approval-mode 变化还可能被错误归属。

## 最终实现方案

最终实现把“模式变化事件”和“每个 conversation 是否已投递”拆开。`Config` 不再只保存单个 pending boolean，而是维护 `manualPlanExitNoticeEventState` 和 `manualPlanExitNoticeCursorState`：前者记录最新事件版本及事件类型（manual-exit 或 clear），后者由每个 conversation 独立记录已经看过的版本。Plan -> non-Plan 的手动切换产生 manual-exit 事件；通过批准的 `exit_plan_mode` 离开 Plan 产生 clear 事件，不触发提醒；non-Plan -> non-Plan 不产生新事件。

投递点从 prompt-specific 装配逻辑下沉到 `GeminiChat` 的 live chat history commit 边界。`GeminiChat` 在 proactive compression 和 hard-rescue 检查之后、真正把 user content 写入 live history 时 claim 待投递提醒，并把提醒追加为当前 user content 的最后一个 text part。这样普通 prompt、ACP/daemon direct send、tool-result continuation、steering continuation 和 hook continuation 都走同一条 model-bound commit path，不需要各协议入口各自注入。

为了保持 exactly-once 语义，claim 后如果同步 setup 失败会 rollback 并恢复该版本的 cursor；provider retry 和 fallback 复用已经提交到 history 的同一个 entry，不会再重复追加；reactive context-overflow compression 重建 retry history 时保留已提交的精确提醒文本。提醒文本中的 mode 名称来自 claim 时的当前 approval mode，而不是事件创建时的旧值。

启用范围也做了收敛：主 chat 与 interactive agent chat 调用 `enableManualPlanExitNotices()`；fork/speculation chat、headless agent、workflow、memory helper 和 compaction side query 不启用，避免 side conversation 消费或污染 live conversation 的用户可见提醒。Agent approval-mode override 创建时继承当前事件 snapshot，保证 interactive agent 与主会话可以各自收到一次同一 inherited mode change。

## 验证方式

PR 验证覆盖变更 conversation、agent、prompt 与 exit-tool 相关的 776 个 focused tests，以及 18 个 approval-mode state-machine tests。人工侧在 macOS PTY wire capture 中复现了 Shift+Tab 后缺少提醒的问题，并验证当前 bundle 在下一次请求中只追加一次提醒、function response 位于提醒之前、后续轮次不重复。

未覆盖范围包括 Windows/Linux 本地人工执行、跨进程重启后的提醒持久化，以及外部 provider 是否真实收到失败 transport request；这些不影响本次 main 内 live history exactly-once 投递语义。
