## 解决了什么问题

大型 persisted JSONL 会话在 `loadSession` / `unstable_resumeSession` 恢复时可能超过旧的 10s initialize timeout。旧逻辑只停止等待 public caller，ACP child 仍可能继续恢复：空 channel 会被误杀，带 sibling session 的 channel 可能被杀掉，late writer lease 或 orphan session 也缺少统一清理；HTTP、ACP、SDK 和 WebUI 只能看到泛化 init timeout，排障时不知道是 restore deadline、late success、cleanup 失败还是 channel 被隔离。

## 当前实现方案

#8691 新增专用 session restore deadline。serve CLI 和 bridge option 支持 `--session-restore-timeout-ms` / `sessionRestoreTimeoutMs`，默认 60s；显式 restore timeout 优先，其次兼容显式 `initializeTimeoutMs`，并限制最大定时器值。daemon 在 `/capabilities.limits.sessionRestoreTimeoutMs` 公告有效 restore deadline，TS SDK 在 `capabilities()` 后缓存该值。

bridge 将 in-flight restore 拆成面向 caller 的 `publicPromise` 和真实 ACP settle 的 `settlementPromise`。public deadline 到期时返回结构化 `SessionRestoreTimeoutError`：REST 映射为 504、`Retry-After: 5`、retryable JSON；ACP HTTP/WS 映射为 JSON-RPC `-32603` data，带 `httpStatus:504`、`errorCode:"restore_timeout"`、`sessionId`、`action` 和 `timeoutMs`。与此同时，session id fence、pending restore event 和 admission/capacity 保留到真实 ACP request settle，避免 caller 立即重试制造重复恢复。

late ACP success 或 failure 都触发 exactly-once `qwen/control/session/close` 清理。空 channel 可以异步 reap；如果 channel 上还有 sibling session 或 workspace control work，不会因为单个 restore timeout 被杀。若 cleanup 不确定，channel 进入 quarantine：已有 session/control 继续运行，但新的 spawn/load/resume/branch 会在 capacity check 前失败，返回 `acp_channel_unavailable` / 503 / `Retry-After: 5`，reason 为 `restore_cleanup_failed`；channel drain 后再回收。

SDK restore timeout 按 per-request `timeoutMs`、显式全局 `fetchTimeoutMs`、server budget + 10s、默认 70s 的顺序派生；`timeoutMs:0` 禁用客户端计时器，且不会序列化进 request body。WebUI restore request 使用 server budget + 10s，外层 watchdog 使用 server budget + 15s，attach 仍保持 30s。过大的定时器值会被安全禁用，避免 Node timer overflow。

可观测性上，bridge 增加 `session.restore` span，向 ACP load/resume metadata 透传 prompt trace context，记录 public result、late result、cleanup/quarantine 结果和 restore action/session/channel/timeout 等低基数字段，不记录 transcript。ACP child 继续输出 `qwen-code.daemon.session_restore`，并记录 settings load、live restore、existence check、config setup、auth、file system setup、session register、response build 等 stage timing 以及 `failed_stage`。

## 边界与风险

- restore timeout 只限制 caller 等待与 channel cleanup，不保证大型 transcript 一定能在预算内恢复成功。
- quarantine 是 cleanup 不确定时的 fail-closed admission gate，不会中断已有 sibling session，但会拒绝该 channel 上的新 session 操作。
- `restore_timeout` 是 retryable 信号；caller 仍应等待或换 channel，不应在同一 session id 上并发重试。
- telemetry 只记录 restore lifecycle metadata 和 stage timing，不采集 transcript、prompt payload、auth token 或文件内容。
