# PR #8507 最终实现：可选 Mem0 记忆写入

> PR: [feat(external-context): Add optional Mem0 memory writes](https://github.com/QwenLM/qwen-code/pull/8507)
> 状态：open。本文只记录当前 diff 方案，不能视为 `main` 已落地能力。

## 解决了什么问题

Direct External Context 已支持仓库绑定的只读检索和 submitted-prompt auto recall，但可信团队没有一个窄范围的“保存一条仓库记忆”入口。直接接入 Mem0 官方 MCP 会暴露更宽的写入和管理面，也会让模型参与选择 provider、app 或语料边界。

#8507 的目标是在现有 direct profile 内增加一个显式 opt-in 的 Mem0 Direct Import 写入变体：管理员继续固定 credential、provider 和 `app_id`，模型只能提交一段待记忆内容，并且写入前必须让用户看到完整内容。

## 最终怎么实现

严格 v1 Mem0 配置只有在包含 `write: { enabled: true }` 时才注册 `context_remember({ content })`。现有 v1 检索配置、Generic HTTP provider、v2 Auto Recall Hook 和默认 extension manifest 都保持 write-free；`enabled:false`、unknown fields 或非 Mem0 写入配置会被拒绝或只暴露 `context_search`。

`context_remember` 接收最多 4000 个 Unicode code points 的 `content`，保留首尾空格、换行和 Unicode，不做总结、改写、去重或 provider/corpus 选择。approved content 会作为一条 Mem0 Platform V3 Direct Import user message 发送到 `/v3/memories/add/`，固定使用管理员配置的 `app_id`，并设置 `infer:false`。

写入路径刻意不做 pre-search、normalization、retry、polling、cache 或 dedupe。返回 `SUCCEEDED` 时报告 `stored`；返回 `PENDING` 且 `event_id` 是有效 UUID 时报告 `accepted`，表示 provider 已排队但不声称持久化完成；timeout、cancel、broken JSON、redirect、非法 HTTP status 或其它不确定结果统一转成 `unknown` MCP error，并提示不要自动重试，因为 provider 可能已经接受请求。

MCP tool annotations 明确表达写入语义：`readOnlyHint:false`、`destructiveHint:false`、`idempotentHint:false`、`openWorldHint:false`。这会和 #8387 的 unsafe MCP replay guard 配合，避免连接丢失后自动重放非幂等写入。

另行安装的 `PreToolUse` command Hook 会展示完整内容的可逆安全转义版本并要求二次确认。默认 approval 模式下，普通 MCP 权限提示之后仍会出现内容确认；YOLO 模式会跳过普通 MCP 提示，但 Hook 仍要求确认。拒绝第二次确认时不会发出 provider 请求。该 Hook 是用户体验防护，不是服务端授权边界。

## 边界与风险

- 当前 PR 是 open，仍不能作为 `main` 落地能力描述。
- 这是外部写操作；Mem0 可能在客户端 timeout 或断线时已经接受请求，重复批准相同内容也可能产生重复记忆。
- 确认 Hook 只是 best-effort UX，不提供不可绕过授权、DLP、审计保留、删除一致性、逐用户 ACL 或 headless/ACP/serve 强制审批。
- 回滚部署配置不会删除 Mem0 已经接受的记忆。
