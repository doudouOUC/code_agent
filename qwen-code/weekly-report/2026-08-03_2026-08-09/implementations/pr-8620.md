# PR #8620 · fix(serve): Allow approved same-host text reads outside workspace

链接：https://github.com/QwenLM/qwen-code/pull/8620
状态：open
规模：+519 / -32，17 个文件

## 解决了什么问题

same-host `qwen serve` 场景下，ACP 子进程的 text read 会被 daemon `WorkspaceFileSystem` 接管。这个边界适合 HTTP `/file` 和最终写入，但它是 workspace-scoped：即使用户已经在 CLI 权限层批准读取 workspace 外的普通文本，direct `read_file` 仍会被 WorkspaceFileSystem 拒绝。

这个问题还会影响 write/edit/notebook/sed/artifact 等路径的 prior read。模型为了看见已批准的外部文本，只能退回 shell 读取，既不符合工具语义，也绕开了 `read_file` 的普通 CLI 权限体验。

## 当前实现方案

PR 新增 bridge 选项 `delegateReadTextFileToClient`，并让 daemon-owned same-host bridge runtime 传入 `false`。这些 runtime 会在 ACP initialize capability 中广告 `readTextFile:false, writeTextFile:true`：read 由子进程本地 `FileSystemService` 处理，write 仍委派给 daemon WorkspaceFileSystem。

因此，direct `read_file`、write/edit/notebook/sed/artifact pre-read 都回到普通 CLI 文件系统服务和 CLI 权限判定，用户批准后可以读取 workspace 外普通文本。最终 text write 继续走 delegated `writeTextFile`，保留 workspace/trust/symlink/atomic write/audit 边界，也继续拒绝 workspace 外写入。

接线覆盖默认 embedded bridge、primary runtime、static secondary runtime、dynamic workspace runtime 四条 daemon-owned same-host 路径。通用 ACP bridge 和 caller-injected bridge 不改变默认行为，仍按宿主注入的 `fileSystem` 能力委派读写。`BridgeFileSystem` 的 read adapter 被保留下来，作为异常或违反 capability 的 delegated read 请求的 fail-closed 防线。

## 关键代码路径

- `packages/acp-bridge/src/bridgeOptions.ts`：新增 `delegateReadTextFileToClient` 选项。
- `packages/acp-bridge/src/bridge.ts`：根据该选项决定 initialize capability 是否广告 `readTextFile`。
- `packages/cli/src/serve/server.ts`、`packages/cli/src/serve/run-qwen-serve.ts`：same-host daemon-owned bridge 构造传入 `delegateReadTextFileToClient:false`。
- `packages/cli/src/acp-integration/service/filesystem.ts`：子进程侧 `FileSystemService.readTextFile` 保持本地读取与权限语义。
- `packages/cli/src/serve/bridge-file-system-adapter.ts`：保留 delegated read fallback，write 继续委派 WorkspaceFileSystem。

## 验证方式

PR diff 覆盖 bridge capability、server default wiring、primary/static/dynamic workspace runtime 接线、ACP filesystem service 与 serve streaming integration。真实场景测试验证 same-host daemon 中，用户批准后 direct `read_file` 能读取 workspace 外文本；最终 write/edit 写入仍被 WorkspaceFileSystem workspace 边界拒绝。
