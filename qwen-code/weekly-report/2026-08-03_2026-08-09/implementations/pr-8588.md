# PR #8588 最终实现：daemon activeWork 深度健康状态

> PR: [feat(serve): Expose active work state](https://github.com/QwenLM/qwen-code/pull/8588)
> 状态：open draft，记录当前 diff 方案；不能视为 `main` 已落地能力。

## 解决了什么问题

`GET /health?deep=1` 之前可以报告 `activePrompts`，但它只覆盖 daemon 已接受且尚未 settle 的主 prompt。主 prompt settle 后，如果 background Agent 仍在运行，或 Agent terminal notification 仍在接受、排队、持久化、由父 session continuation 处理，`activePrompts` 已经归零。

这会误导 restart controller 或外部 supervisor：它们可能把 daemon 判定为空闲并重启，导致后台 Agent 的最终通知丢失或父 session continuation 被打断。仅靠 session count、pending permission 或 channelAlive 也不能表达“仍有用户关心的工作尚未归档”。

## 当前实现方案

#8588 在 `GET /health?deep=1` 返回体中新增 additive boolean `activeWork`。聚合逻辑遍历所有 managed runtime，包括 draining runtime；任一 runtime 的 bridge 报告 active work 时，daemon-wide `activeWork` 为 true。若任意 getter 失败，deep health 仍沿用 fail-closed 错误行为，不把未知状态伪装成空闲。

bridge 侧把 active work 定义为三类未 settle 工作的并集：`pendingPromptCount > 0` 的 accepted-but-unsettled prompt、正在接受/等待/处理的 Agent terminal notification、以及 ACP child 上报的 background Agent active 状态。生命周期门控从只看 `pendingPromptCount` 改为 `entryHasActiveWork()`：自动 detach cleanup、spawn-owner wanted kill、attach rollback、last-client-detach close、idle reaper 等路径都会保留仍有 active work 的 session；显式 close、kill、shutdown 和 channel exit 仍保持强制语义。

daemon 与 ACP child 通过 `initialize._meta["qwen.daemon.activeWorkHeartbeat"]` 私有版本能力协商。daemon 请求 v1 和 15s heartbeat interval；支持的 child 在 response meta 中确认后，Session 会在 active 状态变化时按单调 seq 串行发送 `qwen/notify/session/active-work`，并在 active 期间每 15s 发送 heartbeat。bridge 校验通知来自 owning channel、session 属于该 channel、seq 严格递增，旧 child 或未确认能力时保持旧行为。

为了避免支持能力的 child 静默卡死，bridge 为处于 active prompt 或 child active work 的 session 设置 45s heartbeat deadline。超过期限仍未收到预期上报时，daemon 回收 owning ACP channel，让上层恢复路径处理，而不是把过期 active 状态永久钉住。deadline 在 session close/die/shutdown、restore rollback、channel exit 等路径清理。

child Session 侧同步扩展 `isIdle()`：除了 closing 和 active turn，还检查 active prompt request、background task registry、Agent notification acceptance、pending Agent notification 与 notification processing。background task status change、notification enqueue/drain、prompt admission/settle、dispose 都会发布 active-work transition，保证 activeWork 覆盖主 prompt 后的 Agent 后续工作。

PR 声明已跑 repo build/typecheck，并补 ACP bridge、ACP agent initialization、Session active-work reporting 和 deep-health aggregation 相关 focused/full unit tests。重点验证包括：旧 child 不协商时保持旧行为；支持 child 上报 active/idle transition；seq 回退、非 owning session、错误 channel 被忽略；45s heartbeat timeout 回收 channel；deep health 统计所有 managed runtime 且任一 active work 使全局 activeWork 为 true。

评审可手工验证：

```bash
curl -s "http://127.0.0.1:4170/health?deep=1" | jq '.activeWork, .activePrompts'
```

在主 prompt 已 settle 但 background Agent 仍运行或 Agent terminal notification 正在处理时，预期 `activeWork:true`，即使 `activePrompts` 已为 0。restart controller 应用 `health.activeWork === true || health.activePrompts > 0`，并继续保留多次采样、grace period 和 graceful shutdown。

## 边界与风险

- `activeWork` 是“仍有工作未 settle”的 restart guard，不是真实 liveness；wedged child 仍需 TCP/进程/trace/log 观测配合判断。
- background shell、monitor、workflow、cron job、follow-up suggestion 等不在 #8588 activeWork 范围内。
- 旧 ACP child 不支持 private meta capability 时不会上报 child active work，daemon 保持旧 `activePrompts` 行为。
- 45s timeout 是 fail-closed 回收 channel，不保证工作成功恢复；它只避免 stale activeWork 永久阻塞 idle 判断。
- 当前仍是 draft open；后续如 active-work 范围、heartbeat interval 或 restart-controller guidance 调整，文档需要按最终 diff 复核。
