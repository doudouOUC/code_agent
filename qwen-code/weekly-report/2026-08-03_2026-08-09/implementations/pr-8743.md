## 解决了什么问题

daemon 的 persisted session restore 当前在 `loadCliConfig()` 中先调用一次 `SessionService.loadSession()`，到 `Config.initialize()` 获得 writer lease 后又再调用一次。两次都会完整 materialize persisted transcript，随后才在 UI replay 阶段应用 `historyPageSize`。

这意味着大型 JSONL 会话即便调用方只需要最近一页历史，也会付出重复全量读取、重复 JSON materialization 和高内存峰值成本。#8691 已把长 restore 的 timeout、cleanup 和 quarantine 做安全化，但没有改变“全量读两次再裁剪”的 restore 形态；#8743 是后续实现 selective restore 前的审阅设计。

## 当前实现方案

#8743 不改运行时代码，只新增 design doc 与 plan doc。方案定义 daemon 内部的 selective restore projection，而不是直接把 `conversation.messages` 的局部切片传给各消费方。

核心类型包括 `SelectiveSessionRestoreOptions`、`SessionRestoreProjection`、`SessionRuntimeResumeState` 和 `SessionRestoreReplayPage`。`replay` 支持 `none | all | recent`：`none` 用于 resume，`all` 保留旧客户端省略 `historyPageSize` 时的完整可见 replay，`recent` 使用数量限制、4MiB source byte 软预算、16MiB expansion ceiling、anchor、`hasMore`、`partial` 和 bounded `replayError` 表达有界页面。

runtime resume state 只包含各 consumer 明确需要的最终状态，例如 model `apiHistory`、token/usage、UI telemetry、attribution、history gaps、recorder state、file-history final snapshots、active branch artifacts、goal records、initial turn 和 background notification task ids。设计明确区分完整 active parent chain 的 `runtimeUuids` 和可见 replay chain 的 `replayUuids`，避免把用于模型恢复的继承上下文误当成 UI 可回放页面。

索引层不新建并行 scanner，而是扩展现有 `SessionTranscriptReader` / transcript index。cold restore 在 writer lease 内构建 fresh index，成功后可把完整 index 发布到 cache；metadata hints 覆盖 compression、usage、telemetry、attribution、user turns、background tasks、title/source、goal、file history 和 artifacts。运行时只读取 deduped union records：最新有效 compression + tail 或无 compression 时的 full active model history、统计/归因/recorder/goal/file history/artifact/ACP initial-turn/background-task 所需记录，以及 requested replay page。

失败语义也被前置成契约：超过 256MiB 的 cold restore 返回 request-scoped `413 transcript_too_large`，不 fallback 到旧全量 loader；snapshot unavailable、mixed ids、writer-change 失败请求；单条 replay record 过大时可返回成功 runtime + `partial:true` + bounded replay error； malformed compression 被忽略并回退到前一个有效 compression 或 full active model history。

当前 PR 是 docs-only draft，验证重点是方案可执行性而非运行测试。计划文档要求后续实现补充 parity fixtures，逐项对比旧 full loader/reducer 与 selective projection；覆盖 recent/all/none replay、byte/record limits、history gap、compression fallback、file history/artifact/goal/notification state、413 sibling survival，以及 lifecycle 中只构建一次 index、不再调用旧 full loader 的断言。

## 边界与风险

- #8743 只新增设计文档，不改变 `loadSession` / `resumeSession` 当前运行行为。
- selective projection 是 daemon 内部实现细节，不新增公开 REST/SDK 字段；如需要 loadReplay envelope anchor，也应保持 internal/additive。
- 413 不应 fallback 到旧 full loader，否则会重新引入无界 materialization 风险。
- replay 的 recent page 与 runtime model history 是两个不同消费面，不能用 UI 页面的 visible subset 替代模型恢复所需 state。
