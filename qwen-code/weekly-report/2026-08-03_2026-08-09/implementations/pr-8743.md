## 解决了什么问题

daemon 的 persisted session restore 当前在 `loadCliConfig()` 中先调用一次 `SessionService.loadSession()`，到 `Config.initialize()` 获得 writer lease 后又再调用一次。两次都会完整 materialize persisted transcript，随后才在 UI replay 阶段应用 `historyPageSize`。

这意味着大型 JSONL 会话即便调用方只需要最近一页历史，也会付出重复全量读取、重复 JSON materialization 和高内存峰值成本。#8691 已把长 restore 的 timeout、cleanup 和 quarantine 做安全化，但没有改变“全量读两次再裁剪”的 restore 形态；#8743 是后续实现 selective restore 前的审阅设计。

## 最终设计内容

#8743 最终不改运行时代码，只新增 design doc 与 plan doc。最终设计把交付顺序固定为 #8691 timeout/late-result safety、transactional WebUI session switching、selective daemon restore、durable checkpoints；runtime 实现必须等待前两个前置条件。

方案定义 daemon 内部的 cold restore projection 和窄 live projection，而不是直接把 `conversation.messages` 的局部切片传给各消费方。冷 restore 执行一次完整顺序索引扫描，加 bounded selected-record seeks；每次只聚合一个 UUID aggregate，使用很小的 glued-line cache，并从 active chain 推导 side-task 边界。新鲜索引只在请求成功验证后非覆盖式进入 cache，避免并发 restore 相互 clobber。

核心类型包括 `SelectiveSessionRestoreOptions`、`SessionRestoreProjection`、`SessionRuntimeResumeState` 和 `SessionRestoreReplayPage`。`replay` 支持 `none | all | recent`：`none` 用于 resume，`all` 保留旧客户端省略 `historyPageSize` 时的完整可见 replay，`recent` 使用有界页面。最终设计把显式 recent bulk replay 精确上限定为 32MiB 和 10,000 updates；第一个额外 byte 或第 10,001 条 update 都应触发 typed page-too-large failure。内部 load-replay envelope 保持 version 1，仅新增 optional `anchorRecordId`，不新增 public REST/SDK success field。

runtime resume state 只包含各 consumer 明确需要的最终状态，例如 model `apiHistory`、token/usage、UI telemetry、attribution、history gaps、recorder state、file-history final snapshots、active branch artifacts、goal records、initial turn 和 background notification task ids。设计明确区分完整 active parent chain 的 `runtimeUuids` 和可见 replay chain 的 `replayUuids`，避免把用于模型恢复的继承上下文误当成 UI 可回放页面。

生命周期上，设计要求 one-shot Config handoff、从 scan 到 atomic publication 的 session-id reservation、map-independent provisional teardown，并在 runtime FileHistoryService hydration 或 provisional Session 构造前完成 ACP 成功响应构建。Goal restoration 拆成 memoized preparation 和 activation：activation 等待已启动的 preparation，dispose 会 settle 否则可能悬挂的 readiness，checkpoint verification/continuation 只能在发布后基于 projection 内有界 evidence window 启动。发布后 activation 先启用 receivers，再 drain capture-only callbacks，最后调度 producers，各组件有独立幂等 latch 和失败隔离。

失败语义也被前置成契约：超过 256MiB 的 cold daemon transcript 返回 request-scoped `413 transcript_too_large`，不 fallback 到旧全量 loader；explicit recent replay 超过 32MiB 或 10,000 updates 返回 `transcript_page_too_large`；typed ACP `-32010/-32011/-32012` 与 REST 409/413 保持一致映射。Direct-ACP live restore 失败保留已有 Session，cold restore 失败不留下目标状态。

## 边界与风险

- #8743 只新增设计文档，不改变 `loadSession` / `resumeSession` 当前运行行为。
- selective projection 是 daemon 内部实现细节，不新增公开 REST/SDK success 字段；loadReplay envelope anchor 保持 internal/additive。
- 413 不应 fallback 到旧 full loader，否则会重新引入无界 materialization 风险。
- replay 的 recent page 与 runtime model history 是两个不同消费面，不能用 UI 页面的 visible subset 替代模型恢复所需 state。
- process-global attribution 对 child pre-publication failure 保持不变，但 #8691 public timeout 后 child late publication 的短暂 attribution 例外被明确记录，session-scoped attribution 或 parent/child commit acknowledgement 不在 #8743 范围内。
