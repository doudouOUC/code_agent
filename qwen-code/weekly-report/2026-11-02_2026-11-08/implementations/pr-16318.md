## 解决了什么问题

无界 platform 线程和 HTTP dispatch 可耗尽宿主；本地启动容量拒绝如果被当作普通 provision 失败写成 RECOVERY_BLOCKED，会让实际尚未启动的原 binding 永远不能重试。相反，已启动或 attestation 后失败又不能借容量错误重放。

## 当前实现方案

当前 open diff 把本地 provisioner 控制任务改为命名虚拟线程，每实例最多 32 个并发 startup，permit 在任务内部 tryAcquire 并 finally 释放，取消 future 不提前释放运行中的名额；worker stdout 继续用独立 daemon platform 线程以避 Java 21 pipe pinning。Broker HTTP 用 64 上限的 platform pool/SynchronousQueue/AbortPolicy，超量关闭连接而不在 dispatcher 执行或排队。只在 local-process provision 阶段返回精确 retryable 503/runtime_local_capacity 时保同 binding/seed 重试；必要时 CAS 清掉尚未启动的 synthetic v1 placeholder，replacement owner 不被改写，attestation 同码或其他启动失败仍阻止恢复。另包含 deferred null map 的异步 400、SSH 清理 warning（仅异常类名）、命名线程、常量/正则和契约注释/无用代码清理。warm 完成后仍需 acquire；drain 完成不等于物理停止或存储可释放。
