## 解决了什么问题

停 Runtime 后不能仅凭配置选择判断 Skill/MCP 是否实际发现，也不能用历史对话准确查看直接子调用及其授权链接。

## 最终实现方案

最终实现已进入 main，只增加 resources 与 agent-trace 两类 Public GET/WebShell POST 查询及 Java SDK、生成类型和 WebShell 两页签，不包含 context-usage/stats/activity。服务先 requireReadableSession，在短只读 REPEATABLE_READ 事务查既有 definition/资源/config_install/MCP/task 投影；不 attach、warm、恢复 Runtime 或重新发现。清单核原 snapshot/bundle，以最多 64 条配置链、256 条 MCP 历史加 sentinel、8 MiB 读取/1 MiB 响应预算区分配置选择、历史 catalog、最新尝试/失败与 liveState unknown；超限标 partial，旧成功不掩盖最新失败。agent-trace 的 direct-invocations 在 SQL 分页前过滤 child_agent，limit 1–100，游标绑定 tenant/actor/session 与原时间/task；父 task 在 child 缺失/不可读时仍保留，仅独立子授权及 parentSessionId/parentChildRunId/depth 谱系匹配才给链接。private/no-store，查询不变更执行深度，不新增业务表或推进 reader floor。
