## 解决了什么问题

Store 分片后的静态锁序解析器持续膨胀，既要解析间接调用，又难证明实际事务连接和失败分支。若仅为减少查询删锁，则可能在 standalone、别库事务或 CSI owner read 中丢失原 root 围栏。

## 最终实现方案

AgentStoreRows 新增普通/legacy 两种 Session+Turn 成对读取 helper，以 Java 参数求值顺序先执行原 Session/stream 准入与锁，再锁 Turn。七条恢复/绑定/回撤/事件路径复用 helper，保留各自 owner/lease 和错误优先级；单行 CAS、空事件和被 CSI 拒绝路径不被强行改成同一加锁流程。

JournalFencing 在已做 CSI check 的路径检查本 JdbcTemplate 的目标连接：只有非 autocommit 且确实归当前 DataSource 事务时才走 root-already-locked 的 head 读取，否则沿原 requireHeadForUpdate。不是仅凭全局存在事务或 continuation 为 null 推断持锁。JournalCommit 复用已读取的 CSI head，避免重复 root/head；普通重放仍提前返回，普通 standalone heartbeat 的 head-only 契约保留。owner/native read 的准入/完成重验同样保原授权、receipt 和事务连接边界。

测试把 SessionRowLockOrderTest 缩为精确签名/完整事务属性和受保护 SQL literal 所有者清单；它不再声称静态控制流证明锁序。新增 StoreLockTrace 记录真实 JDBC SQL、映射、连接/事务及 commit/rollback，Agent/Journal 契约测试通过真实 Spring 事务代理断言执行顺序、同事务、拒绝分支、重放与通知时序，并提供复用场景的 MySQL IT。条目清单标注场景类别，不等于每个入口每个分支均有运行时覆盖。最终 head 已接入 #16142 的内部默认重载清理；相对上一观察的主要代码变化是这些已删中转，不改变本项锁协议。

最新 main 演进：#16223/#16225/#16256/#16268 将指定受理/命令/journal/inline 路径按 Session 行排序，并对普通 storage admission、authority mirror 用共享当前读；#16275 cleanup lane 保有界 placement。这里的执行轨迹契约也随各 PR 测试同步，旧精确清单不是永不变化的锁集合。

2026-11-06 最新 main 复核：#16327 队列/创建首锁、#16329 Session 共享准入及 #16335/#16354/#16370 普通 publication 的三步去锁均有新执行轨迹/并发测试；旧清单不作为当前完整锁集合。

2026-11-07 最新 main 复核：#16415 将普通 execution control 改为已有 Session root 证实非 CSI，root 缺失/CSI 保 guard；#16410 普通 snapshot writer 复用无 guard 分支，原 expected head/lease 保留。执行轨迹清单随真实路径演进，不证明全部分支。

2026-11-08 最新 main 复核：#16478 合格 admit 首锁 root 并让 drain 同 root 排序；#16480 仅租约控制复用无 guard，CAS 保原路径。执行清单随新消费者演进，不推断全分支无锁。
