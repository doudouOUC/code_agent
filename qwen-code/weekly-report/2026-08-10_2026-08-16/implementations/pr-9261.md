## 解决了什么问题

`GET /workspaces/:workspace/sessions` 是 persisted catalog 查询，会按请求形状扫描 JSONL、读取 organization/worktree sidecar、过滤分页，并合并 bridge live state。把它当成高频 active/waiting/client-count 探针，会让轻量 volatile status 刷新反复触发最重的 catalog 路径，大型或慢 session store 下容易把 sidebar/status polling 变成 timeout 风险。

## 当前设计方案

#9261 当前 open draft 只新增设计文档，不包含生产路由或 Web Shell 行为变更。方案规划新增 `GET /workspaces/:workspace/sessions/live-state`，仅从 selected trusted workspace runtime 的 bridge 内存读取，返回 `v:1`、`catalogVersion:{generation,revision}` 与完整 live session volatile snapshot。该路由不访问 storage、settings、commands 或 ACP child，不接受 query，也不 fallback primary；untrusted workspace 继续 403。

catalog version 是 daemon-local equality token。bridge 提供 `getSessionCatalogVersion()` 和 `markSessionCatalogChanged()`，`generation` 随 bridge 重建变化，`revision` 只在当前 generation 内单调递增；客户端只能比较整对 token 是否相等，不能做 revision arithmetic。revision 覆盖 live membership、display name、worktree summary、persisted branch/fork commit、archive/delete/organization/group 等 catalog membership/static metadata 变化；普通 prompt/transcript activity、attach/detach/permission wait 等 volatile state 不递增，而由 live-state response 直接携带。

设计还规定 route 维护 `WeakMap<AcpSessionBridge, BridgeSessionCatalogVersion>` 的 last-exposed version。首次或变更后暴露新 version 前，必须同步失效 active 与 archived persisted catalog cache，避免客户端看到新 token 后又命中旧 catalog snapshot。客户端 handshake 是 `live A -> full sessions -> session groups(如启用) -> live B`，只有 A/B 相等且资源请求在 A 之后启动并成功，才能接受 bundle；版本驱动 reload 需要 coalesce 和 backoff。

## 边界与风险

- 当前为 open draft，未合入 `main`，也未实现 REST route、bridge clock、cache invalidation 或 SDK/Web Shell 调用。
- 该协议不观察其它 daemon、TUI 或外部进程直接写入的 persisted store；停止全量 catalog polling 后，这些变化没有有界发现时间。
- 普通 turn activity 不递增 catalog version，跨 controller 的 ordering/updatedAt 可能到下一次 catalog reload 才刷新。
- 未来实现若遗漏 daemon-owned writer，或在失效旧 catalog cache 前暴露新 revision，会产生错误稳定的 catalog version。
