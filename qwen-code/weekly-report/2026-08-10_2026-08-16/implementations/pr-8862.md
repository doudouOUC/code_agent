# PR #8862 最终实现：OpenAI API 日志后台保留清理

> PR: [feat(cli): add background cleanup for OpenAI API logs](https://github.com/QwenLM/qwen-code/pull/8862)
> 状态：merged，已合入 `main`。
> 规模：+715 / -8，8 个文件

## 解决了什么问题

启用 `model.enableOpenAILogging` 后，每次 OpenAI-compatible API 调用都会把完整 request/response 写入新的 JSON 文件。旧实现没有 rotation/retention；重度使用场景可在两个月产生约 34.2 万个文件、95 GB 数据，并长期保留完整 prompt 与模型响应，既消耗磁盘/inode，也扩大敏感数据驻留时间。

## 最终实现方案

#8862 把 OpenAI API 日志保留接入现有 interactive background housekeeping。新增配置 `model.openAILogRetentionDays`，默认 7 天；`0` 表示约 1 小时的最短保留期。设置 schema 与 VS Code companion schema 同步暴露该字段，用户文档补充配置说明。

清理器 `cleanupOldOpenAILogs` 只接受 `OpenAILogger` 实际生成的文件名契约：`openai-<UTC timestamp>-<id>[-suffix].json`。它先用文件名中的 UTC 日期和 cutoff day 快速判断，大多数文件不需要 `stat`；正好落在 cutoff day 的文件再用 mtime disambiguate。目录通过 async iterator 流式扫描，删除并发有界；非匹配文件、目录和用户自己的 `openai-*.json` 导出不会被触碰，log 根目录本身也不会删除。

scheduler 侧为每个解析出的 log dir 使用独立 marker，最多每天成功清理一次。首次 housekeeping 同时检查 file-history marker 与 OpenAI log marker：OpenAI marker 缺失或超过 7 天时使用 1 分钟 catch-up delay，只有所有适用 marker 都新鲜时才走 10 分钟普通延迟。默认 per-workspace log dir 使用 merged settings retention；自定义 `model.openAILoggingDir` 只能使用 user/system 级 retention。若 trusted workspace 提供 workspace-scoped retention 导致同一个自定义目录策略歧义，则跳过清理并不写 success marker。

## feature 文档处理

已在 telemetry-observability 与 auth/provider 文档中补充 OpenAI API log retention：它是本地日志/磁盘/隐私保留控制，不改变 OTel export、provider auth 或请求本身。

## 边界与风险

- headless `-p` 和 SDK-only 进程不启动 interactive housekeeping，仍可能累积日志；写入路径同步清理是后续工作。
- 删除谓词刻意匹配 writer 契约而非宽松 reader；若 `OpenAILogger` 文件名变化，测试会提醒清理器同步更新。
- 自定义目录不编码 workspace ownership，因此 workspace-scoped retention 被视为歧义并跳过，用户需把策略放到 user/system scope。
