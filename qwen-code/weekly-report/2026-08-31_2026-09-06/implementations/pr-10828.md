> 规模：+729 / -0，5 个文件

## 解决了什么问题

当前 Conversations runtime 由 process-global owner 锁住，同一 Conversations root 上只允许一个 daemon 挂载。这个边界避免了多进程写坏 transcript，但也会让第二个 daemon 的全部 standalone surface 返回 `conversation_runtime_in_use`，即使两个 daemon 从不同时操作同一 session。简单移除 owner 还会遗漏 shared task file、scheduled-task rehydrate 与 deletion journal reconciliation 这些跨进程写入入口。

## 当前实现方案

当前 docs-only 方案允许多个更新后的 daemon 挂载同一 Conversations root，但把所有写路径收敛到强制 per-session writer lease：standalone、Live 和 scheduled task 只要可能写同一 session，就必须先获得相同 lease。第二个 daemon 操作已被占用的 session 时返回 `409 session_writer_conflict`；active session 保持 daemon-local，不新增跨 daemon routing、共享 live index、分布式 cache 或一般意义的 multi-master。

方案同时收紧 stale active owner 回收。只有 well-formed、unsealed record 可证明属于同一 local identity，且进程确定死亡或 PID 已复用时才允许回收；Linux 还要求 hostname、boot ID 和 PID namespace 一致。live、stalled、foreign、字段不全或判断不确定的 owner 继续被 fence。现有 process-global owner 降级为迁移期 inspect-only 检查：live legacy owner 仍返回 503，精确可证 stale owner 才移除，更新后的 daemon 不再新写 owner。

scheduled task 不另造 task lease：同一 bound controller 的并发恢复先由 session lease 选出唯一 resident scheduler；unbound durable task 在跨进程 task-file transaction 提交唯一 controller binding 前保持 dormant，失败方可清理 orphan。它只消除并发 restore/binding 造成的重复，保留 prompt dispatch 到 fired-state 持久化之间既有 at-least-once 窗口。deletion-journal reconciliation 遇到 session lease contention 时按“另一 daemon 正在处理”跳过该 UUID，不把无关操作判为 compromised。WebShell 的同版本最低行为要求把 list/legacy-owner 错误显示在 Recents section，把 writer conflict/unavailable 显示在受影响 session/section 并提供 retry，不通过 navigation global toast 重复报错。

## 边界与风险

- PR 仍为 open 且仅修改设计文档；当前 `main` 仍执行 process-global Conversations ownership。
- 方案不提供同一 active session 的并行写、跨 daemon active routing、共享 live state、原子 multi-session 操作或 exactly-once scheduled-task delivery。
- WebShell inline error treatment 是未来实现的同版本要求，不是该 docs-only PR 已交付的 UI 行为；`activeElsewhere` 仍明确延期。
- stale reclaim 依赖可证明的 local process identity；任何缺失或不确定状态都必须保持 fenced。
