# PR #10719 最终实现：fresh standalone 首屏模型选项

> 状态：merged；2026-09-02 复核到合并 head `4ad78100f8`，以下按最新 `main` 中的最终实现记录。
> 规模：+1,524 / -44，36 个文件

## 解决了什么问题

WebShell 为 standalone chat 延迟到首次 prompt 才创建 session，但 provider/model catalog 以前也只能在 session attach 后获得。新打开页面因此会显示空 model picker；即使用户预选模型，创建后再 best-effort switch 也可能失败，使首个 prompt 已经用 daemon 默认模型运行。

## 最终实现方案

最终实现新增 `standalone_session_options_v1` capability 和只读 `GET /standalone/session-options`。route 不接受 query/body/workspace selector；`StandaloneSessionService.getOptions()` 获取 exact internal Conversations runtime，在 runtime generation activity 与 exact root proof 内读取 workspace provider status，并确认返回 `workspaceCwd` 与 runtime 一致。response 只投影 version、initialized、current、approvalMode、providers 和脱敏 errors，不暴露内部 Conversations path 或 ACP live state，也不创建 session/目录。

TypeScript SDK 只有在 capability 存在时请求 endpoint，并对整个 response 做有界、strict runtime validation：provider/model/config options、approval mode 和 error kind 只接受已知形状。WebShell standalone provider 在 deferred startup 读取 options，用既有 provider mapper hydrate model/reasoning controls；读取失败或旧 daemon 缺 capability 时保持 picker 隐藏，但不阻止首个 prompt 使用 daemon 默认模型。

首次 prompt 创建时，selected `modelServiceId` 与 approval mode 一起进入已有 standalone create request。standalone path 不再执行 attach 后的 best-effort `setModel`；reasoning effort 仍在 attach 后应用，但 `persist:false`，不写入内部 Conversations workspace。非 standalone create 不允许 per-call model，原 workspace flow 保持原行为。

## 边界与风险

- `standalone_session_options_v1`、route、SDK method 和首屏模型 hydration 已合入；客户端仍必须兼容旧 daemon 缺 capability。
- fresh page 会获取 internal Conversations runtime，但请求只读且不创建 session；失败时 UI 退化到 daemon 默认模型，不自动创建 workspace session。
- Windows/Linux 浏览器、Global New Chat、Recents、uploads、Live、workspace flow 和 daemon lifecycle 不在该 PR 的验证范围。
