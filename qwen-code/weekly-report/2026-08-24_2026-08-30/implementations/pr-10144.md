## 解决了什么问题

REST existing-session scheduled-task path 可绑定一个刚创建但还没有 transcript 记录的 session。task metadata 虽然提交成功，daemon 重启后却无法从 storage 恢复该 session，留下指向不可恢复对象的 durable task。

## 最终实现方案

`AcpSessionBridge.ensureDefaultSessionPersisted(sessionId)` 通过 private existing-session extension 写入 `{sessionId, sourceType:'default'}`，并与 transport close 竞争、受 initialize timeout 约束，只接受 `{persisted:true}`。空会话因此得到隐藏的 `system/session_source` anchor；该操作不触发模型、hooks 或用户可见消息。

REST task binding 在 task persistence 前调用该能力，并在前后重查 selected runtime generation。能力未安装返回 409 `session_binding_unavailable`，session 不存在返回 404，持久化失败返回 500。trusted current-session `cron_create` 已位于 persisted prompt 内，不重复执行；unbound dedicated task 行为不变。若后续 task commit 失败，caller-owned transcript anchor 可安全保留，不做危险 rollback。

## 关键代码路径

- `packages/acp-bridge/src/bridge.ts` / bridge types：private existing-session persistence extension 与 close/timeout handling。
- `packages/cli/src/acp-integration/session/Session.ts`：把默认 source 写入 transcript 的受控入口。
- `packages/cli/src/serve/routes/scheduled-tasks.ts`：REST binding 前置持久化、错误映射与 generation fence。
- route、bridge 与 real-daemon integration tests：覆盖空 session、能力缺失、失败和重启恢复。

## 边界与风险

- 只修复 REST existing-session binding；trusted current-prompt 与 unbound dedicated path 保持原语义。
- task commit 失败可能留下无可见内容的 source anchor，这是有意的安全残留，不代表 task 已创建。
- 持久化仍依赖 selected runtime generation 和 bridge transport 可用。
