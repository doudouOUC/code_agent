## 解决了什么问题

QQ 和微信 adapter 允许同一 chat 并发多个 daemon session。若共享 chat-level latest message、stream 或 typing 状态，较晚完成的异步 response 可能引用另一条入站消息，segment retry 也可能漂移；一个 session 完成还可能提前取消另一个 session 仍需要的 typing indicator。

## 最终实现方案

QQ 定义 `QQReplyContext {chatId,msgId,timestamp}`，同时维护 message-id map 和 latest-by-chat compatibility view。`AsyncLocalStorage` 将入站 reply context 绑定到完整异步调用链，stream state、chunk/final delivery、延迟 flush 和 retry 都保留 segment-origin context；context 与 msgSeq 在 5 分钟 TTL 后清理。

微信把 chat-scoped typing set 改为 `Map<chatId, Map<sessionId,count>>` 和 session owner tracking：单个 session 完成只释放自己的引用，最后一个 owner 离开才取消 indicator。示例 adapter 同样使用 `AsyncLocalStorage` 与 `ChannelOutputSegmentContext.messageId`，保证重叠消息乱序完成时精确回复。公共 adapter interface、routing 和 persisted QQ schema 不变。

## 关键代码路径

- `packages/cli/src/daemon/channels/adapters/qq/`：reply context、stream state、TTL cleanup 与 session-aware delivery。
- `packages/cli/src/daemon/channels/adapters/weixin/`：chat/session typing ownership 与引用计数。
- `packages/cli/src/daemon/channels/examples/`：示例 adapter 的 async reply context。
- QQ、Weixin 和 plugin example tests：覆盖重叠 session、乱序完成、retry 与 typing 生命周期。

## 边界与风险

- TTL 后才到达的超长延迟投递会失去已清理 context，adapter 必须按既有失败路径处理而不能猜测目标消息。
- 变更只解决进程内并发归属，不提供跨进程 delivery journal 或 exactly-once 保证。
- QQ/微信真实平台限流、重连和错误码行为未做 E2E 验证。
