## 解决了什么问题

standalone daemon routes、capability、TypeScript SDK 与 #10418 显式 provider context 已合入，但用户仍看不到 standalone chat 入口、Recents catalog、生命周期操作或恢复状态。若 UI 继续从空 cwd 猜测目标，还会在失败时错误回退 primary workspace，并让项目控件出现在 standalone/Live 会话中。

## 当前实现方案

当前 docs-only 计划建立固定入口路由表：Home/global New Chat 设置 pending standalone context，项目/Goals/Git 入口保持 exact workspace，当前会话 New Chat 继承显式 context，Live 当前会话 New Chat 继续走既有 `startLive('new')`。Capability 处于 loading 时等待；加载失败时 fail closed；只有加载成功且明确缺少 `standalone_sessions_v1` 才允许 legacy primary fallback；capability 已存在但 create 失败时必须保留 standalone intent 并展示结构化错误。

计划新增顶层 standalone Recents，并把 active/archived 分 lane，消费分页 list 与 rename/export/archive/unarchive/delete；partial-success lifecycle response 逐 ID 解释。深链使用 `/session/<id>?context=standalone`，在 provider mount 前先按 exact standalone owner 解析，archived summary 先 unarchive 再 load，创建中状态只做有界 poll并取消 stale resolution。Standalone/Live 隐藏 workspace selector、Git、项目设置、文件浏览、pin/group 和两类 upload，同时隔离 commands、skills、`atWorkspaceCwd`、draft/history 等 composer 状态；旧全局 history fallback 对 standalone 禁用，Git status 与 `/diff`、`/log`、`/prs`、`/settings`、`/schedule`、`/memory` 等 workspace effect/handler 也按显式 context 阻断。Scheduled Tasks 等 workspace-maintenance caller 必须先解析 exact cwd 并传 workspace intent，不能从 standalone 继承；context 切换丢弃 held attachments，提交边界再次拒绝。typed recovery 覆盖 recreated/missing/compromised directory、repair/reload、creation outcome unknown、archived 与 `fileCleanupPending`。本 PR 只有计划文档，没有修改 WebShell/WebUI 运行时代码。
