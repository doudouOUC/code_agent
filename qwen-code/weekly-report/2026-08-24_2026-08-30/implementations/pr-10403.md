## 解决了什么问题

`qwen serve` 默认只允许在 loopback 上无 token 启动，但过去这条部署边界只放行 non-strict API。严格 mutation 仍返回 `token_required`，`--enable-session-shell` 在无 token 时被忽略，Local Control pairing material 对本地 Web Shell 隐藏，Channel 管理也被渲染为只读。本地用户因此必须额外配置 token 才能使用完整 operator surface。

## 当前实现方案

当前 diff 将 credential authentication 与 deployment authority 拆成两个事实。`isTrustedLoopbackMode()` 仅在主监听实际绑定 loopback、没有 token 且未启用 `--require-auth` 时成立；`requestHasOperatorAuthority()` 接受已验证 listener credential，或 trusted-loopback 模式下来自 primary listener 的请求，但不会把后者标成 Bearer 已认证。

strict mutation gate、显式启用的 session shell、Local Control 配对材料和 Web Shell Channel controls 统一消费这条 authority。`localhost` 在派生权限前先解析为地址，listen 后再用实际 bound address 复核；若预期 trusted-loopback 却落到非 loopback，启动会 fail closed。非 loopback 无 token、`--require-auth` 无 token、wildcard CORS 无 token、LAN Local Control pairing、Channel webhook auth、Host/Origin 与 WebSocket listener credential isolation 均保持原行为。

这条 authority 不绕过下游 workspace trust、session owner、`X-Qwen-Client-Id`、permission confirmation、feature flag、输入校验或资源限制。Web Shell Channel 页在没有 bearer 时读取 daemon status security facts，只在 `loopbackBind && !tokenConfigured && !requireAuth` 时启用管理控件。
