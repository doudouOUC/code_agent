## 解决了什么问题

已有 JDBC binding 可保留 `READY` 状态，但 Broker 重启后没有本 JVM 的 live lease；仅信任旧 endpoint 会把工具派给被替换的进程，直接拒绝又无法恢复仍然存在的资源。

## 最终实现方案

最终合入 diff 为 opt-in durable provisioner 引入预先持久化的 provision seed、加密凭据和 scheduler resource handle；`RuntimeBindingRecord` 增加 `LOST`/`RECOVERY_BLOCKED`、attestation generation 与 reconcile 时间。Broker 恢复时先用 handle 观察原资源，再核对 seed/lease/scope 并调用 `RuntimeTransport.attest`；仍持有 operation generation 时 CAS 更新记录，然后才放入本进程 live binding。`STARTING`/`UNKNOWN` 有界重试，`NOT_FOUND` 标记 `LOST`；只有明确的身份冲突/未授权才阻塞恢复，其他 attestation 错误不被当作身份事实。LOST generation 的遗留 ACQUIRING/READY/RELEASING 会话在无活跃 execution 时可释放，之后无活跃 session/execution 才回收 binding。JDBC 用 AES-GCM 保护 seed，并按绑定上下文校验解密。

## 边界与风险

- 后续主干 `LocalProcessRuntimeProvisioner` 已返回 `local-process` kind 并实现 ensure/reconcile；其 observe 仍依赖本进程 owned map，不能证明跨 Broker 进程接管。生产 scheduler provisioner 与真实跨进程验收仍缺。
- 加密密钥的部署、轮换与灾难恢复需要单独落实；密钥不可用时不能猜测原资源身份。
