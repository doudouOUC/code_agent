> 规模：+67 / -5，5 个文件

## 解决了什么问题

已合入 JDBC helper 通过 UTC `Calendar` 读取 `CURRENT_TIMESTAMP`，但 MySQL 会先按连接 session time zone 返回该值。`+08:00` 连接可让新 lease 相对服务 `Clock` 向未来偏约八小时，`-04:00` 则让它立即过期；Repository peers 彼此仍使用同一错误数据库值，因此普通多实例测试不容易发现 Service 与 Repository 的双时钟分叉。

## 当前实现方案

当前 diff 把 `databaseNow` 改为同一查询返回 `UNIX_TIMESTAMP()` epoch 秒与 `EXTRACT(MICROSECOND FROM CURRENT_TIMESTAMP(6))` 微秒，再以 `Instant.ofEpochSecond` 构造绝对时间，不再让 JDBC timestamp 解码解释 session time zone。结果为空、微秒为空或不在 `[0, 1_000_000)` 时失败关闭。

H2 单测固定 epoch/micro 组合验证构造与异常边界；可选 MySQL integration 在 UTC、`+08:00`、`-04:00` 三种 session offset 下读取数据库时钟，要求彼此接近且与 JVM `Instant.now()` 的偏差在容限内。中英文 JDBC 设计同步冻结该时钟契约，不修改 schema 或公共 API。

## 边界与风险

- 当前实现尚未进入 `main`，已合入 Repository 仍使用受 session time zone 影响的 timestamp 读取路径。
- SQL 依赖 `UNIX_TIMESTAMP` 和 `EXTRACT(MICROSECOND ...)`，只对当前私有 H2-MySQL/MySQL adapter 有覆盖，不承诺其它 SQL dialect。
- 单次 offset integration 不能替代长时间多节点漂移、连接池动态时区或真实故障注入。
