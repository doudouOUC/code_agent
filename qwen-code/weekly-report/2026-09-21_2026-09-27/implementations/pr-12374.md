# PR #12374 当前实现观察：session debug 日志保留清理

> PR: [fix(cli): clean up stale session debug logs](https://github.com/QwenLM/qwen-code/pull/12374)
> 状态：open；以下按 2026-09-22 快照 head `eb641ff8847d` 描述当前 diff，不能作为 `main` 已落地能力。
> 规模：+472 / -7，9 个文件

## 解决了什么问题

启用 `QWEN_DEBUG_LOG_FILE` 后，每个会话在 resolved runtime `debug/` 目录中生成一个 `.txt` 日志。file-history、subagent transcript 与 OpenAI request/response log 已有保留清理，但 session debug log 不在任何 retention pass 中，长期交互使用会持续积累文件和调试内容；直接复用固定 marker 又会让不同 `QWEN_RUNTIME_DIR` 彼此错误节流。

## 当前实现方案

当前 diff 把 debug log sweep 接入仅由 interactive Config 启动的 background housekeeping，并复用 `general.cleanupPeriodDays` 的 cutoff。每个 resolved debug 目录经过 SHA-256 截断生成独立 marker；首次调度把该 marker 与 file-history/OpenAI marker 一起判断，任何目标缺失或过期都会选择一分钟 catch-up。即使当前未开启 file logging，也会清理过去留下的文件。

`cleanupOldDebugLogs` 只枚举 debug 根目录中的普通 `.txt`，文件名主体必须是合法 session ID，或明确允许的 `transcript-replay`、`workspace-mcp-discovery` 两个 ACP pseudo-session；当前 session 显式排除。文件按 mtime 与 cutoff 比较并以既有并发批次删除，单文件失败只计数并继续。`latest` 软链、`daemon/` 子目录、无关文本和其它扩展名不会进入候选，根目录也不会在清空后删除，避免 debug logger 已缓存 ensure-dir 后静默丢失后续输出。

## 关键代码路径

- `packages/cli/src/utils/housekeeping/cleanup.ts:cleanupOldDebugLogs`：候选筛选、mtime 判定、分批删除与根目录保留。
- `packages/cli/src/services/housekeeping/scheduler.ts:runHousekeeping`：interactive 调度、当前 session 排除、pseudo-session allowlist 与独立 marker。
- `packages/cli/src/services/housekeeping/scheduler.ts:getFirstPassDelay`：把 debug marker 纳入首次 catch-up 判定。
- `packages/cli/src/utils/housekeeping/cleanup.test.ts`、`packages/cli/src/services/housekeeping/scheduler.test.ts`：有效/无效文件、软链/目录、并发批次、active session、marker 和 runtime-dir 隔离回归。
- `docs/users/configuration/settings.md` 及 settings schema/i18n：把 session debug log 纳入 `general.cleanupPeriodDays` 用户口径。

## 边界与风险

- 当前只由 interactive housekeeping 启动；headless、ACP 与 `qwen serve` 不会主动扫描，短期只运行这些入口的环境仍可能保留旧日志。
- 删除依据是 mtime；除当前 session 外，仍在追加的 pseudo-session 依赖最近 mtime 自然留在 cutoff 内。
- `latest` 软链可能在旧目标被删除后短暂悬空，直到下一次 file-debug session 重建指向。
