## 解决了什么问题

Runtime Broker 已能识别 binding 与逻辑 Runtime Session，却没有一条稳定 Tool execution 记录连接重试、dispatch owner、取消和最终结果。若 dispatch 响应丢失或 owner lease 过期，调用方可能再次执行同一副作用；若旧 owner 仍能结算，或 cancellation intent 能被 replacement 覆盖，持久状态会与真实物理调用分叉。

## 当前实现方案

当前 diff 定义 `ToolExecutionRecord`，把 `executionCallId` 与唯一 `idempotencyKey` 绑定到 binding generation、Harness/Runtime Session、Turn、tool call、request digest 和不可变 invocation reference；重复幂等键返回第一条记录供调用方比对，重复 execution ID 搭配另一幂等键则拒绝。状态封闭为 PREPARED、DISPATCHING、EXECUTING、CANCEL_REQUESTED、SETTLED 与 UNKNOWN。

同步内存 Repository 把 dispatch 写路径与取消路径分离。`compareAndSet` 除 immutable identity/version 外还要求 caller 持有匹配且未过期的 owner/lease/generation claim，settlement、状态推进与 dispatcher 上报 UNKNOWN 都不能由旧或 foreign owner 完成。过期 PREPARED/DISPATCHING claim 可提高 generation 接管；过期 EXECUTING/CANCEL_REQUESTED 只转为 UNKNOWN 并保留旧 claim 供核验，不授予新 owner，也不重放物理调用，必须按原 execution identity 走 `resolveUnknown`。

`requestCancel` 不要求 dispatch claim：PREPARED 直接以 cancelled 结算，DISPATCHING 保持状态但置 cancellation flag 让 owner 不启动调用，EXECUTING 转入 CANCEL_REQUESTED；实际执行后的终态仍需 claim owner 提交物理结果/停止证据。当前实现只是一进程参考 Repository，不含 JDBC 或真实 Runtime dispatch。

## 边界与风险

- 内存同步只能证明单 JVM 语义；数据库唯一约束、行锁、数据库时钟与跨 JVM takeover 仍需独立 JDBC adapter。
- `UNKNOWN` 只冻结不确定结果，真正恢复必须查询原 physical execution；不能把 resolve API 当作重放授权。
- invocation/result 是私有 Broker payload；当前记录不负责 tenant 鉴权、公开 Event/Item 投影或敏感信息 redaction。
