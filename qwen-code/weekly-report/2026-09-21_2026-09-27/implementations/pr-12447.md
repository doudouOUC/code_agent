## 解决了什么问题

预览 Managed Runtime 的 Express handler 与 raw HTTP admission gate 分别维护 route 清单，曾出现 handler 已注册但真实请求仍被外层 404 的分叉。Java Broker 与 TypeScript Runtime 若继续各自维护宽松 mock，也无法证明双方对 method/path、16 KiB 限制、身份字段和错误分类使用同一 wire contract。

## 最终实现方案

最终实现增加单一 `OWNED_MANAGED_RUNTIME_ROUTES` typed manifest，固定 `POST /internal/managed-runtime/v2/attest`、protocol v2、请求/响应 16 KiB 与 `no-store`。raw gate 和 Express 注册共同消费该 manifest，URL 必须精确匹配，不接受 query、尾斜线或错误 method。handler 先用常量时间比较 bearer token，再解析 JSON；同时校验 no-store、lease id/epoch header、closed request fields、tenant/workspace generation/cwd、capability digest 与 isolation class。

响应冻结当前 Runtime instance/incarnation/lease/epoch 和不可变 Workspace 身份；失败稳定映射为 401 credential、400 malformed/protocol、409 identity conflict、413 too large，并拒绝压缩 body。语言无关 schema 与 538 行共享 fixtures 同时驱动真实 `node:http` TypeScript 测试和 Java Runtime Broker conformance consumer，减少两端漂移。

## 边界与风险

- Java 目前只消费 fixture/schema；真实 Java transport 与 TypeScript handler 仍未进入同一个 required 跨语言 CI lane。
- 不包含 Broker reconcile/CAS ready gate、Kubernetes 身份、TLS/mTLS、进程 E2E 或部署故障注入。
