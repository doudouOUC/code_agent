## 解决了什么问题

Binding、Runtime Session 与 Tool Execution Repository 已分别定义状态和 fencing，但调用方仍需自行解析 Workspace scope、协调 provision/acquire、续租、控制操作、dispatch/cancel 和 release。缺少统一编排层时，不同接入方容易绕过同一租约与 CAS 边界，重复创建 Runtime、重放不确定副作用，或把重启后仅有持久记录的 `READY` 误当成本进程已验证的 Runtime。

## 最终实现方案

最终实现新增无框架依赖的 `RuntimeBrokerService`，组合 `HarnessSessionResolver`、`RuntimeProvisioner`、`RuntimeTransport` 和三类 Repository。`warm`/`acquire` 先解析权威 scope，以进程内 future 合并同一 binding/session 的并发工作；provision claim 由 Repository 的 operation lease 约束，外部 provision 期间定时续租，成功后 CAS 到 `READY` 并记录精确 generation/lease 的进程内 `liveBindings`。因此 Java 重启后即使数据库仍有 `READY`，没有 adoption/reconcile 也会以 `runtime_reconciliation_required` 失败关闭。

Session acquire 通过 Repository 幂等创建、调用 transport 后再 CAS 到 `READY`；control 只允许固定私有操作集合，并与 release 的 active-control 计数互斥。Tool execution 先按 idempotency identity `findOrCreate`，后台认领 dispatch lease、进入 `EXECUTING`、续租并调用 transport；失败或结果不明确转入 `UNKNOWN`，明确结果按 owner/generation 结算。cancel 保留独立取消路径，release 则拒绝仍有 control 或未终结 execution 的 Session，并要求 transport 明确返回成功后才写入 `RELEASED`。

## 边界与风险

- 不包含具体 Runtime provider、Spring/HTTP adapter、Hosted Harness 接线、重启 adoption/reconcile 或生产 schema migration。
- `RuntimeBrokerService` 本身不会让持久 `READY` 在新进程自动可用；必须先完成 attestation 与 CAS 后才能恢复本地 gate。
- 该 PR 合入时 `enterExecuting` 竞争失败路径只检查状态；后续 #12477 已合入 transport 调用前的最终 owner/generation 复核。
