# PR #12477 当前实现观察：阻止旧 dispatch owner 执行副作用

> 规模：+116 / -1，2 个文件

## 解决了什么问题

`RuntimeBrokerService` 从 `DISPATCHING` CAS 到 `EXECUTING` 时若输掉竞争，会重读胜出记录。已合入代码只确认该记录仍是 `EXECUTING`，没有确认 owner 与 dispatch generation 仍属于自己；另一 Broker 接管过期 lease 后，旧 Broker 因此仍可能调用同一 transport，尽管数据库状态已正确归新 owner 所有，造成重复外部副作用。

## 当前实现方案

当前 diff 在 `enterExecuting` 返回后、启动 lease renewal 和调用 `transport.execute` 之前，复用既有 `ownsDispatch(executing, claimed)` 比较 owner 与 generation。任何一个不匹配，旧 dispatcher 都直接完成本地流程，不启动续租、不调用 transport，由当前 owner 继续负责 execution。

新增确定性测试把竞争插在 CAS 与返回之间：Broker A 的 lease 过期后，Broker B 接管 generation 2 并进入 `EXECUTING`；断言 A 的 transport 调用次数保持为零，同时持久记录仍归 B。修复只增加物理副作用前的最后一道 fence，不替代 transport 自身幂等。

## 关键代码路径

- `packages/sdk-java/runtime-broker/src/main/java/com/alibaba/qwen/code/runtimebroker/RuntimeBrokerService.java:dispatch`：对 `EXECUTING` 结果补 owner/generation 最终复核。
