# PR #12477 最终实现：阻止旧 dispatch owner 执行副作用

> PR: [fix(java): Fence stale tool dispatch owners](https://github.com/QwenLM/qwen-code/pull/12477)
> 状态：merged；按合入提交 `99bf4ce86b32` 与最新 `main` 核对。
> 规模：+116 / -1，2 个文件

## 解决了什么问题

`RuntimeBrokerService` 从 `DISPATCHING` CAS 到 `EXECUTING` 时若输掉竞争，会重读胜出记录。已合入代码只确认该记录仍是 `EXECUTING`，没有确认 owner 与 dispatch generation 仍属于自己；另一 Broker 接管过期 lease 后，旧 Broker 因此仍可能调用同一 transport，尽管数据库状态已正确归新 owner 所有，造成重复外部副作用。

## 最终实现方案

最终实现于 `enterExecuting` 返回后、启动 lease renewal 和调用 `transport.execute` 之前，复用既有 `ownsDispatch(executing, claimed)` 比较 owner 与 generation。任何一个不匹配，旧 dispatcher 都直接完成本地流程，不启动续租、不调用 transport，由当前 owner 继续负责 execution。

新增确定性测试把竞争插在 CAS 与返回之间：Broker A 的 lease 过期后，Broker B 接管 generation 2 并进入 `EXECUTING`；断言 A 的 transport 调用次数保持为零，同时持久记录仍归 B。修复只增加物理副作用前的最后一道 fence，不替代 transport 自身幂等。

## 边界与风险

- 修复已进入 `main`，但仍需真实 transport 与多进程端到端验证。
- 该 fence 只阻止已失去 Repository claim 的旧 Broker 发起 transport，不提供 transport 层幂等 token 或部署接线。
- 回归使用进程内可控 Repository/transport；多 JVM 与真实网络副作用仍需后续端到端验证。
