## 解决了什么问题

Managed Runtime Broker 的 binding 与逻辑 Runtime Session 原先只有进程内 Repository。Java 重启会丢失 placement generation、Session 绑定、乐观版本与 operation lease，多 JVM 也没有共享事实源来阻止同一 scope 重复分配 active binding、旧 owner 写回或跨 tenant/workspace 复用。

## 最终实现方案

最终实现新增只依赖 `javax.sql.DataSource` 的 JDBC adapter 和三张私有表。`qwen_runtime_binding_slot` 以 scope hash 固定分配行，`findOrCreate` 在事务内插入/锁定 slot、重读 current binding，并只在没有 active generation 时递增分配；`qwen_runtime_binding` 保存完整 scope、generation、状态、endpoint、operation lease 与 version；`qwen_runtime_session` 保存 binding generation 下的逻辑 Session 与终态。

更新路径使用 `SELECT ... FOR UPDATE`、完整 identity、expected version 与 generation 共同 fencing；operation lease 读取数据库时钟，避免 JVM 时钟偏差决定 owner。Session 唯一键竞争通过 reread winner 收敛，终态 Session 不能重新激活；SQL 异常回滚并上抛，不回退进程内实现。schema initializer 使用幂等 `CREATE TABLE IF NOT EXISTS`，但生产迁移策略仍由后续接线负责。

## 边界与风险

- 不包含 Tool Execution ledger、Spring/DataSource/Flyway 生产接线、Runtime 进程创建或 reconcile/attest。
- durable row 只证明 Broker 状态存在，不证明 endpoint 指向的物理 Runtime 仍存活或可安全接管。
- initializer 适合当前私有模块边界；生产 schema versioning、迁移顺序、加密 endpoint token 与多实例部署仍需嵌入服务负责。
