## 解决了什么问题

Java 控制面未来通过私有 Session 路由调用常驻 Hosted Harness 时，bearer authentication 只能识别 caller，不能证明双方使用同一私有协议、同一部署 capability 集或同一 Harness 进程 generation。若 Harness 重启而调用方沿用旧内存 owner，旧请求可能被另一个进程接受并错误恢复。

## 最终实现方案

最终实现增加独立 `HostedHarnessContract` foundation。contract 固定 protocol v1，启动时生成且只在进程内保存 RFC UUID v1-v5 boot ID（默认 v4），并要求 deployment 传入 canonical `sha256:` 加 64 位小写十六进制 capability digest。创建后 envelope 与嵌套版本数组冻结，boot ID 统一小写。

Express middleware 在响应中始终回传当前 boot ID，并按固定顺序校验请求：缺失/不支持 protocol header 返回 426、`Upgrade: qwen-hosted-harness/1` 与 `hosted_harness_protocol_required`；缺失或 malformed boot ID 返回 400；合法但不是当前 generation 返回 409；匹配才调用 downstream route。UUID 比较不区分大小写，boot ID 只是 generation fence，不替代未来 bearer authentication，capability digest 也不是 credential。

## 边界与风险

- 本 PR 没有创建 `qwen serve` Hosted profile、环境配置或 `/capabilities` 广告，也没有把 middleware 挂到任何生产 route。
- 未来接线必须在 bearer authentication 之后、仅对 private Session routes 挂载同一个 process contract；普通 `qwen serve` 路径保持不变。
- capability digest 只校验表示形式；deployment 如何 canonicalize 配置、排除 secret 并与 Java admission 对齐仍由后续实现负责。
