## 解决了什么问题

替代 Harness 已能接入原 journal，但模型推理中断和审批决定后的 Turn 仍可能缺少可续跑的精确请求、工具批次和内存 waiter。仅恢复可读 Session 不能完成原 Turn；直接重新提问或重建调用会重复副作用，终态先于物理释放失败也会遗留不可追踪的 owner。

## 当前实现方案

新增 64 KiB 上限、versioned 的 `hosted-model-request`、`hosted-approval-continuation` 和 `hosted-turn-cleanup` 资源。模型快照固定原 Session/header、activation、boot/eventEpoch、round、sequence、请求/历史/config/route/provider digest 和已完成调用；禁止持久化 secret/瞬态 transport 字段，并核验原 attempt、digest 和 checkpoint。

证据完整且没有后继已提交 assistant/tool intent 时，可在新 attempt 下重发保存的主模型请求，沿用原 prompt 和剩余回合/deadline；不把它当新输入。已有完整最终 assistant 消息和 checkpoint 证明时只补终态，不再推理。旧部分流式输出按 journal 身份有界撤回。无完整快照、未知副作用或冲突证据保持阻塞。

审批 options v3 引用保存的原 assistant 批次、工具定义/参数、原 Action ID/ordinal、Runtime binding/generation 和 Workspace generation。恢复原 requested waiter、deadline 和已提交决定后，只继续原批次；核验定义/args，复用原 prepare/intent 身份，再衔接已有 Runtime 结果恢复。原生审批 producer 限 read_file/write_file/edit/glob，不能扩展成 Shell/Hook/MCP 重放。

原生 Turn 在已知原 Runtime binding/generation 后、acquire 之前持久记录 cleanup owed，覆盖 acquire 丢响应时的 owner 清理义务。先提交 durable terminal 并闭合 file history，才释放原 binding/generation 并写 confirmed。释放失败保留 debt 和输入屏障，load/resident attachment/lifecycle 可重试原清理；不能重复终态或凭失败响应认定资源不存在。Java 递归校验新增资源引用闭包与事件 schema，并把含新记录的 reader floor 提升为 2，通过私有 header ceiling 拒绝旧 reader。

最新 head 通过 `hostedRuntimeSessionId` 将包含冒号等不适合 Broker 路径的 automation/monitor prompt ID 稳定映射为 SHA-256 wake ID；原 prompt/file-history turn ID 不变，approval plan、execution input 和 cleanup descriptor 一致使用映射后的 Runtime Session ID，映射本身幂等。审批恢复只查询原 assistant 提交之后的 batch/requested Action，旧 v2 options 不得冒充可恢复的 v3；cleanup 返回 owed/confirmed 状态供恢复分支对账，不能把已释放 owner 当成新 acquire 的依据。

## 边界与风险

- 主模型冷重发限定无 Hooks/MCP；未完成的 prefix continuation 不保存冷重发快照。Shell、Hook、MCP、child 仍沿各自 owner 处理，不因本 PR 得到泛化恢复。
- 模型请求重发可能重复 provider 推理，不保证 exactly-once。未知工具副作用不能换 ID/Runtime 重放；两侧 owner 同时重启、跨宿主接管、混版本集群及旧控制面 fencing 另需验收。
