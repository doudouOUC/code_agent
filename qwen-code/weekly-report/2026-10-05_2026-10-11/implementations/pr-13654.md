## 解决了什么问题

大 publication 的 seal/terminal 验证占据 HTTP 请求和线程，固定请求预算可能让完整输出无法及时结算。

## 最终实现方案

最终实现先持久提交 PENDING verification operation，再由有界 verifier executor claim/验证；Runtime 轮询原 operation status，claim epoch/deadline fence 防止旧验证者提交。

默认 async-verification-enabled=false；已合入迁移为 V68，需先升级全部 server，开启 journal-head-authorization 后才能启用异步准入。FAILED operation 也视为终态，避免失败的 prefix 验证永久阻塞 collector；所有 object 仍必须 VERIFIED，其它引用/退休保护也仍生效。CANDIDATE/QUARANTINED 对象不能仅据 operation FAILED 释放 bytes 或 quota。

最新 head 以 CLAIM 权限完成已接受的验证，在原 CSI execution 已结算/退休时不误用 PRODUCE 权限永久拒绝。原 activation/grant 仅时间窗暂时失效可 defer 等待原身份续期，writer 失效、身份/epoch 冲突仍拒绝。verifier 的错误处理若再次失败，退避 poison candidate，避免饿死后续项。永久失败的 FINISHING operation 在事务内撤销该 operation 的 terminal candidate 与 charge、恢复 producer OPEN，事务后尝试删除对应对象；这与直接放行所有非 VERIFIED 对象的 collector 不同。

最终合入 head 将原 authority 冲突和非 READY 的 Session recovery_status 都转换为永久 `managed_tool_publication_fenced`，不把 recovery block 当短暂 busy。claim 前或读中 blockRecovery 使原 operation FAILED，停止该 operation 的继续验证，不停止 verifier 队列。健康普通 resource candidate 保留 CANDIDATE/bytes，不因授权失败隔离为损坏；FINISHING 按原 operation 撤销 terminal candidate/charge。未分类 storage read 的普通 IllegalArgumentException 保留 PENDING、candidate/charge 和原 bytes 供重试；只有 `CorruptObjectException`/`ContractViolationException` 证实对象/契约损坏才相应处理，明确非瞬态 API 拒绝与 OSS AccessDenied 仍永久失败。
