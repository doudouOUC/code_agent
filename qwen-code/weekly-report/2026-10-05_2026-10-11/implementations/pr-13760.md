## 解决了什么问题

Java 已有 Session cwd operation，但 WebShell 缺少可信能力声明、目录切换入口和丢响应后的原命令对账。若客户端超时后换键重提，或切换未确认就发送输入，模型可能使用用户未确认的新目录或旧 contextRevision。

## 当前实现方案

Java 为 creator-owned、ACTIVE、Workspace 绑定且 files 开启的 Session 批量核对 execution registry、冻结的 Workspace generation/storage 与 OPERATOR/OWNER grant，派生 `cwdChange` capability。Provider 仅在可信 productScope 下暴露提交与查询方法，并校验返回的原 Session、operation 类型和 operation ID。

对话框打开时冻结 expectedContextRevision；确认前显示版本过期状态。Hook 先向按 provider/session 分隔的 sessionStorage 写入 workspaceId、目标 cwd、原 revision 和稳定幂等键，再提交 operation。pending/installing 继续轮询；completed 还必须有更高 revision，并刷新到至少该 revision 的 Session/Workspace 摘要，才清除意图和解除输入屏障。

超时、网络不确定或未确认结果保留原意图，刷新后仍可查询原 operation，或在未取得 operation ID 时用同一键重提同一命令。初次提交的确定性 4xx（408/429 除外）才可清除意图；不能凭未知响应创建新的切换。Session 切换终止当前轮询，不删除持久待确认意图。

## 边界与风险

- 只能在原 Workspace 的授权范围内切换 cwd，不是跨 Workspace 迁移。Shell、Hook、后台持有者和 W1c 的兼容边界不由 UI capability 自动解除。
- #13761 是已关闭未合入的 capability-only 方案；本 PR diff 含相应能力接线，不推断关闭原因或把任一方案写成主干能力。
- 当前 diff 的 creator-owned 筛选基于较早权限代码；提交前主干 `5b1c701400c9` 的 `ManagedAgentStore.beginCwdChangeOperation` 已允许 Workspace OPERATOR，actor-scoped 原键重试先于可变角色拒绝，结算再核验持久 initiator。合入前须对齐 capability 与这条新后端权限边界，不能以旧 creator-only 条件描述最新主干。
