## 解决了什么问题

publication mutation 先锁 retention，再由 Session writer 获取 placement，而 admission 顺序相反，会产生并发死锁。外层事务还可能把 preflight 的后续锁保留到 admission，不能仅修正最内层事务。

## 最终实现方案

mutation 先读取实际 publication 行，校验 tenant/Workspace/Session、publication ID 与规范 binding digest；新 reservation 才使用已校验的候选 binding。原 Runtime 同时核对发现记录的 scope/generation；若 JDBC repository 共用数据库，还核对持久 tenant、Workspace、generation 和 provisioner，之后才取得 placement。

锁顺序统一为 placement 在 retention、quota 和 Session writer 之前。`lockStagedPlacement` 只在已有外层事务时让 preflight 先参加该顺序，独立 preflight 保留原事务边界。prepareAdmission、commitReceipt 以及 finished/quarantine 复用已确认的原 Runtime；publication 行加锁后再核对完整 binding/digest，并把加锁查询限制到原 scope，发现变化则拒绝。

这份已合入拆分只处理普通与已有 K1 publication 的锁顺序，不引入 #13526 的私有 CSI Session guard、producer/native execution 或 generic retention 资格，不改变路由/schema。主干 `18f80f56666a` 已包含上述路径。
