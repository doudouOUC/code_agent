## 解决了什么问题

#7947 让 Serve `/file?line=&limit=` 可以读取大文本窗口，但翻页仍需要客户端重新指定行号，服务端也要从文件开头扫描到目标行。对持续增长的日志和超大文件来说，这会让“下一页”成本随行号增长，并且协议没有稳定表达 `hasMore` / `nextCursor`。

## 最终实现方案

最终实现为 workspace text read 增加 opaque byte cursor。`GET /file` 在有界 line/limit/maxBytes 读取时可以返回 `hasMore` 与 `nextCursor`；后续请求带 `cursor` 后，服务端直接从 cursor 指向的下一行 byte offset 继续读，而不是从 byte 0 重新扫描。`cursor` 与 `line` 互斥，畸形 cursor 返回 `parse_error`。

cursor 绑定 path、snapshot 与 descriptor 信息。append-only 日志可以继续翻页；文件替换、截断、descriptor/snapshot 不一致或 path 变更会返回 `hash_mismatch`，避免在不同文件版本之间拼页。输出仍受 256 KiB response cap 保护，line-offset scan 仍受 8 MiB 上限约束；binary、unsupported streamed encoding、unsafe UTF-8 split 都 fail closed 或返回安全前缀。

协议面保持 additive：`workspace_file_read_cursor` capability 标记可用性；TS daemon client、daemon MCP workspace read、Serve HTTP docs 与 ACP bridge adapter 都增加 request `cursor` 与 response `hasMore`/`nextCursor` 字段。旧客户端不传 cursor 时仍走原 line-window 行为。
