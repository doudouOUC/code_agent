## 解决了什么问题

#7947 为 Serve 大文本有界读取引入了 caller-owned file descriptor 路径，但 Core 的文本范围读取仍把 path-read、handle-read、强制 streaming 与扫描上限揉在同一个 helper 里。这样的接口既容易让借来的 fd 被误关闭，也会让后续 byte-cursor paging 继续复制一套“从同一 descriptor 读窗口”的逻辑。

## 当前实现方案

当前 diff 把 Core 文本范围读取拆成两个明确入口：`readTextRange()` 继续负责 path-based 读取并保留小文件 fast path；`readTextRangeFromHandle()` 只处理 caller-owned handle，要求调用方传入 byte range，用 explicit-position reads 读取，不关闭传入 handle。encoding detection 也统一支持 path 或 handle；handle 探测阶段出现 I/O probe error 时先按 UTF-8 fallback，真正读取阶段仍会暴露底层错误。

`readFileWithLineAndLimit()` 删除 `fileHandle`、`forceStreaming`、`maxScanBytes` 这类混合模式参数，Serve/ACP 需要复用 descriptor 时改走专用 handle request。旧的 `readFileHandleBuffer`、runtime `RangeError` trap 和 inherited dead fields 被清理；`readFileHandleChunks` 收敛为以 handle + byte offset 为中心的 chunk iterator，为 #8002 的 byte cursor 继续复用同一 fd 打基础。

行为边界也更清晰：unsupported encoding 在 large-stream 路径统一抛 `LargeNonUtf8TextError(detected)`；`CoreReadTextFileHandleRequest` 不再继承 `path`/`stats` 这些在 handle 场景无权威意义的字段；Serve 文件读取仍由外层负责 path/inode/snapshot 验证。

## 关键代码路径

- `packages/core/src/utils/read-text-range.ts`: path 入口、borrowed handle 入口、encoding detection 与 chunk iterator 分层。
- `packages/core/src/utils/fileUtils.ts`: `readFileWithLineAndLimit()` 简化为 path-oriented 调用面。
- `packages/core/src/services/fileSystemService.ts`: Core filesystem service 对 handle request 的独立类型接入。
- `packages/cli/src/serve/fs/workspace-file-system.ts`: Serve large-window read 改用 handle-bound Core 入口。
- `packages/cli/src/serve/routes/workspace-file-read.test.ts` 与 `bridge-file-system-adapter.test.ts`: 验证 path replacement、large-window 与 ACP adapter 行为。
