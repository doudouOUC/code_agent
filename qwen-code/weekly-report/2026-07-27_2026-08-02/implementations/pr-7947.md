## 解决了什么问题

PR #6404 已经让 Core `read_file` 支持大文本按行范围有界读取，但 Serve workspace filesystem 仍在读取前用 256 KiB 大小门拒绝文件。结果是 HTTP/ACP/Web 侧即使请求 `line=1&limit=20`，也会在切片前收到 `file_too_large`，无法查看大型日志、构建输出或长文本的局部内容。

## 最终实现方案

最终实现允许 Serve 对超过 256 KiB 的 UTF-8 文本做 bounded line-window read。large-window path 从文件验证、binary probe 到 streaming read 都使用 caller-owned file descriptor，并在读取后重新检查 path 与 inode，避免检查后被 symlink swap 或文件替换。输出仍受 256 KiB cap 约束，因此能力是“读大文件的小窗口”，不是放开完整大文件读取。

full snapshot、edit、hash 与 optimistic locking 继续保留原 256 KiB 门。大文件 partial response 会报告完整 file size 与 `truncated: true`，不会返回 full-file hash；只有 streaming reader 到达 EOF 时，才返回 original line count。binary content、unsupported large non-UTF-8 text、symlink swap、以及读取期间内容变化仍 fail-closed。

ACP bridge 与 Serve HTTP 路由一起更新，确保同一 workspace filesystem contract 暴露给 `/file` 与 bridge filesystem adapter；Core 的 `readTextRange` / `FileSystemService` 边界仍作为底层能力复用。
