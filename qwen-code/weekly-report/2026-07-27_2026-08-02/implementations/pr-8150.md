## 解决了什么问题

旧 LLM span 上的私有 `ttft_ms` 表示“首个用户可见输出”耗时，单位是毫秒；OpenTelemetry GenAI v1.41 的 `gen_ai.response.time_to_first_chunk` 表示“首个 normalized response chunk”耗时，单位是秒。两者边界不同：metadata-only / usage-only chunk 对标准 first-chunk 有意义，但不算用户可见输出。继续把 `ttft_ms` 当作标准 first-token 字段会让 ARMS/OTel 查询混淆语义和单位。

## 最终实现方案

最终实现，在流式 `LoggingContentGenerator.generateContentStream()` 中记录 wrapped provider invocation 前的 monotonic `performance.now()`，拿到 async generator 后把该 `requestIssuedAtMs` 传入 `loggingStreamWrapper()`。流式 LLM span 开始时写 `gen_ai.request.stream=true`；消费到第一个 normalized `GenerateContentResponse` 时写 `gen_ai.response.time_to_first_chunk = max(0, performance.now() - requestIssuedAtMs) / 1000`。

first-chunk 只尝试写一次。即使 `setAttribute` 抛错，也不会重试或影响 stream 消费；如果 stream 没有产出 chunk，则省略该字段。stream 之后失败、abort 或 idle timeout 时，只要已经观察到 first chunk，标准字段会保留。非流式请求继续写兼容字段 `llm_request.stream=false`，但不写 `gen_ai.request.stream=false`，也不写 first-chunk 字段。

私有 span-level `ttft_ms` 被移除，避免把 first-visible-output 误认为标准 first-chunk。但内部 `ttftMs` 仍保留在 `LLMRequestMetadata` 和 API response event 路径中，继续驱动 `ApiResponseEvent.ttft_ms`、`sampling_ms`、`output_tokens_per_second`、API request breakdown metric 和 `/stats` 相关展示。文档同步说明查询迁移：标准 first-chunk 读 span 的 `gen_ai.response.time_to_first_chunk` 并乘 1000；旧 first-visible-output 语义读 API response log。

## 关键代码路径

- `packages/core/src/core/loggingContentGenerator/loggingContentGenerator.ts`: stream request issuance monotonic timer、standard stream attributes、first chunk write-once guard。

## 验证方式

PR 最终记录覆盖 `loggingContentGenerator.test.ts`、`session-tracing.test.ts`、telemetry docs/design 更新与 typecheck。测试重点包括：streaming span 写标准字段、non-streaming 不写标准 stream flag、first normalized chunk 与 first visible output 分离、空 stream 省略 first chunk、setAttribute failure 不重试、不打断消费，以及错误/abort 后已观测 first chunk 的字段保留。
