## 解决了什么问题

Core scheduler、ACP bridge、UI telemetry、chat recording、QwenLogger、OTel logs 与 metrics 都会消费 tool-call terminal event。旧实现里 `status`、兼容字段 `success`、`error` 和 `error_type` 可以互相矛盾：成功事件可能携带 stale error，取消事件可能被当作失败，soft error 没有分类时会落入空 bucket，空工具名也会造成日志和指标维度不稳定。结果是同一次 tool call 在 UI、日志、metrics 和 recording 里可能被解释成不同结果。

## 最终实现方案

最终实现新增统一 terminal normalization boundary。tool-call event 在进入 UI telemetry、chat recording、QwenLogger、OTLP logs 和 metrics 前先归一化；authoritative `status` 派生兼容 `success`，而不是让各 consumer 自己推断。`success` 与 `cancelled` 事件会清掉 stale `error` / `error_type`，失败事件保留稳定错误分类；没有分类的 core soft error 归为 `unknown`，空 tool name 归为 `unknown_tool`。

metrics 侧的 tool-call counter 增加低基数 `status` 维度，避免只靠 success boolean 统计。QwenLogger 增加 `status` 与 `tool_type`，但保持低敏：不记录 tool arguments、tool results、stack trace 或 MCP server name。Desktop agent 与 core scheduler 共用同一归一化入口，确保 agent mode、interactive UI 和 telemetry export 对 terminal state 的解释一致。

## 关键代码路径

- `packages/core/src/core/coreToolScheduler.ts`: terminal event 构造后进入归一化边界，并保持 UI / recording / telemetry fan-out 一致。
- `packages/core/src/telemetry/loggers.ts`: QwenLogger tool-call event 增补归一化状态与 tool type。
- `packages/core/src/telemetry/metrics.ts`: tool-call counter 增加低基数 terminal status 维度。
- `packages/core/src/telemetry/qwen-logger/`: logger schema 与测试覆盖 terminal status。
- `packages/core/src/core/coreToolScheduler.test.ts`: success、error、cancel、unknown soft error、空 tool name 等归一化边界。
- `packages/core/src/agent/`: desktop agent tool-call terminal telemetry 复用同一口径。
- `docs/design/tool-call-terminal-telemetry-contract.md`: terminal status、兼容 `success`、错误字段与低敏采集契约。

## 验证方式

PR 最终记录覆盖 core scheduler tests、telemetry logger/metrics tests、desktop agent tests、developer telemetry docs 和 settings docs。测试重点包括：success/cancel 清理 stale error、soft error fallback 到 `unknown`、empty tool name fallback 到 `unknown_tool`、QwenLogger 不泄露 args/results/stack/MCP server name、metrics status 维度稳定，以及 UI telemetry、recording、logs、metrics 看到同一 terminal status。
