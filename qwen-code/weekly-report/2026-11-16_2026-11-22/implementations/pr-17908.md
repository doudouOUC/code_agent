# PR #17908 最终实现：正常挂起 seal 戳与默认关闭的到期唤醒

> PR: [feat(managed-agent): stamp clean suspensions for wake dispatch](https://github.com/QwenLM/qwen-code/pull/17908)

> 规模：+905 / -115，34 个文件

## 解决了什么问题

带未来未尝试wake输入的Session仍不能挂起；控制面重放整个journal才能判到期与ready，而拒载后的普通seal可能被误用为正常挂起证明。

## 最终实现方案

按 #17869 实现单列wake_seal_revision，而非父设计wake_due_at/独立dispatcher。Store controller在wake-dispatch.enabled=true（默认false，环境QWEN_MANAGED_AGENT_WAKE_DISPATCH_ENABLED）时对acquire/renew grant广告wakeDispatch；Core严格按true暴露supportsWakeDispatch，旧客户端/未广告部署保持原行为。

Harness共用pickWakeInputs与泵的全已提交前缀选择。能力开启时，pending门只放行未来、未尝试、wake来源且非stopped-message输入；已到期/非wake/已尝试或relay仍欠结算的消息保留原职责。teardown在activation释放后、seal前重新计算pending/dueAt，只有正常挂起调用authority.close(wake)。HTTP client用当前grant journalRevision填revision；Java在原writer token/generation/head锁下要求精确匹配，否则409 managed_session_wake_stamp_stale。戳和SEALED/is_wake_pending/wake_head_revision同写，有pending才写wake_retry_at=dueAt。普通seal无戳；递增generation的acquire清戳并将未来retry压到NOW+30秒，不能让后来新输入被旧远期时间隐藏。

现有WakeRecovery到期选中并claim后，对同revision stamped候选跳过journal proof，仍核父run并被动recoverForWake；无戳崩溃head走旧证明，不改其缓存行为。ready在SEALED/activation released且投影当前、无其他义务下接受wakeProven或同revision seal戳。transport对戳有效且无pending/未来retry给NOT_DUE；已到期仍沿既有activateForWake，并未全面改被动。

没有新表、独立WakeDispatchJob或四态proof。关闭开关停止新放宽挂起，但原stamped head仍按到期消费；后台Shell/Monitor及审批仍不在3a范围。默认兜底2秒扫描/8候选、暂态claim30秒重试是现有参数，不是本次证明的真实到期延迟或成本界。

当前 main 后续 #17954 抽出 wakeDispatchOwnsInput 并复用 stamp/recovery 断言到 MySQL；#17955 已把 transport load 改为 recoverForWake。上文到期仍 active 是原 PR 的历史范围，不再代表当前 transport 行为。#17953 的3b staging/后台 seal 已默认关闭地合入，并有 #18110 后续修正；Phase 4 的 #18115 仍 open，不能作为 main 能力承诺。
