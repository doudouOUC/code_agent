## 解决了什么问题

tenant guard同时存hash与原identity并每次锁做碰撞核对；投产前去哈希计划需要先在共享锁域验证可读scope、大小写/尾空格语义和两个真实消费者，不能一并改全库identity。

## 当前实现方案

当前 open diff，不能作为 main 能力承诺。唯一V1的ma_tenant_guard将tenant_key CHAR64+tenant_id VARBINARY改成tenant_id VARCHAR96 utf8mb4_0900_bin，以(tenant_id,guard_domain)为主键，保自增id唯一键与域check。ToolPublicationRetentionStore.lockTenant及JdbcRuntimeBindingRepository.lockPlacementDomain改用原tenant/sentinel setString绑定，仍先幂等插入再FOR UPDATE，保query timeout和读回identity校验。

只覆盖output_publication/runtime_placement两个guard域，不移动调用方锁序，不重写Session/Broker其他scope hash或API身份。同步 schema 投影和 fixture/MySQL guard 断言；设计/计划包含后续 cluster 路线，但未实现。最新 head 补齐既有 schema conventions/锁清单双语引用；当前 scope 上限为 96 字符，超长暂由严格模式 INSERT 拒绝，完整 admission 校验留待后续。collation 由 ManagedSchemaMySqlIT 的 MySQL-shape 门核验，不能称跨引擎 catalog 已核对它。主干当前仍hash guard；候选必须按MySQL8.4的0900_bin/NO PAD与VARCHAR字符长度、Unicode和尾空格行为实测，不把H2或原VARBINARY字节语义当同义。V1仍原地改、无升级迁移。
