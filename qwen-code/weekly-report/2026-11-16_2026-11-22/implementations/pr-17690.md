## 解决了什么问题

idle Hosted Session 持续占 writer/activation 续租、内存和 Runtime owner；直接 detach 会终结输入，缓存缺失也不能证明恢复已就绪。需要保 durable obligations 的非终态暂停与可审计的冷开恢复。

## 最终实现方案

最终合入新增 hosted-session-suspension 状态机与 Session 旁 registry，gate 独立于 resident：open→closing→blocked。实现 idle 10 分钟、最多 10% jitter、单实例冷开并发 8、在途工作等待 30 秒；仅更短的 QWEN_E2E_IDLE_SUSPEND_MS/测试参数可覆盖，未新增部署开关或 capability。准入 mutation、Turn settle、load 成功重置时钟，GET/heartbeat 不重置；所有 open 模式在 acquire/reuse 前查 gate，mutation 计到 handler 自身结束而不是 socket close，异步尾部另查 live work。

pending input（含未来 notBefore）、active/recovered Turn、cleanup debt、client-files、活跃 monitor/child、配置/压缩/消息等阻止暂停。首个 teardown 调用前可回退；之后按完成步骤保原对象精确重试：停 wake，非终态关闭 Hook/MCP，核 Runtime lease/release/cleanup，关 publisher，再停 writer 与 activation renewal、release activation、memoized seal，最后 stopLocal 并移除 resident；placement 保留。最多 5 次，指数退避加 jitter；失败达到上限移除 resident 但 gate 留 blocked，不复活半关闭对象。

实现还包含自动清 gate：停止 timer renewal 后等待该 Session leaseDuration + 30 秒默认 Store request timeout + 10 秒 margin，由后续 acquire 的新 generation 围住旧 seal。这个推导依赖请求超时及没有更晚续租/旧副作用的假设，不是本次证实的安全时间界；提高 IO 超时须复核该界。状态码分别 closing/open_busy/teardown_blocked；新加统计是累积计数/耗时，不是已测性能。

Java wake 入口仅在调用方已于 SQL wake fence 观察无 live writer 时按引用清缓存再 load；create 的409仅 already-attached/already-exists 两码可转 passive load，不能把 open_busy 再当已存在。恢复 view 用 durable SEALED、released activation、activation/wake revision 均等于 journal revision、无 pending wake 且无 Turn/Runtime/cleanup 义务证明 ready，不按缓存缺失或 sealed 单项推断。上述 Phase 1 已在 main。

当前 main 后续 #17749 已把 MCP close 扩为可选 parking、增加 durable pending 资格并改看 client-files.active；该演进不反计到本 PR 的27文件。pending notBefore、活后台 Shell/Monitor 和审批仍阻止暂停；#17805 仅合入 Phase 3 设计。
