## 解决了什么问题

后台 Shell/Monitor 的增量摘要和观测策略仍在 Harness，正常挂起会停止捕获；只换 publisher 不能延续同一 SHA-256 状态，丢答时也无法确认哪些资源已持久。

## 最终实现方案

最终合入方案把后台捕获与 Monitor 策略交给 worker，前台路径保留。delivery entries 以每 run 的 deliverySeq 串联 output/observation/terminal，每条携带新增资源、原身份和摘要；worker 在附着时 push，断开或失败后保留 outbox，由现有租约通道 observation-pull 拉取，不新增 worker 主动访问 Broker 的持久凭据。当前实现用 128KiB 段、每页最多256个段描述、逐段 revision、512KiB 请求和每 run 8MiB outbox，不能套用原设计的 256KiB 常量或称所有容量已验收。

RuntimeObservationCoordinator 对 binding/generation 领取 SQL 单拉取者租约，续租后异步拉取；JdbcRuntimeStageStore 在事务内核 claim、锁 Session/head、保存资源和 RUNTIME_STAGE 引用、stage 行及 wake hint，terminal 同事务结算原 execution。只有提交后才向 worker 确认 stagedThrough；stage 删除需当前 writer/generation 的已应用水位。最终新增 ma_runtime_stage，V1 为48张业务表，并增加 observation claim 与 wake_seal_background；这些接线已进入 main，开发 catalog 仍重建而非升级。

重开先注册新 publisher，再在 delivery gate 内排空 Broker staged entries 并按已提交记录水位去重、提交后 ack，最后放行实时 push。挂起资格需 runtimeObservation grant（配置 qwen.managed-agent.runtime-observation.enabled 默认 false）和当前 generation 的逐 run 后台证据；只有 shell/monitor 的 running_attached、start receipt、观测 binding 与所有 cleanup hold 均可证实，才豁免后台义务。证书每轮重算，detach 携最终水位，释放只探测并保留 mount；backgroundHeld 只在原 supportsWakeDispatch() seal 分支内写入，runtimeObservation 单项不是完整可用证明。wake/ready 同步识别 staged work，删除/退役清引用。

stage 的默认水位为4MiB、hard cap 16MiB、每 run 最多10000次 observation；达到容量需排空，terminal 路径与强停、满队列及重启时序仍须真实验证。发现 SQL 首批 LIMIT256、stage list 与异步拉取链不等于已证明全量公平性或恒定容量成本。增加进程、MySQL、跨副本 puller 和 capture 等价测试及测量脚本，但脚本存在不代表本次运行，更不代表完整 Phase 3b 已验收。

最终版已整合 #18019 的主干业务键形状，并修正后台证书同时要求 runtimeObservation 与 wakeDispatch、只扫描 :process 后缀以免前台行挤满256候选、stage JSON 保留必需 null、published tool-result 资源准入、重新附着失败清 listener 与 generation 水位围栏。worker 对失败 push 以1秒至30秒退避重试，资源入 outbox 后释放重复缓存；Monitor 资源独立、已确认终态和未启动 run 都清理 registry。不能再用早期一段一页或 managed-delivery/1 标签代表最终 wire。

后续 #18110 又修本地资源 ID 路径校验与 Broker 重启取消，并修真实进程测试 drain 见证；不反计入本 PR 75文件。计划中的 Linux 启动/挂起/链路声明不是本次独立验收，容量、公平性与故障仍需真实证据。
