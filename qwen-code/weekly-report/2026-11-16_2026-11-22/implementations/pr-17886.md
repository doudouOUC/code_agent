## 解决了什么问题

另一个控制面副本没有加载过该 Session 时，Harness status 可能为空；即使原 Harness 已持久结算且没有未结义务，恢复视图仍停在无证据。清理recheck抛无类型异常又无法向调用方区分暂态不可达和确定拒绝。

## 最终实现方案

JdbcSessionRecoveryRepository 新 hasNativeTerminal 只认同tenant/session/turn、SESSION流、is_terminal=1且source_key非空的公开事件；控制面自行写的SQL失败/取消不算native结算。SessionRecoveryService 在没有active Turn、head ACTIVE、没有本地cached recovery attachment、status确实为空、有该native终态且无durable Turn/Runtime/cleanup义务时，从任一副本返回ready。

本地有cached attachment却读失败/外prompt的状态不伪装成无附件；有active Turn、只有控制面终态或还有义务都保持保守。这个新ACTIVE分支与原SEALED/activation证明并存，不把缓存为空单项当健康。cleanup recheck保原ManagedAgentException；typed HostedHarnessRecoveryDeclinedException映409及原reason/cause，其余RuntimeException记日志并映503 recovery_runtime_unavailable。OpenAPI和生成类型同步该错误词汇。
