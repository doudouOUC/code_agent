## 解决了什么问题

后台进程在worker，但增量摘要、分段资源发布和Monitor策略都在Harness；它退出后捕获fail-stop，换publisher还会identity冲突，父设计的重新打开直连/三方交接无法直接续写同一捕获。

## 最终实现方案

最终4文件全Markdown：新增双语独立3b设计并更新父设计互链，仍为实现前提案。将后台LocalShellStreamCapture、Monitor防抖/idle/maxEvents与稳定观测序号移到worker；前台lane不变。每run有deliverySeq递增outbox，output/observation/terminal条目各自携带完整新资源；有Harness时幂等push并确认appliedThrough，无Harness时Broker在现有租约通道observation-pull，单binding claim拉取者，事务写ma_runtime_stage及RUNTIME_STAGE引用后才ack stagedThrough。

这取代父设计的worker→Broker持久授权与三方冻结：worker不主动调Broker，无需新worker凭据/撤销库。重开先按writer generation换publisher并取得stagedThrough，再排空到该水位，之后接push；重复按record原水位去重，提交manifest前遍历分页闭包，原始payload只在journal取代引用后删，generation变动不等于可丢弃暂存。暂存会触发旧兜底staged分支，seal/recordPending与暂存hint在同head锁下互围栏，避免解除挂接→seal窗口丢wake。

terminal暂存同事务结算execution，随后仅排空wake提交journal终态、cleanup和Runtime Session释放，不提交模型输入；后台run仍受所有既有回收守卫。后台挂起需默认关闭runtime-observation门、worker能力和当前代次逐run证据共同满足，扩seal backgroundHeld证明；两条释放改只探测、保mount，MCP回收在断连接前先拒活后台。outbox按run/worker字节背压且terminal留保留槽，强制取消不能被满队列卡死。删除/退役须清stage引用；回滚先停新挂起，旧run继续拉取，最后才能回滚worker。

256KiB段、512KiB请求、16GiB流容量和各水位是方案常量/测量起点，不是当前行为。本次main没有ma_runtime_stage、RUNTIME_STAGE或runtimeObservation grant接线，3a已合入不代表3b可用；没有第二journal writer。
