## 解决了什么问题

Phase 1 每次 idle suspension 都关闭 MCP，下一次冷开重建 stdio/HTTP 连接；简单不关连接又会让无人回收的 owner 长期占据 Workspace 成员资格，阻塞维护，或把失效连接误当可复用。

## 最终实现方案

最终实现让 HostedMcpSession.suspend 先 reconcile effects，再选择仍启用 server 的最新配置；仅 settled、active 且有 connectionGeneration 的配置可保留。它重新 acquire 原 owner（非 reuse 形式），只有 Broker 广告 mcpParkable 才 park，否则仍非终态 close；过时配置先退役。journal head 的 SEALED 标记挂起，不另加 parking 表或 journal kind。挂起资格同时检查 durable pending operations/未结算配置，client-files 改看 active 而非对象存在。

重开先 acquire 原 owner，再 status/lookup；待重新校验配置在 mcp-discover 携带 revalidate:true。HTTP ping 超时5秒，明确不支持 ping 的 -32601 可接受，其他失败将连接标 retiring；stdio 依靠原进程退出检测。失效后先完成替代配置，再退役旧配置，替代被拒绝不把原记录提前释放；worker/generation 丢失不能铸造新 owner 来假装恢复。worker 原16连接上限不扩大，只能回收其他 runtimeSession、无 pending 且至少闲置300秒的最久未用连接，无合格受害者或关闭失败仍拒绝 quota。

部署必须同时启用 runtime-broker.enabled 与 mcp-parking.enabled；后者默认 false。只有回收 job 装配时才 enableMcpParking，且 mcpParkable 排除外部 Workspace，避免单 holder 长期排斥其他执行。默认 idle-duration30分钟、scan-delay1分钟、batch-size100；时长至少1ms，批量1至1000。独立单线程 scheduler 标 defaultCandidate=false。JdbcParkedMcpOwners 用 READY、持有 execution_storage_key、mcp-/extensions-components- owner 与 SEALED head 选候选，按 id 游标扫描。维护因成员忙而失败会 expedite 对应 storage，下一 tick 可跳过 idle 时长，但仍要 sealed。

回收核 binding/generation/READY Session，必要时扫描恢复原执行上下文；替换 mount claim，前后复核 parked，再经认证的 worker reclaim 路由先关连接、结算背景行、最后交还 mount。并发后继 acquire 换掉 claim 会使交还拒绝；失败恢复原 claim（若仍属于本次），不静默释放后继资源。worker 入口保持内部身份认证、4KiB 请求上限与 protocolVersion/runtimeSessionId 闭集。JdbcSessionRecoveryRepository 的义务探针改走 session_scope_key，并不把 SEALED 或缓存缺失单独当 ready。

## 边界与风险

- park 仍占存储成员资格且连接是 Runtime 进程资源，不是持久 TCP 或跨主机恢复保证；维护加速不是同步立即回收。后台 Shell/Monitor、pending wake 与审批的 Phase 3/4 挂起能力不由本 PR 提供。
