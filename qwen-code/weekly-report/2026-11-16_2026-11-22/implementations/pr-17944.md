# PR #17944 最终实现：content-only 扩展按包降级 MCP 与 Hooks

> PR: [feat(managed-agent): degrade process components per package in content-only extension runtimes](https://github.com/QwenLM/qwen-code/pull/17944)
> 状态：merged；已合入 main，merge `18846c6e4bfa`，最终 head `0df2bfa9d93b`；对照 main `d4b28087f457`。
> 规模：+1468 / -20，14 个文件

## 解决了什么问题

没有stage进程能力的content-only runtime遇到带MCP/Hook的合法包会整包拒绝，使同包Skills/commands/instructions/assets也无法使用；静默忽略又让管理视图误报全部组件已生效。

## 最终实现方案

最终合入方案：ManagedExtensionRuntime在没有dependencies.stage时，仅为profile admission构造mcpServers/hooks为空的内容视图，保留完整 contributions与pin/manifest比较和摘要验证；去掉全局process unsupported拒绝，不启动任何MCP/Hook。staged runtime仍验证完整贡献并运行原stage，失败不降级为content-only。

preparedView按每包真实贡献生成可选degradedComponents:[mcp,hooks]，HostedExtensionSession把它写入effective bundle，Core闭集parser只接受这两个值、最多2且去重并固定顺序。只降级process组件，Skills/commands/上下文/资产仍在原授权、profile和编译边界内。executionMode仍为全局环境信息，不能用它推断每包组件是否可运行。

Java管理snapshot从最近已active bundle读取per-extensionId映射，不按新pending操作或包名称猜测；TS/Java均拒坏数组/重复/未知值，OpenAPI及生成类型同步。缺字段旧bundle等同无降级，不改资源schema版本；新字段仍需同版本读写方协调。64KiB inline资源预算保留：可达content-only形状的effective MCP为空，fully-optioned极端组合若超限由原publish capacity guard fail-closed，不放大上限。

最终 head 另补 MCP-only、无进程组件及 installed/recovered 等降级快照回归；仍无 stage 时才做内容准入，staged 失败不自动降级。
