## 解决了什么问题

checkpoint 随工具历史增长后会撞上通用 64 KiB 资源上限，TS、Java 和 CSI readback 的预算不一致；Harness 已阻塞恢复时，Java 仍可能消耗重试次数，界面也不能说明为何暂时不可继续。

## 最终实现方案

按 kind 将 managed-checkpoint 上限统一到 maxEventBytes，即 1 MiB；普通资源默认仍为 64 KiB，managed-input 8 MiB、Skills 2 MiB、model-request 32 MiB 保持独立。TS 发布与引用校验、Java inline/ref、工具 publication 和 CSI native readback 同步，错误包含 kind 与字节长度。后续 #15170 又将物理 checkpoint 的已结算历史分页，不能把本次单根预算扩大当作无限历史支持。

HarnessCoordinator 优先 flush 已取得的权威事件；没有新事件时才每 15 秒查询原 cached attachment 的状态。仅在同 boot/eventEpoch、无活动 prompt 且 cursor 后没有 transcript 的 recoveryBlocked 观察上，保存 HARNESS_RECOVERY_BLOCKED。原 ACCEPTED/RUNNING 与未结算事实保留，15 秒后再观察，不消耗模型/执行重试预算，也不 takeover、submit 或生成 continuation。查询失败继续停放，不把活性观察当执行证明。

UI 显示 recovery_blocked，禁止新输入但保留取消；cleanup/lifecycle 不得因原 Runtime 仍被阻塞引用而提前退休。当前 main 还包含 #15131 的显式恢复状态和原 prompt cleanup，只读自动观察与操作员恢复核验是两条不同路径。
