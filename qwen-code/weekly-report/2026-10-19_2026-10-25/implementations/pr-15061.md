# PR #15061 最终实现：同一侧栏中的 daemon 与 Managed Workspace

> 规模：+3135 / -184，23 个文件

## 解决了什么问题

全局 Local/Managed tab 隐藏另一条链路，打开项目和新建任务时容易丢当前 Workspace 或落到默认目标；共享 UI 若不隔离 pending，还可能将未知请求转到另一后端。

## 最终实现方案

最终 diff 只调整 WebShell；移除全局模式 tab，在原 sidebar 同时呈现 daemon Workspace 与 ManagedWorkspaceNavigation，只有当前链路高亮。Managed 按 provider.storageKey/Workspace 分组，分页每次 50、按 ID 去重，补 default Workspace 和已选 summary，搜索匹配分组或会话；展开状态按 provider/Workspace 持久化。

App 明确保留 managedWorkspaceId 和后端来源，选会话回传其 Workspace，新建仍用该目标。全局新任务在当前详情 Workspace 尚未读回时拒绝，不借用默认目标。选择 daemon 目标核对 id/cwd/hostOrigin 与 trusted，远端仍走原 daemon 路由，Java Session ID 不进入 ACP。

打开项目复用 AddWorkspaceDialog/WorkspaceExecutionSelect，可选 daemon 或 Managed；只有 provider 广告 createWorkspace 才显示后者。Managed 仍使用 #14970/#14405 原浏览/导入/受控创建 API，不使路径自动跨主机映射，也不扩大服务端权限。

WorkspaceBindingCreator 接显式 workspaceId 后通过 get 再验相同 ID/canCreateSession；无权/404 显示该目标错误，不静默回退默认 Workspace。加载/切换/dirty cwd 确认期间阻止提交。未知 Session/Workspace 创建继续保留原 payload/key，pending/busy/编码时禁切后端；放弃不代表未执行。

在已有 Session 打开项目用 creationOnly 保留原会话，不偷偷提交新 Session。成功创建回传原 Workspace 并刷新目录；对话框关闭后的迟到成功不强制导航，切 provider/请求取消仍隔离结果。当前 main 后续生命周期/恢复/子视图已修改相关 UI，但仍沿原显式 Workspace 与后端权限，不把导航统一当作 #14928 启动器已合入。

本 PR 是 closed #15040 拆出的 UI 切片，不包含 managed-local launcher、发行下载、signed 导入或普通 daemon 挂载 Managed 前门；本地常驻服务仍依原部署配置。

2026-10-24 当前 main 的 #15331 在原双链路导航上复用 Managed 行/tooltip 并汇入统一 Archived 折叠区；归档查询、已加载计数、错误/重试仍按原 provider 隔离，不增加后端 authority 合并。
