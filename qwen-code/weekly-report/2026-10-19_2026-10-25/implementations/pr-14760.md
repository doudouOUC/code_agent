> 规模：+1174 / -298，8 个文件

## 解决了什么问题

activation/inbox 每次状态转换都追加日志，长会话即使有效状态没有相应增长，磁盘和重开解析成本仍不断累积。

## 最终实现方案

在下一次持久写入前，当 snapshot 之后的增量达到 max(64 KiB, snapshot 大小) 时，把完整有效状态编码为 v2 snapshot，保留 nextSequence、原排序、activation epoch/lease、消息 payload/fence/取消/终态和幂等身份，再继续原 v1 追加。重开仅允许第一条为快照，校验版本、SHA-256、顺序、状态与引用；旧 v1 完整日志仍可读。

替换通过独占 0600 pending 文件、文件 sync、原子 rename 与非 Windows 目录 sync。任一步失败（包括 rename 之后）令当前 writer 停止，重新打开才能恢复；不把不完整快照截断为空。所有终态身份和消息仍保留，减少的是转换日志冗余，不是任意长度 Session 的总内存/有效状态硬上限。
