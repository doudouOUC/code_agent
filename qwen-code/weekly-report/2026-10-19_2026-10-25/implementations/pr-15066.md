## 解决了什么问题

V15 后普通执行权已在 Runtime Session 成员上，故障测试仍读单 storage holder 会得出错误结论；按整个 JVM 的 descendants 等待退出又会误伤并发测试的其它 worker。

## 最终实现方案

最终 diff 只改测试与 probe。HostedProcessCrashIT、HostedSseGapProbe、HostedWorkspaceToolTurnIT 通过原 tenant/storage/Harness/binding/generation/runtimeSession 对账 execution_storage_key/execution_exclusive，而非要求 ma_storage_owner.holder_key 等于 prompt。

完成或可信 handback 后自身 membership 为 null；唯一未结算 PREPARED prepare-twice 保留原物理 key 与身份，READY/RELEASED 按故障分支分别核验，不把空 holder 当作无活执行。

普通 Broker close 测试从 LocalRuntimeProcessProvisioner 的 owned/starting 原进程及其 descendants 收集待退出集合，不枚举整个 JVM；另外创建不相关 Node fixture，断言 Broker 关闭后仍活并由自身 finally 清理。native verified recovery fixture 扩到 Linux/macOS。

主干已有 #15026 生产 membership，本次故障断言/fixture 隔离也已合入；不改变生产清理权、SQL schema 或对 UNKNOWN 的处理。
