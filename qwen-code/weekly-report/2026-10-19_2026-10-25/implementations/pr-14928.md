## 解决了什么问题

现有 Managed 部署要分别准备 Java、Harness、数据库和前端，个人本机试用缺少版本匹配、持久状态、受保护入口和统一退出的启动流程。

## 当前实现方案

当前 diff 新增显式 qwen serve --managed，普通 serve 不变。仅 native macOS/Linux、Node >=22，拒绝 Bun；先校验 Java 21，再按已安装 CLI 的精确版本/target 解析服务端。支持显式 runtime 目录和带 JRE 的包，缓存于 QwenHome/managed-runtime；每次解析校验 manifest 与 JAR SHA-256，不因缓存损坏静默切安装源。

首次下载依次尝试 OSS 与官方 GitHub Release，checksum 限 1 KiB、严格文件名，JAR 限 256 MiB 且核对 ZIP signature；锁、临时文件和原子 rename 保护缓存。每次下载尝试有五分钟预算。HTTPS 同源 checksum 不等于独立签名或发行可信链。

managed-local 状态根必须位于所有 Git worktree 外，canonical 路径且拒绝末端 symlink，目录 0700、状态文件 0600/不超过 16 KiB，单 launcher 锁固定 installationId、私密端口和凭据。数据非空但状态丢失时拒绝启动，恢复必须一起保全状态与 H2 数据。

managed-local profile 使用 loopback、signed auth、H2 file、durable local-process 与 verified recovery，trusted reboot recovery 为 false；无 H2 console，也不开放 SSH/已有挂载/resident CSI。先启动 Hosted Harness/Java，验证精确能力及 readiness，创建应用管理的默认 Workspace，再启前门。退出先关前门、逆序停止子服务，不能把 Java 单进程退出等同全部持久 worker 已清理。

专用前门使用 bearer/Host/Origin/loopback 门禁，只代理白名单 WebShell 路由及 Artifact GET/HEAD；原 body 最多 10 MiB，拒绝重复幂等头，剥离调用方 authority 后以固定 tenant/actor 对 method/path/query/body digest/key 签名。boot 不泄露私钥，不是通用内部代理。

发行 workflow 手动 dry-run 默认开启，绑定已发布 CLI 的不可变 tag，构建版本匹配包；已有资产字节不符拒绝，仅补缺失 GitHub/OSS 资产并读回。该 workflow 本次未执行，不能宣称下载渠道已有可用发行。主干快照尚无本 PR 新增启动器；已合入 #14970 的 OPEN 本地导入与此 signed profile 不可自动拼接，closed #15040 的集成也未进入 main。
