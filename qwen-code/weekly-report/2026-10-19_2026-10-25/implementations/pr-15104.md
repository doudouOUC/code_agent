## 解决了什么问题

Managed 用户不能主动压缩上下文；直接调用模型并替换本地 history 会在失响应或 Hook 崩溃后重复生成摘要，也可能跨过尚未结算输入与工具的恢复边界。

## 最终实现方案

Public/WebShell 以当前 actor、可读 Session 与 Workspace OPERATOR 准入，要求 ACTIVE bound Workspace、files/capability、原 storage/cwd/generation 和 expectedCompactionRevision；活动 Turn/Action/Hook/维护、恢复阻塞、非 READY head 或 pending rename 均拒绝。相同原 actor/key 与请求摘要回放同操作，不能换 payload。

V16 只扩 ma_operation 的 CONTEXT_COMPRESSION kind。冻结 operationId、模型选择、provider/policy pin、historyCutSequence 和已准入历史/原 prompt 与 completed tool IDs。仅结算的 Turn/system 进入压缩输入，取消或失败中未回答的 user input 不混入。Hosted 以 safeMode 和禁止工具的配置调用已有 ChatCompressionService 的 force/manual 路径，不读取新的 Workspace 设置、MCP、Skills 或文件 checkpoint；配置/pin 变化拒绝。

history_maintenance 持久走 admitted→generating→candidate→settled。摘要 candidate 必须先耐久，再执行 PostCompact 和最终应用；恢复复用原 candidate，不再请求模型。PreCompact/PostCompact 仍经原持久 Hook dispatcher；未知 Hook/缺 candidate 维持 recovery_blocked，不伪造成功。最终同事务提交维护终态、context.compacted、summary ref 与被替换 message IDs，revision 来自权威提交；公开 transcript 和原 journal 不删除。

Java 在外部调用前标 HARNESS_SUBMITTED；丢响应从原 journal/query 对账，不盲重发。只有尚在 JAVA_DURABLE 的准备阶段可安全重试，明确拒绝且无持久证据才失败。历史回填仍校验连续原字节/摘要，缺失或已裁剪历史 fail closed；noop 保持 revision 语义。

2026-10-24 当前 main 的 #15263 已把上述 V16 CHECK 折叠到唯一 V1、删除原 migration 文件；开发目录重建，原压缩账本和恢复流程保留，不提供旧目录升级链。

## 边界与风险

- 压缩不是历史删除或总存储回收；不会允许忙会话跨越原执行。旧 writer/reader 的 operation/维护记录支持须匹配，当前 V1 重建不提供混版本写入或旧目录迁移保证。
