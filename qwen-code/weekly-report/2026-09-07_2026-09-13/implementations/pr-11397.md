# PR #11397 当前实现观察：按 Mem0 SDK 放宽 DELETE 响应解释

> 状态：open；以下描述2026-09-09复核到head `d0a7fc1716f6`的当前diff，不能视为`main`已落地能力。
> 规模：+64 / -76，4 个文件

## 解决了什么问题

#11337合入时把英文示例回执当作closed协议常量，只接受 `Memory deleted successfully`或带`!`的message，并约束可选status/event/cascade/error字段。真实Holo返回HTTP 200和 `Memory <id> deleted successfully.`，目标随后确实为404，但client因为message不匹配仍报告`unknown`。

## 当前实现方案

当前open diff将DELETE响应处理与Mem0 SDK的HTTP层口径对齐：接受任意`response.ok`状态，继续做1MiB有界、严格UTF-8 JSON解析，但不再解释message/status/event/cascade/error等provider字段。JSON内容可以是object、array、null或任意合法值；成功HTTP状态本身仍不证明删除完成。

只有随后一次exact GET按既有absence contract确认目标不存在，结果才是`deleted`。目标仍存在、final GET不确定、非2xx、transport失败、空body/204、坏JSON或超预算body都返回`unknown`，且DELETE最多一次、不自动retry。删除前的ID、scope、全文、repository binding、审批与deadline语义保持不变。

## 关键代码路径

- `integrations/external-context-mem0/src/delete-request-engine.ts`：从固定回执判定改为`response.ok`+bounded JSON parse+exact final GET。
- `integrations/external-context-mem0/src/delete-request-engine.test.ts`：真实Holo message、任意JSON/2xx、空/204、非成功状态与目标仍存在。

## 边界与风险

- current diff会忽略2xx JSON中的provider-specific error/status字段，安全结论完全依赖后置exact GET absence。
- 204虽是成功HTTP状态但没有JSON，仍为unknown。
- 不改变非原子GET/DELETE竞态、full-text审批、fixed scope或unknown后的人工核对责任。
