## 解决了什么问题

#10924 已强制每个 Conversations session 使用单 writer lease，但 process-global runtime owner 仍使任一 daemon 占用整个 Conversations root，第二个 daemon 即使只服务无关 standalone session 也会被拒绝。直接删除全局 owner 又会留下三类风险：旧 daemon 混跑、多个 Live publisher 同时激活，以及删除 journal 或 WebShell 恢复绕过 session fence。

## 最终实现方案

`ConversationRuntimeManager` 不再长期获取全局 owner，只在首次发布 runtime 前执行一次 legacy owner 检查：活跃旧 owner 继续阻止 cutover，已死且身份稳定的旧记录在锁内回收；新版 daemon 之后可同时挂载同一 root。真正写入仍由 mandatory session lease 逐 session 排他，缺失 attestation 的 runtime 进入 terminal quarantine。

删除 journal 从旧 owner 目录迁到 stable base 下独立的 `conversations/deletions` 私有状态目录，并持续校验 base/state/journal 的 realpath 与 inode identity，journal 初始化不再依赖全局 owner。Live 的 HTTP/Host start 共用 coordinator 的 `beforeStart`，只有 stable discovery 中 protocol、PID、instance nonce 都精确匹配的 publisher 才能激活；stop/disable/dispose 取消待准入动作。

WebShell 把 writer conflict/lost/unavailable/transcript-changed 识别为 session-local 阻塞：direct link 和 Recents 保留当前导航与列表，停止无意义的自动 restore，给同一 session 提供显式 retry，并用 generation 隔离迟到错误。writer lease 日志同步说明 lock 只证明 fence，不证明原 writer 仍存活，残留锁恢复前必须先隔离所有可能 writer。

## 边界与风险

- 新旧 daemon/ACP writer 不支持滚动混跑，升级与回滚都必须先 drain 并隔离全部 writer。
- Linux boot/PID namespace、原生 Live 音频、完整升级回滚和所有崩溃窗口未被本次独立验证。
- per-session lock 的 residual recovery 仍是人工受控流程；不增加 force unlock、TTL 抢占、跨 daemon forwarding 或 exactly-once scheduling。
