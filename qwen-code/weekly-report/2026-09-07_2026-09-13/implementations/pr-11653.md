> 规模：+94 / -96，4 个文件

## 解决了什么问题

Node/libuv在没有配置内存限额的cgroup v1/v2环境中可能把“无限制”报告成接近2^63或2^64的巨大值。旧`getAcpMemoryArgs()`只判断该值大于0，随后按一半可用内存、16 GiB封顶计算，因此7,265 MiB普通Linux主机上的每个ACP child会被显式抬到16 GiB老生代，而daemon状态模型按宿主内存只报告3,632 MiB，授权与观测严重分叉。

## 最终实现方案

最终删除spawn路径对`process.constrainedMemory()`和`os.totalmem()`的重复推导，改为复用`daemon-memory-budget.ts`中的`detectAvailableMemoryMb()`。该函数只有在constraint为正且严格小于host total时才采用cgroup值；无限哨兵、等于或高于宿主的值都回退host total。`getAcpMemoryArgs()`再按既有策略取50%、封顶16,384 MiB。

其余策略保持不变：结果仍进程内缓存，只计算一次；只有目标高于当前启动进程V8 heap limit时才下发`--max-old-space-size`，并始终保留`--expose-gc`。因此这不是按child数量切分、RSS enforcement、spawn admission或动态重算，只修正输入内存总量的来源。`legacyChildCeilingMb()`注释同步收敛为“raise-only guard仍可能让child高于模型值”，没有把未解决问题包装成已完成。

测试把原来按module cache拆分的两个文件合并为一个动态重载套件，覆盖cgroup v1/v2哨兵、constraint高于/等于host、无constraint、6/4/2 GiB真实限制、target等于当前heap limit和64 GiB封顶，并锁定首次计算后的cache。spawn parity用相同常量校验模型值与实际argv；测试stub避免反复加载Core barrel累积process exit listener。

## 边界与风险

- 受影响主机上的显式child老生代授权会下降，这是修复目标，可能改变GC/OOM时点。
- 目标不高于当前V8 heap limit时仍不下发参数；#8182记录的低内存raise-only缺口尚未解决。
- 老生代上限不是进程RSS、总child内存或daemon准入保证，也不替代真实负载容量验证。
