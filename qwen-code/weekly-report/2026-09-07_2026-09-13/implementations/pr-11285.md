# PR #11285 最终实现：deleted bind mount 上的 housekeeping 快速失败

> PR: [fix(cli): stop housekeeping hanging on a deleted bind mount](https://github.com/QwenLM/qwen-code/pull/11285)
> 状态：merged；head `51c94b68edaa` 已于 2026-09-07 合入 `main`，以下按最终 diff 与最新 `main` 复核。
> 规模：+78 / -3，2 个文件

## 解决了什么问题

当 qwen目录位于源路径已删除的 bind mount中，mountpoint仍可 `stat`为目录，但创建其子项返回 `ENOENT`。Node recursive `mkdir`会把该错误解释为父级缺失，在创建父级得到 `EEXIST`后不断重试叶子；promise不settle使housekeeping链永久悬挂，部分Linux进程还形成高频失败系统调用并放大孤儿sandbox的CPU占用。

## 最终实现方案

`runThrottledOnce`在获取跨进程lock前仍确保lock目录存在，但将 `mkdir(dirname(lockPath), {recursive:true})`改为单层0700创建。当前三个调用点都把lock直接放在global qwen dir，其父级 `$HOME` 已存在：首次运行仍能创建目录；deleted mount或其它不可创建状态则立即reject并由既有catch吞掉，后续lock获取按原语义失败/跳过，不再卡死。marker freshness、stale lock接管与task执行逻辑不变。

## 关键代码路径

- `packages/cli/src/utils/housekeeping/throttledOnce.ts`：单层私有目录创建与故障原因注释。
- `packages/cli/src/utils/housekeeping/throttledOnce.test.ts`：验证目录仍会创建、权限不向group/other开放，并禁止恢复 `recursive:true`。

## 验证方式

PR声明 `throttledOnce.test.ts` 13项与housekeeping相关80项测试通过；Linux私有mount namespace复现中，recursive形式6秒后仍pending且约103% CPU，单层形式立即 `ENOENT`且0% CPU。可复跑上述Vitest；mount复现需要Linux root/unshare环境。本次独立核对最终两文件diff、merge状态和最新 `main`，未执行root级mount复现。

## feature 文档处理

该改动是通用CLI housekeeping底层故障修复，没有新增用户入口或稳定协议，因此未建立独立feature专题；仅在本周周报与实现文档保留根因、实现和验证口径。

## 边界与风险

- 未来若新调用方把lock放在多层未创建路径，必须先自行创建父目录，否则该轮housekeeping会跳过。
- 容器泄漏源头和runner池负载不在本PR范围；本改动只消除孤儿进程中的CLI侧放大器。
- recursive mkdir为何在部分环境热循环、部分环境安静悬挂仍未完全解释，但两类路径都由单层创建规避。
