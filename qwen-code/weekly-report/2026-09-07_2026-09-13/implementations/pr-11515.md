# PR #11515 最终实现：默认支持 256 个注册工作区

> PR: [feat(serve): support 256 workspaces by default](https://github.com/QwenLM/qwen-code/pull/11515)
> 状态：merged；2026-09-10 11:57 UTC合入，以下按head `56864062d63b`及最新`main`描述最终实现。
> 规模：+1,857 / -175，33 个文件

## 解决了什么问题

`qwen serve`此前最多注册25个用户工作区，即使多数runtime没有活跃session，也会在第26个工作区返回`409 workspace_limit_reached`。直接把共享常量改成256又会放大总session、Channel owner事务和持久化文件边界，且旧store reader只能接受24条secondary记录与256 KiB，扩容后可能无法重启读取。

## 最终实现方案

最终把注册容量默认值提升为256，并新增operator-only `QWEN_SERVE_MAX_WORKSPACES`及embedded `ServeOptions.maxRegisteredWorkspaces`，只接受1到256的整数。显式option优先于启动环境，项目`.env`和项目settings不能调整process-wide容量。启动workspace、完整持久化恢复、dynamic registration、scratch runtime、promotion与store锁内add都消费同一个boot-time解析值；超限恢复在发布listener前失败且不修改store。

注册容量大于25且没有显式`maxTotalSessions`时，标准`runQwenServe`固定使用800个total session上限，即使只启动一个workspace或单workspace上限为0/Infinity也不放大；显式`--max-total-sessions`继续优先。低级`createServeApp`不会凭注册值伪造其无法强制的800上限。capabilities/status新增optional `maxRegisteredWorkspaces`与`maxChannelControlWorkspaces`，让客户端看到实际process policy。

持久化schema仍为version 1，但结构上限提升为255条secondary记录与8 MiB，并在atomic write前按UTF-8字节检查。Channel控制仍独立限制25个owner，准入会计算current、pending、candidate及为recovery保留owner的并集，并以`channel_control_workspace_limit_reached`拒绝超限，既有2,130,000ms SDK事务预算与observe-only ACP child模型不变。

## 边界与风险

- 256是注册policy，不是4核8 GiB部署可安全同时运行256个active runtime或800个模型session的实测保证；runtime仍会eager构建。
- dormant runtime、LRU/eviction、ACP child内存enforcement、Channel timeout协商和UI配置均未实现。
- 降低配置前需先用新版本删减显式/持久化注册；降级旧版本前还需把secondary记录降到24条以内且store不超过256 KiB。
