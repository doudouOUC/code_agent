## 解决了什么问题

configurable Mem0 package在#11246/#11311后已有检索、Auto Recall与显式写入，但没有安全的单条删除路径。删除既是破坏性、非幂等外部副作用，又需要防止模型凭搜索摘要或错误ID删到其它scope/内容；网络不确定后自动重试还可能重复提交。

## 最终实现方案

最终实现新增仅由管理员显式安装的schemaVersion 5 delete profile，默认Extension、search与writer profile都不启用。MCP暴露两个工具：`context_get({memoryId})`精确读取完整目标，`context_forget({memoryId, expectedContent})`执行显式删除。ID限制为1到256个ASCII安全字符且拒绝`.`/`..`；expected content最多4000 Unicode code points，拒绝unpaired surrogate并做逐字精确匹配。

配置绑定canonical repository root、绝对Delete Dialect路径、endpoint、credential和固定非空scope。GET必须返回exact ID、全文以及所有配置scope字段；absence只接受选定的404或200 JSON null契约。删除前再次GET并核验ID/scope/全文，只允许一次DELETE；合并时最终代码只认可HTTP 200及固定成功message（可带`!`），可选status/event/cascade/error字段也必须满足closed规则。认可回执后仍需第三次GET确认absence，才返回`deleted`。

结果明确区分`not_deleted`（零次DELETE）、`deleted`（回执与后置absence都成立）和`unknown`（DELETE已开始但回执或确认不确定）；不自动retry。MCP annotations标记destructive、non-idempotent、open-world。搜索结果中过长ID改为整体省略而非截断，避免后续把截断值误当删除目标。

## 边界与风险

- GET与DELETE不是provider端原子事务；final GET后发生的并发更新仍可能已被本次DELETE移除，部署前需确认ID不复用与scope不可变。
- `unknown`不能自动重试；应先用精确读取检查当前状态。
- 当前`main`仍使用严格英文回执。真实Holo回执放宽由open #11397提出，尚未落地。
