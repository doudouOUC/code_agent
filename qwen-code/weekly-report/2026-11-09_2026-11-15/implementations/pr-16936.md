## 解决了什么问题

JdbcRuntimeBindingRepository 混合持久 repository 操作与被多模块静态调用的 storage/Harness fence 规则，调用点依赖具体实现类，锁与事务归属难以分辨。

## 最终实现方案

最终实现增加 RuntimeAdmissionFences，把 storage alias/physical owner、Harness drain/lifecycle 与 admission 检查移到无状态静态引擎；保留传入 Connection，不能自己开启事务。JdbcRuntimeBindingRepository 继续作为 repository wrapper，控制面、journal、Workspace migration/recovery 与 CSI 相关调用改指向同一引擎。

原 FOR UPDATE、生命周期 authority 下 Session claim 的 MySQL FOR SHARE/H2 FOR UPDATE、generation/lease 校验与 key 编码沿原逻辑保留，测试引用和锁 owner 清单同步。该重构不改变 schema、public HTTP 或持久 repository 接口，也不意味着所有锁契约已经执行通过。

## 关键代码路径

- `packages/managed-agent-server/persistence/src/main/java/com/alibaba/qwen/code/runtimebroker/persistence/RuntimeAdmissionFences.java`：无状态 admission/fence 规则。
- `packages/managed-agent-server/persistence/src/main/java/com/alibaba/qwen/code/runtimebroker/persistence/JdbcRuntimeBindingRepository.java`：继续拥有 repository 包装及事务入口。
- `packages/managed-agent-server/persistence/src/main/java/com/alibaba/qwen/code/managedagent/persistence/JournalFencing.java`：已改用同一 fence 入口。
