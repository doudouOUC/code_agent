## 解决了什么问题

大资源与长期 journal 正文持续占用 SQL，现有 Tool Publication 对象适配器不能直接充当全 Session 的存储和归档协议。外置正文必须保留精确归属、reader/恢复围栏和 UNKNOWN 对账，否则丢答可能导致覆盖、重复 PUT 或错误回收。

## 当前实现方案

候选 `ImmutableObjectStore` 定义稳定非秘密 namespace identity、无覆盖/不隐藏重试的 putIfAbsent、带 guard/字节预算的 open 和精确删除。`ImmutableObjectStores` 通过 ServiceLoader 加载 factory，拒绝无效/重复 kind 和缺失 provider，验证配置与 identity；Spring、独立 operator 工具共用加载器。Aliyun 实现及 ToolPublicationObjectStoreAdapter 复用原发布协议，另提供本地插件示例和契约检查器，不承诺内建任意云后端。

Session 资源以 SQL `ma_resource` 的 store_id/object_key、长度/digest 和原 operation 记录持有归属：短事务 allocate，外部 PUT 在事务外逐次核 guard；同一 attempt 只物理创建一次，读回校验后才标 PUBLISHED。IN_FLIGHT/UNKNOWN 只核原 locator 对账，不因网络错误重新写对象。读取采用受保护视图与有界正文，retirement、读 lease、引用和 recovery/migration 约束 GC，默认 24 小时删除宽限；原 Tool Publication 与 Session 对象受理仍分开。

`JournalColdStorage` 以 SQL manifest/operation 工作项打包精确原始 journal 字节，校验链、pack digest、revision、writer generation 与 archive epoch。候选仅选择 CLOSED/ARCHIVED、PUBLIC、SEALED/READY、activation released、冷却至少 7 天且 journal 至少 32 MiB、无活读/执行/恢复的 Session；CSI guard 与 recovery-protected 排除。归档与正文驱逐分开开关，PACKED 校验后才可 HOT→EVICTING→COLD；读/写/恢复入口先 pinHot/ensureHot，HYDRATING 按原 manifest 分批还原并验证完整链后才 HOT。失败保持拒绝/待补热，不把缺失 record_bytes 当空历史，也不恢复未知外部执行。

候选修改唯一 V1 的 residency、epoch、store_id 和可空 journal 正文，reader/HTTP 支持上限 5→6；不是新 DDL 升级脚本。provider 默认未配置，resourceWritesEnabled、gcEnabled、journalColdStorageEnabled、journalEvictionEnabled 默认 false；关闭新写不意味着现存对象数据可丢失 provider。最新 main 已由 #16868 落地复用 ToolPublicationObjectStore 的 OSS 资源/pack，但仍 reader 5、没有此候选的通用 SPI/冷补热状态机；main 为 44 表，当前候选仍旧基底 42 表，字段/约束不同，不能仅比较 reader 或表数判断兼容。
