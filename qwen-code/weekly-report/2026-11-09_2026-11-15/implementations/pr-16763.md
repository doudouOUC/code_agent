## 解决了什么问题

单 Harness 与池化连接器各自写 capability token 和依赖判断，审批派生能力容易漏掉基础 approval-selection 检查，后续增加能力也会形成两套定义。

## 最终实现方案

增加包内 `HarnessFeature` enum，集中 token 及所依赖的 feature，`in(advertised)` 同时验证自身和依赖。两连接器改用同一枚举；单连接器获取能力异常仍返回 false，池连接器仍基于已协商 contract。`sessionStore.isEnabled()`、public child 的非池/lifecycle 限制和原精确 attachment 查找保留，枚举不自动打开任何执行权限。最新 main 随后加入 SIDE_QUERIES token，属于 #16758 的后续增量，不计作本 PR 新增业务能力。

## 关键代码路径

- `packages/managed-agent-server/adapters/src/main/java/com/alibaba/qwen/code/managedagent/harness/HarnessFeature.java`：token 与审批依赖的唯一声明。
- `packages/managed-agent-server/adapters/src/main/java/com/alibaba/qwen/code/managedagent/harness/HarnessPoolConnector.java`：池 contract 能力判定。
- `packages/managed-agent-server/adapters/src/main/java/com/alibaba/qwen/code/managedagent/harness/QwenHostedHarnessConnector.java`：单实例能力读取、原开关和异常拒绝。

## 验证方式

本次仅核对三文件 diff 和最新 main。Java 从 `packages/managed-agent-server` 执行 `mvn -Dtest=HarnessPoolConnectorTest,QwenHostedHarnessConnectorTest test checkstyle:check`，需 JDK 21 和匹配 SDK；检查缺少基础审批 token 时派生能力为 false、读取失败拒绝、关闭 SessionStore 不暴露相关能力。未运行这些测试、CI 或真实 Harness 协商。
