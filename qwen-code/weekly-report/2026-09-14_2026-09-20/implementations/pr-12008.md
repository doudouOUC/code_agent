## 解决了什么问题

#11911 会在 child 数量满额时拒绝新 spawn，#11940 只能自动回收零 live session、零 activity 的 warm child。当剩余名额被 loaded session 占用时，冷 workspace 或已停止页面的 Resume 仍只能失败；系统不能自动中断他人会话，但用户也缺少查看受影响 session、明确选择并停止 runtime 的恢复路径。

## 最终实现方案

最终增加只读 stop-options 和 selected-runtime stop control plane。候选返回 workspace/runtime identity、影响 session 与阻塞原因；执行请求必须携带精确候选 identity/confirmation，服务端在关闭前重读 runtime/session/activity，拒绝 stale confirmation、独立 ACP client、scheduled work 或其它不可安全停止状态。停止结果区分完成、部分完成和未知，不把 persistence/close/process-release 未确认误报为成功，也不自动重试 stop。

成功停止只终止所选 managed child，保留 workspace 注册、文件和已保存 conversation，并等待 `ProcessRegistry` 确认名额释放。容量发起方只获得一次 guarded continuation：草稿、session 集合、owner context 或 recovery generation 变化都会作废；竞争启动抢走名额时仍返回容量失败。被停止页面接收 additive terminal cause，显示 stopped 状态，不自动冷启动；用户显式 Resume 后重新加载原 session/history。

WebShell 的 capacity dialog 默认不选择候选，展示受影响 session 并要求确认；取消保留原普通/shell/goal 草稿。review follow-up 又封住了停止态普通提交、deferred `/plan`、cwd 尚未解析时的 queued-prompt stash、已有 recovery intent 与 continuation rejection 后的 resume latch，避免停止后隐式提交、取消后反复弹 chooser 或让 Continue 永久失效。SDK/REST/capability/event surface 均为 additive，legacy client 可继续只显示容量错误。该实现现已进入 `main`。

Stop budget 现在明确区分两种结果：某个 close 已在 flight 时超时返回 503 failed，但隔离和清理继续；两个 close 之间预算耗尽返回 409 incomplete，清理结束且需要 fresh preview。后续 readback 即使已经 `stopped+released`，仍可保留先前 teardown warning。registry release 证明也按平台收窄：POSIX 跟踪 owned process group，Windows 只证明 root settled exit，不能声称 descendant tree 已全部消失。

## 边界与风险

- stop 会中断所选 runtime 中全部已确认 session；它是一次性释放，不是持久 suspend。
- 释放名额不归当前请求独占，continuation 仍可能被竞争请求阻断。
- Linux/Windows process tree、React 18、附件、真实 provider 和穷举 teardown 故障尚未同等验证；Windows 的 `released` 只证明 root exit。
