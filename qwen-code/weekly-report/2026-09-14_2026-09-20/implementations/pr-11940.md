## 解决了什么问题

#11911 的 `admit` 在 modeled child count 满额时直接拒绝新 spawn，即使占用最后名额的只是零 live session、无待处理工作的 warm ACP child。该 child 的 workspace 注册、文件、持久化历史和 runtime service 都可以保留并在之后冷恢复；如果只能等 keep-alive 或人工干预，新 workspace 会在可安全释放物理进程时仍收到容量失败。

## 最终实现方案

最终给 managed factory 增加可选 reclamation callback。首次 admission 拒绝时先取消请求自己的 reservation，再调用 daemon 共享 reclaimer；回收完成后重新读取同一个 `ProcessRegistry`，只有确实低于 limit 才做一次 fresh reserve/decide 并继续原 spawn。取消、回收失败、竞争请求抢走名额或第二次拒绝都返回既有 `AcpChildCapacityExceededError`，每次 factory 调用最多尝试一个候选和一次重新准入，不重放外层 create/load/MCP/prompt。

候选仅来自同一 daemon registry 管理的 active、trusted、registered runtime，排除 requester、special provenance、closed guard、非本 daemon bridge 和缺少完整 activity hooks 的对象。`sessions`、active prompt、pending start、ACP connection、memory task、Channel worker、Voice 与 coordinator runtime work 必须全部为零；bridge 再用当前 channel identity、runtime epoch、`lastUsedAt` 和私有 lifecycle snapshot 做最终复核。合格项按最旧实际使用时间、再按 workspace ID 排序，只终止一个 exact child，清除其 soft keep-alive 并等待 tracked teardown；workspace/runtime/bridge、saved session 和注册记录均不删除，loaded session 即使空闲也不回收。

该方案复用 #11911 的 503/error/UI 行为，成功回收不新增公开 route 或确认 UI。最终 review follow-up 同步了 default child factory fixture 与设计/运维文档；功能已进入 `main`，但仍只自动回收零 session、零 activity 的 warm child。

## 边界与风险

- loaded session、pending work、缺少 activity observation 的 runtime 和 special runtime 都不回收；满额并不保证新请求最终成功。
- 回收释放的名额不归 requester 独占，竞争请求可先取得；实现选择拒绝而不是回收第二个候选。
- 方案没有跨 runtime 的原子 eviction transaction，只依赖候选 token、bridge 最终复核和既有 tracked termination；真实 delayed descendant exit 及 Windows/Linux process tree 尚未同等验证。
- 自动回收不触碰 loaded session；需要用户选择停止 loaded runtime 时使用后续已合入的 #12008。
