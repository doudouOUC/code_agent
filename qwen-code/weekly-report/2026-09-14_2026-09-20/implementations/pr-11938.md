## 解决了什么问题

`review-runner-schedule.test.mjs` 会在临时目录生成可执行 fake `gh`，再用 subprocess 验证 runner label 切换顺序。fixture 原来写 CommonJS `require('node:fs')`，其解释方式却可能继承临时父目录的 package scope；父目录声明 `type:module` 时，Node 把无扩展名 fake CLI 当作 ESM，两个 subprocess 测试因此报 `require is not defined in ES module scope`。测试结果取决于 runner 临时目录环境，而不只取决于仓库代码。

## 最终实现方案

最终让每个 fixture 目录都写入自己的 `package.json`，明确声明 `{"type":"module"}`，并把 fake CLI 的文件系统加载改成 `import fs from 'node:fs'`。fixture 的模块类型和语法现在一致，不再依赖外层 `TMPDIR` 或 runner 祖先目录的 package 配置。真实 `review-runner-schedule.mjs`、runner 筛选、先加新 label 再删旧 label、失败保留旧池和无匹配 fleet 的报错逻辑都没有变化。

## 关键代码路径

- `.github/scripts/review-runner-schedule.test.mjs:writeFakeGh`：为临时 fixture 建立显式 ESM package scope，并生成使用 ESM `fs` import 的 fake `gh`。
- `.github/scripts/review-runner-schedule.test.mjs:spawnPlanner`：继续在受控 PATH/env 下执行真实 planner，验证 label API 调用顺序与失败语义。

## 边界与风险

- 该修复只让 fake CLI 自包含，不证明受影响 Linux runner 的祖先 package 配置为何漂移。
- 两个 subprocess 测试原本即跳过 Windows；Windows 上的 fixture 执行未由本 PR 增加同等覆盖。
- 合并时完整 Ubuntu test lane 不是全绿，失败来自未修改 TUI loop-guard 测试，不能把 merged 状态写成全套 CI 通过。
