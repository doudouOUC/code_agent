> 规模：+1177 / -144，43 个文件

## 解决了什么问题

既有 `--child-heap-mode observe` 会根据 daemon memory budget 报告 `maxConcurrentChildren`，但 spawn 只增加 `refusals` 观测值，超过上限仍会启动 ACP child。多 workspace daemon 因而无法把 modeled process count 变成可选的真实准入限制；冷 workspace 满额时，REST、ACP 和 WebShell 也没有统一、可识别且不会引发自动重试的容量失败。

## 最终实现方案

最终新增 opt-in `--child-heap-mode admit`，默认仍为 `observe`。daemon 启动时基于同一 resolved memory budget 构造唯一 `ChildHeapPolicy`，并将它与唯一共享 `ProcessRegistry` 注入所有 managed child factory；零 child 模型、injected bridge 或缺少共享 registry/policy 的伪接线会在启动期拒绝。workspace 注册和复用已有 channel 不占新名额，只有创建物理 child 才先 reservation、再用包含 attached、reserved 和尚未释放的 terminating child 的 committed count 做决策，超限时在 OS spawn 前抛 `AcpChildCapacityExceededError`。reservation 的 attach/cancel 保持单一释放路径，避免并发 cold start 同时越界。

错误沿调用链保持同一事实：workspace runtime ensure/load 与普通 REST 返回 HTTP 503、`acp_child_capacity_exhausted`、limit 和 committed count；ACP JSON-RPC 在 error data 中携带等价 `httpStatus:503`；standalone create 仍先执行既有 verified rollback，再把 capacity 嵌入 `standalone_creation_rolled_back`，且容量失败不发送 `Retry-After`。WebShell 统一识别顶层、RPC data 与 standalone nested capacity，显示本地化提示，停止 auto reconnect/create retry，并保留普通 prompt、shell 与首次 `/goal` 草稿；用户可在释放容量后显式重试。

status 将数量准入和 heap enforcement 明确分开：`limits.memory.enforced` 仍固定为 `false`，因为 modeled `perChildCeilingMb` 未传给 V8；`limits.memory.childHeap.mode` 可为 `admit`，`admissionEnforced` 表示 count gate 是否真实接线，`runtime.memory.committedAcpChildren` 报告包含 reservation/terminating 的准入计数。现有 host-derived child heap 参数、默认 `observe/off`、注册上限和 session policy 均未改变，也没有新增 capability tag。

## 边界与风险

- `admit` 限制的是 daemon-managed ACP 物理 child 数量，不读取实时 RAM/RSS，也不把 modeled `perChildCeilingMb` 应用到 child argv；#8182 的 raise-only heap 授权缺口仍存在。
- #11940 已在首次拒绝后补充零 session warm child 的单候选自动回收；本实现本身仍不关闭 loaded workspace，用户确认 stop 由后续已合入的 #12008 提供。
- reservation 和 terminating child 会继续占 committed count，优先避免并发超发；进程退出变慢时会延长容量不可用窗口。
