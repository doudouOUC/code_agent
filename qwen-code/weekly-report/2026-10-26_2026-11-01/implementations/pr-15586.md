## 解决了什么问题

Managed WebShell 只能引用 Workspace 已有文件，不能把本机选择的文件安全放入目标目录；直接重试文件写入又可能覆盖现有文件、写错已切换的 Workspace，或在 SSH 丢回包后重复产生副作用。

## 最终实现方案

WebShell octet-stream 上传与原 upload ID 查询使用两个专用路由。原 actor、当前 Workspace 创建权、scopeRevision、路径及 canonical UUID 校验后，最多读取 8 MiB，拒非 identity Content-Encoding 和长度不符。上传仅支持 LOCAL/SSH_LOCAL；锁定原 physical storage，要求 READY、无 holder/maintenance/并发 execution member，再以 WORKSPACE_UPLOAD operation 和 holder 保存完整原目标/摘要。本项只扩唯一 V1 的 operation CHECK、不加表；合入时 38 表，最新 main 后续由 #15745 增为 39 表并扩 Session worktree 文件 scope。

SQL 保存冻结的原 node/CLI/SSH 配置、root/identity/cwd/路径/长度/sha256，不在 SQL 事务中运行文件进程。新 operation 只派发一次 bytes；后续同 ID/摘要重放、状态查询和每 5 秒有界对账只发 upload-status，不再传文件内容。未知或不可达保留原 holder，最终同源 completed/failed receipt 才释放自己的占用；四个本地槽约束并发读取/交换。

CLI 在真实 storage identity 与目录围栏下使用专用 --workspace-file-upload、12 MiB 编码请求限额和 8 MiB 文件限额。原 upload ID 的私有 claim/receipt 固定目标、摘要和原 PID；重复请求不得再次执行，未知进程仍 pending，原进程不活才检查最终文件和临时物。文件先写 0600 独占临时文件并 fsync，hard-link 到不存在的目标，不覆盖现有文件、不自动创建父目录；重验目录/存储并同步父目录。路径拒绝 symlink/越界/保留内部目录，原 SSH 注册和 qwenVersion 仍核对。

客户端只在查询返回 maxUploadBytes 且 provider 支持时启用上传。网络/5xx 后查询原 ID，确认相同 scope/path/size/digest 格式后才加入已上传文件引用；Workspace 切换或原 signal 取消后拒写入旧草稿。上传成功只生成 Workspace 文件引用，不是将任意二进制内容作为模型附件直接发送。后续 #15588 修正上传路由的验收 fixture，不改变此协议。

## 边界与风险

- 不支持 CSI/resident、覆盖写、目录创建或上传后自动执行；未知不能换 Runtime 或换 upload ID 冒充原操作恢复。
- 本地文件路径检查不等于平台或对抗性跨进程文件系统资格；真实 SSH、MySQL 和中断矩阵需独立验收。
