> 规模：+921 / -37，9 个文件

## 解决了什么问题

已有 native snapshot 存储若不接入真实 HTTP reader，恢复仍从 revision 0 逐页拉原交易；反之，直接相信 descriptor 会接受跨 scope、损坏页、缺资源依赖或过期 writer 的状态。

## 最终实现方案

HTTP readJournal 在持有 writer grant 后向 restore 显式请求 includeNativeSnapshot。服务端在 ACTIVE/READY、未 compact 且非空的冻结 head 以内，选择覆盖 revision 最大的一个 NATIVE_SNAPSHOT，重验 manifest scope、原 owner/pins、sequence/activation/storageVersion 上界与 writer generation；不安全的路径型 snapshotId 不用于分页路由。普通 restore 不要求返回额外字段。

客户端从选定 committed-prefix-v1 页开始，逐个验证 durable ref、16 MiB 页/单批预算、最多 100 页的 cursor、previousPageDigest、连续原交易、record bytes 摘要和资源 census。新出现资源读原 bytes 并验证其嵌套依赖，冲突/缺失拒绝。prefix 的 sequence/digest/activation/checkpoint 必须与 manifest 一致；再从覆盖 revision 拉取到冻结 head 的尾部，不能越读后续提交。

完整逻辑 journal 再由原 scanner 校验最终 head；快照路径结束重读 restore 并核原 writer generation/未倒退位置，最后才更新 grant。maxBytes 只在完整校验后生成有界投影，不能用截断数据通过快照校验。没有 descriptor 时沿旧全交易路径，已选快照损坏不静默回退掩盖故障。

本 PR 比 #15569 聚合 PR 更早合入，最终两份 diff 的 HTTP 接线重叠；main 只有同一套 reader。仍需读取/扫描完整 prefix 与资源，不是常数内存或 journal 删除方案。
