## 解决了什么问题

Managed home 同时在顶部、侧栏和上下文面板重复提供控制；cwd 切换又形成额外准入、pending UI 与客户端 API 负担。只隐藏按钮而继续公开提交，会使旧客户端仍能创建新 cwd operation；全部删去旧 operation 读取则会破坏已受理请求的恢复。

## 最终实现方案

home 标题保留双击改名，把显式重命名合入 Session actions 菜单；侧栏未选中 Session 也可按其原 summary 改名，hook 冻结目标 ID、请求键和取消周期，结果回写相同目标。Managed 扩展/MCP 管理汇入统一 plugin manager，删除顶部重复入口、home 的重复 Workspace 详情和创建区管理 Skills 快捷入口；非 home 仍显示绑定信息，不删除 Session 的 Workspace/cwd 选择值。

Public /sessions/{id}/cwd 和 WebShell /sessions/cwd/change 新提交路由、请求模型、OpenAPI/生成类型、Java WebShell client/provider、cwd control/hook 与相关新 admission 方法一并移除，capability 固定 cwdChange=false。共享判定改名为 mayChangeContext，继续服务模型、审批与 Plan，不能因删除 cwd 一起关闭其他上下文能力。

CWD_CHANGE SQL kind、旧 operation 查询/序列化/协调和结算路径保留；没有新 operation 入口，不代表可以手清旧 pending/未知或删除原 context 证据。Core config_install/Workspace context 协议也不由此退役。Runtime attestation worker 另允许带 managedExtensions 的合格 boot 配置 publisher registry，保持 version2/非 storage 条件，不扩成任意 resident 后台支持。

这是接口收窄，调用方须停止提交旧 cwd 请求；不是自动换目录、复制文件或新 Session 迁移。当前 main 的 #15586 上传仍以创建/绑定时的原 cwd 与 scopeRevision 为目标。

## 边界与风险

- 旧客户端继续提交 cwd 请求不再受支持；不能用旧设计或历史 API 表宣称当前仍可新建 cwd operation。
- 保留旧 operation 不等于自动恢复已未知执行；真实 UI/Runtime、源码门禁和适用 CI 仍需独立验证。
