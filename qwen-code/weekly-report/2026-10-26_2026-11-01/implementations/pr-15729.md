## 解决了什么问题

此前 resident 维护入口只能封存 DRAINING 并记录原 UID/resourceVersion 的 Pod 删除尝试，不能把 DELETE 成功、Pod 404 或租约过期当成磁盘已安全释放；否则新 worker 可能与旧进程或卷占用冲突。

## 最终实现方案

在已有 OWNER/空闲/原 binding-generation/物理存储/保护映射验证上，新增 `prepare-reclamation` 与 `reclaim`。v2 plan 固定原配置映射，准备时核唯一 PV/volumeHandle、原 PVC 单一 Pod consumer、原 Node UID/bootID、Ready 和有效 NodeLease、唯一 attached VolumeAttachment 及节点 volume 占用，保存 baseline/digest。原 Pod 通过 UID/resourceVersion/finalizers JSON Patch 安装专属 finalizer，防正常删除先抹掉终止证据；不使用 force delete 或节点异常 fence。

`delete-pod` 仍是原 ID、有界、带 UID/resourceVersion 前置条件、30 秒 grace 的尝试；未知结果保留原 attempt，不重发同一请求。reclaim 要求 finalizer 保护下的原 Pod 同 spec、原 containerID/imageID、零重启、真实 terminated 且非 ContainerStatusUnknown；Node 同 boot、后于 baseline 且不早于结束时刻的新 heartbeat/Lease，volume 已不在 inUse/attached，VolumeAttachment 列表为空，且物理映射和唯一 consumer 仍匹配。deletionTimestamp 是 grace deadline，不强制 container finishedAt 晚于它。

证据形成原 resourceIdentity/baselineDigest 的 durable cleanup receipt，事务将 DRAINING 推进 PLATFORM_CLEANED。仅此后可尝试移除专属 finalizer；等原 Pod 真正消失后，再在 SQL 锁和 idle 围栏下核原 receipt、无活跃 claim，释放原 Runtime binding/slot 及存储 owner，推进 RELEASED。finalizer ADD/REMOVE 每种最多 8 次、合计最多 16 条耐久 attempt；失答可由独立平台 readback 对账，不用 HTTP 成功代替清理证明。

resident 专用 revision 使用奇数 RESERVED、偶数 RELEASED，释放递增后允许下一次 reserve；原普通 CSI revision 路径不泛化为任意循环。`ma_storage_owner` 保留 tenant，注册/查询/预留核同一数据租户；数据政策 `retain-same-tenant-admin-handoff/1` 不擦盘、不跨租户复用。唯一 V1 只扩 POD_FINALIZER_ATTEMPT CHECK，不加表；旧 v1 plan 仍保留历史 DRAINING 观察，不可冒充 v2 回收证明。

平台清单每页 128、最多 8 页/1,024 项，固定 list resourceVersion、拒重复 UID/token；清单超限/换代、节点不健康、异 boot、缺证明、提前 Pod 404 都拒绝回收。只覆盖可信独占 Managed namespace 的正常卸载/detach，不声称节点死亡/强制 fence 的异常回收。

## 边界与风险

- 已合入不等于真实平台故障矩阵通过。异常节点、强制删除、跨租户及擦盘均不在许可内，不可跳过原回收证据清物理占用。
- 依赖可信平台、独占 namespace、完整且新鲜的原 Node/Lease/CSI 证据；任何未知都保留占用，不能人工改 RELEASED 或把删除回执当安全复用。
