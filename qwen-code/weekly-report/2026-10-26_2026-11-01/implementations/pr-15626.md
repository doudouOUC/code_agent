## 解决了什么问题

本地恢复每次读取完整物理 JSONL，不能安全改为 snapshot base 加 tail：旧 writer 可能按旧 offset 继续写，冻结 cursor 会混用物理/逻辑字节，缺少嵌套资源或不确定 rename 又可能丢失原恢复证据。

## 最终实现方案

仅对认证 sealed resume 准入后的原 writer 准备布局；新建、普通静态读、未提交尾部或无已提交事件不触发转换，已含 base 的文件不再次轮换。acquire 使用 lock schema3，恢复提升到 format2；原 Session key、seal sequence/digest 必须与完整 journal 扫描一致。先遍历 header/event 和 schema 声明的嵌套资源边，拒 scope/同 ID 元数据冲突，不把任意工具参数、cancel/replyContext 等 opaque JSON 猜成资源引用。

原 committed bytes 按事务边界切成至多 16 MiB 页；manifest 固定原字节长度/摘要、sequence/commit digest、lastRecordUuid、全部资源 refs、title/source anchors。页和 manifest 使用摘要 ID、私有临时文件 fsync、hard-link 不覆盖和目录同步；普通资源 publish 不接受保留的 snapshot kinds。它保存原逻辑记录，不把模型历史重新生成成另一份权威。

原物理文件替换为必要 owner 前缀、minimumReader=managed-session/2 header 与紧邻的 snapshot_base。SessionWriterLease 在 format2/原文件摘要围栏下独占写临时文件、fsync、rename/同步目录、读回验证，并重验原 logical commit proof。rename 已尝试而结果未知时保留 replacementFailure，后续写/释放拒绝；format2 只能保留 seal/active fence，不能降级或普通 release 让旧 writer 接管。

读取先验证同一物理 generation、base/manifest、所有页和资源 bytes，再拼原 prefix+当前 tail 给原 scanner，核完整提交证明。冻结 maxBytes 仍是物理 offset，返回的 committed/header/uncommitted offsets 显式换算；只允许原 generation 的追加，不接受即使同时增长的前缀改写。尾部新增资源也按 schema 递归核对；title/source 用 manifest anchor 加完整已提交 tail，不受旧显示窗口截断。

Config 恢复、authority/journal handle、message projection 和列表元数据 reader 同步接入。此为本地布局转换，和 #15569/#15599 的 Java HTTP committed-prefix-v1 是不同格式/存储路径；既不后台周期压缩，也不删除原资源、推断工具已停或使未知调用重新执行。

## 边界与风险

- snapshot 仍保存并验证完整原 prefix，不证明常数内存、资源 GC、跨主机恢复或 journal 生命周期目标全部完成。
- 新 header/lock 与 reader 必须匹配；不能清 lock、降级或删除原页来绕过未知替换失败，底层 path-based 文件系统竞态仍需独立资格。
