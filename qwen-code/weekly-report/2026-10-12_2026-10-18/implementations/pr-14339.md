## 解决了什么问题

Workspace 隔离的 binding 没有某个 Harness Session 的 isolation key。沿用 binding key 判断执行、恢复或清理 owner，会把共享 binding 误认作单个会话，或允许不属于它的 Session 释放原资源。

## 最终实现方案

集中 HarnessOwnership 判定 workspace isolation + managed context + local-process + 精确 Workspace capability。该类 binding 的每次 acquire、执行、Hook/recovery 和逻辑 release 都从持久 Runtime Session/execution 读取真实 Harness owner；普通 Session-isolated 行为保留。JDBC 路径仍校验 storage/physical fence，再按真实 Harness Session 查询 admission/drain/recovery。

本 PR 的共享 binding owner 检查不接受跨 binding lifecycle authority；关闭/恢复只操作原 owner 的 Runtime Session。releaseOriginal 必须找到匹配 binding/generation/scope/Harness 的已存 Session，不能为一个从未属于该 Harness 的 Runtime Session ID 创造清理 tombstone。非共享 Session 原 tombstone 机制不变。内存 repository、transport 与 operator recovery 同步采用这一身份规则。后续 #14435 为显式共享 bound Session 增加 lifecycle/Hook/cleanup 路径时，仍通过原 Runtime Session 对应的 Harness claim fence 授权，不授予任意 binding owner 生命周期权限。

双语常驻设计随之压缩重排，但本 PR 不是 idle timer、容量调度或多写环境交付。后续 #14340 在其独立 resident CSI profile 增加逻辑 Session 交接，#14435 另交付显式共享 bound Session 隔离及原 Session 逻辑 close；不能由本 helper 的 local-process 条件推断任意 provider 共享。

## 边界与风险

- 不放松原 storage/lease/execution fence，不以 Workspace ID 代替 Harness owner，不授予共享 binding 的任意退役权限。
- 不实现自动替换、idle retirement、keep-warm 或生产共享资源验收。
