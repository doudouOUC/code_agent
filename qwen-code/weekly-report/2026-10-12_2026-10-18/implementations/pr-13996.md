## 解决了什么问题

私有 CSI worker 已有执行与文件历史协议，但普通 Managed Session 创建、writer、资源读取和 legacy mutation 并不能证明它们属于同一个原始 CSI authority。仅有请求携带的 binding/grant 会让旧写者、错误 Session 或替换 Runtime 进入原 history，破坏结果归属与恢复边界。

## 最终实现方案

`WorkspaceCsiSessionMain` 只提供离线私有 CREATE：严格解析有界请求，cwdRelative 限定为 `.`，固定 registration、actor、revision 与原 idempotencyKey；短 SQL 事务按 placement、retention、registration 顺序核验，再写入私有 Session 和原 request pin，不启动 worker/Harness，也不开放公共选择器。`ManagedLegacySessionGuard` 在原连接锁定 csi_guard，拒绝普通 close/delete、子 Agent 父会话和其它未资格化 mutation，不能回退 Legacy 执行。

`WorkspaceCsiRuntimeAccess` 使用同一 DataSource 上的新事务，锁定原 binding/control/registration，限定原 Session/runtimeSession UUID、bootstrap、READY generation、lease、seed/handle 和 context revision。context 安装后读回比较原 binding/Session version 与 attestation；native 认证同时验证 provision seed token 与 Runtime lease token，bind/prepare/execute/control 的响应也复核原身份和原 SQL head。Read/Write/Edit 的 execution comparison reference 来自认证后的原生读回，不信任调用者自己声明的结果。

`ManagedSessionStore` 在 journal 提交事务中调用 `JdbcCsiActivationAdmission.acceptCommit`：genesis、首 writer/activation、原 commit revision/sequence/digest、资源引用与固定事件前缀共同校验。首次 activation 必须紧接 genesis、未存在 earlier authorization，并 CAS 保存原 binding 的 first activation revision；toolIntent/dispatch checkpoint 核验完整原批次与 reservation，结果回执核验原 execution/history。续租或后续提交不能换 writer、activation 或 Runtime。

私有资源读取分为原身份准入、事务外有界 JDBC fetch、原连接再校验结算；read lease 保护交付窗口，返回前比较 head/writer/resource 元数据及 bytes digest。fetch 未确认保留 UNKNOWN，不冒充成功。最终实现接入 32 表 catalog：resource-read 意图/原身份/结果保存在 ma_request_receipt，交付 lease 在 ma_read_lease，不新增独立 read 表；原 writer、activation 与 resource scope 仍校验。

最终迁移为 `db/managed-schema/V2__private_csi_authority.sql`，只向 ma_session/ma_runtime_binding/ma_tool_execution 添加 request key、generated csi_guard/index、first activation revision 与 native authorization，不沿用旧分支 V69–V72。Broker fresh 初始化生成完整 V1/V2 形状；已验证 V1 无 history 可由 Broker 应用 V2，有 history 则要求 application Flyway migration。Spring 按真实 catalog 的 schemaVersion 选择 baseline，current V2 保持 32 张业务表。后续 main 的首次 writer/资源准入仍在原连接锁定后核验，不放宽原 READY owner 边界。

后续 main 增量先执行 Session admission 并插入 CONTROL root；新插入 root 不可能是 CSI，故跳过空 csi_guard 索引的 locking read，避免 REPEATABLE READ 下跨租户首 writer 的 gap lock。原已存在 CSI Session 仍走原 guard/READY 检查。Catalog 对未加引号的 FALSE/TRUE token 统一为 0/1，generated expression 比较不忽略字面字符串或语义漂移；这不是开放替换 writer。主干后续 V3__session_list_created_at.sql 固定 immutable 创建时间列表 keyset；V2 仍是本 PR 的迁移边界，不表示当前 catalog 只到 V2。

后续 #14185 已将 main V1/V3 时间改为 epoch-ms/gmt 列，当前列表为 gmt_create keyset；authority/锁序边界保留。开放私有文本及旧字段 SQL fixture 集成时须对齐此新库形状，不据单一合入推断组合验收通过。

## 边界与风险

- 不是公共 CSI selector、完整 DRAINING/finalization、generic cancel 或多 owner 接管；release 仍要求 `csi_finalize_required`，close/delete 不由此开放。
- 代码检查不能证明真实 Kubernetes/CSI 或正向 SQL grant→worker→retained history 全链路已验收。
- 最终 V2 只扩展已验证的 canonical V1，不升级旧 legacy 表族；此前 V69–V72 及其冲突记录只属历史分支，不能用于当前部署。
