## 解决了什么问题

files 生命周期回执不能证明 Shell 后台进程、Monitor、MCP 连接及完整输出已安全关闭。直接复用旧 close/delete 会把 Hook 完成当成资源释放，或在冷加载时重建 SessionStart、模型和通知，造成新效果或遗留原 owner。

## 当前实现方案

`WorkspaceToolProfiles` 对 files/1 保留 lifecycle v1，对精确 Shell/1、MCP/1 选择 v2；未知 Shell/MCP 版本不回退 legacy。Harness 仅通过默认空的 `QWEN_HOSTED_LIFECYCLE_V2_PROFILES` 显式广告精确 profile，拒绝重复/未知值。Java consumer 与 SDK 校验 v2 profile，而不是以一个全局版本推断所有 profile 可用。

Coordinator 先验证原 execution 已结算，再持久保存 effects 回执。close 执行 SessionEnd，delete 顺序执行 SessionEnd/SessionDelete，使用原 operation/claim 与 Hook occurrence 记录，不换键重跑。effects 保存后 phase 变为 DRAINING，v2 保留 claim lease；资源阶段只能用原 lifecycle authority 继续清理。冷加载读取原 definition/MCP pin，建立 cleanup writer，不恢复模型、SessionStart 或新的 Monitor 工作。

`prepare_resources` 停止 wake pump、抑制 Monitor 通知，并结算待处理的通知输入；Shell 先经 Broker drain，再关闭观察 loop/publisher，保留最终输出。MCP 拆开 effects 对账与资源关闭，按原配置逐个释放连接，最后释放共享 Runtime owner。丢失 Harness 只在可信原 stopped receipt/holder 证明下走 MCP stopped recovery，不能据断线、404 或无 live handle 推断已停止。

Java `WorkspaceProfileLifecycleVerifier` 复核原 binding/generation、RELEASED Session owner、MCP releaseState/drain receipt，以及 Shell execution/publication/source/manifest 的资源闭包。`verifyOutputContents` 验证 publication 内容，最终完成事务再复核资源；私有输出退役与 Session tombstone 同步，不删除共享 Workspace 文件或其它 Session。授权、claim、身份或内容不确定时准确 recovery_blocked，不返回完成。

## 边界与风险

- 必须先升级 Java/SDK/Harness consumer，再按精确 profile 开启 v2；files v1 兼容不证明 Shell/MCP v2 可用。
- 这是原 Session 的关闭/删除清理，不是未知副作用重放、完整 CSI finalization 或跨宿主泛化接管；archive/unarchive 不能冒充物理释放。
- 输出验证须保留 inline receipt outcome 与 object publication 的原身份及各自 digest 口径，不能将不同协议的 input/args digest 统一成整个请求 hash。
