## 解决了什么问题

仅修正共享 Harness owner 并未让公开绑定 Session 真正共享 worker。原 close 只枚举 Session-isolated binding，开启共享后 v0/v1 可能不释放自己的 Runtime Session 就 CLOSED；反之整 binding 退役会破坏其它 Session。

## 最终实现方案

新增独立 `qwen.managed-agent.runtime-broker.bound-session-isolation-class`，默认 session，显式 workspace 才启用。要求 durable local-process，不能与 child Workspaces 合用；不改全局 isolation-class，也不允许任意 provider 共享。placement 用 Harness Session ID 授权并解析原 Workspace/storage，而共享 binding isolation key 为空。verified recovery 对共享请求复核原 mount/root，不虚构单一 Session owner。

准入、工具执行、生命周期 Hook 与 cleanup 按持久 Runtime Session/execution 的原 Harness owner 及当前 claim fence 核验。共享 worker 不等于并发 storage 执行；既有物理 holder/workspace_busy 屏障保留。Session close 先走原资源结算，再按 tenant/Harness Session keyset 每批最多 100 个枚举，只释放自己的 Runtime Session 和精确 holder；两个 close 协议均覆盖，v2 never-initialized 还须证明从未存在共享 Runtime Session。

binding/generation/worker 保持 READY 供其它 Session 使用；未知原执行、丢共享 worker、缺 binding 或释放失败继续阻止 close，不把单 Session 停止扩大成 binding 退役。只有带 storage fence 的原 storage retirement 才能 drain 并严格 stop 共享 worker。恢复维护、资源查询和 retention 同步沿真实 owner；未结算 child run 仍保护其原 binding。

V9__runtime_session_harness.sql 只给 ma_runtime_session.harness_session_id 建单列索引，tenant 在查询过滤。原拟双 VARBINARY(2048) 组合超过 InnoDB 键长，不沿设计旧编号部署；当前主干 V1–V10、32 业务表。

## 边界与风险

- 不交付 idle retirement、generation 硬预算、Session 创建时 warm 或 keep-warm；不是整个常驻设计已完成。
- 不新增跨宿主替换、CSI 物理释放或任意共享 provider；lost/UNKNOWN 继续保留原资源证据。
- 关闭一个 Session 后 worker 仍运行并占资源，只有独立 storage retirement 才提供物理关闭路径。
