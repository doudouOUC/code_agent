## 解决了什么问题

任务投影虽显示 automation_run，但没有单 run 停止入口。取消整个 Session 或停 schedule 会影响其它回合；仅确认取消 HTTP 请求也不能证明原运行已停止。

## 最终实现方案

ManagedExtensionProjection 将 automation_run 纳入既有任务取消资格，TaskCancelCoordinator 复用原 operation/重试预算，向原 Harness 发送 cancel_run。scheduleId、occurrenceKey 与计算出的 automationRunId 必须完全匹配；停止只针对 automationInputId(runId)，不退休 schedule、不创建替代运行。

HostedAutomationSession 在串行队列中先结算已完成工作；终态直接读回，尚为 execution=intent 的 run 可直接持久结算 cancelled。已接纳 run 则以稳定 automation-cancel:runId 命令写 cancel.requested，重试不重复请求。仅 session.active.promptId 精确等于原 run Turn 才 abort，不取消正在运行的其它用户/后台回合。

排队 wake 在真正执行前重读取消事实，保存 cancelled turn_result 并走原 run settlement，不调用模型；结算失败仍 busy，由下一次 wake 继续原义务。Java 通过 authorizeCommittedStop 的原附件/恢复路径停止已承诺工作，而非按新工作重新准入，也不顺便启用 stoppedMessages。

协调器只有观察到原 automation_run 的 cancelled 终态才完成取消结果；接收 cancel_run 的 ACK 仍可等待实际 Turn 结算。自然结束不会被改写为取消。OpenAPI 与生成的 WebShell 类型同步既有取消接口语义，无新专用公开 route。

## 边界与风险

- 不停 schedule，不等同 Session close 或取消其它回合；ACK、abort 信号与物理完成必须分开。
- UNKNOWN 工具与未完成资源清理沿原恢复门禁，不因 run 投影 cancelled 获得任意重放/释放资格。
