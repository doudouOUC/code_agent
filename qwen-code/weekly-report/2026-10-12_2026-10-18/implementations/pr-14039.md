## 解决了什么问题

Harness 已成功 detach 但响应丢失时，Java 仍缓存旧 AttachmentRef。资源结算重试反复使用已不存在的附件，即使 SQL 已保存原 effects 和 cleanup authority，也不能进入可核验的 cleanup-only load，造成生命周期长时间阻塞。

## 最终实现方案

`QwenHostedHarnessConnector.settleLifecycle` 保留原请求与失败语义。在 DaemonHttpException 404、lifecycle v2 且 phase 不是 effects 时，以 `attachments.remove(key, ref)` 条件清除仍指向该原附件的缓存；仅移除成功才清 pendingRecovery，随后仍抛出原异常，不把 404 返回成成功。

下一次重试由既有 lifecycle 路径读取 SQL 保存的原 operation/claim/effects，重建 cleanup-only attachment，再完成资源结算。条件删除不移除并发替换的 AttachmentRef；effects 阶段或 v1 不采用此处理。资源/输出闭包、原 claim 和最终事务验证继续由 L4 协议负责，缓存失效只恢复重试入口，不证明物理清理完成。
