## 解决了什么问题

原生文件工具已将结果和 history 持久提交，但原 Runtime binding 已退役时，停靠 Turn 恢复仍尝试 acquire 原 owner。已有结果因此无法交付，甚至诱导在替换 Runtime 上重跑文件写入。需要只续接原已提交结果，并明确原 owner 释放证据。

## 最终实现方案

`restoreRuntime` 的限定路径要求 files profile、无 Hooks/MCP、没有未完成 history/undo、原 prompt 可运行且 continuation 为 results_ready；所有工具已经结算且仅为 read_file/write_file/edit/glob。Write/Edit 必须有原 history，Read/Glob 才允许无 history；`canSettleHostedFileHistory` 与所有原 outcome refs 必须能完成证据核验。

`confirmReplacedHostedTurnOwner` 要求当前 warm Runtime 与 owed cleanup descriptor 的原 binding/generation 不同，但 Workspace generation 相同，原 prompt/runtimeSessionId 精确匹配。调用 Broker release 的仍是 descriptor 的原身份，只有确认释放才进入 retiredOwnerResults。此恢复分支不再次 acquire 或运行新工具效果；后续 acquire 被拒绝，新工具需要新 Turn。

完成时即使本轮没有 acquired lease，也结算已消费的原 continuation，并沿 durable terminal/history→cleanup debt 的顺序闭合。构造器仍可能预热 Runtime，本修复不承诺零 provision/warm；它禁止在已提交结果路径上重新执行工具，不泛化 UNKNOWN 恢复。

## 边界与风险

- 原 release 或结果证据不确定仍 blocked，不用新 Runtime 接管未知副作用。
- 不解决 open JDBC retention 分支所需的独立 Hosted cleanup release-proof 契约；原 descriptor 不能因 binding 收集而失去核对资格。
