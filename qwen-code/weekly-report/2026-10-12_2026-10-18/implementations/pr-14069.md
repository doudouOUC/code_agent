## 解决了什么问题

逐切片扩展的 Managed/Broker 表族增加了重复 receipt/work/resource 模型和初始化路径，单纯合并表名却会破坏 journal 原子性、lease/generation、独立生命周期和资源保留。新库方案需要一个可验证的 canonical catalog，而不是对已有生产数据库直接删表重建。

## 当前实现方案

`ManagedSchemaContract` 固定 32 张 ma_* 业务表及封闭的 operation/receipt/work/resource-owner/delivery/head/guard 类型。Session/head/Turn/journal/event/message/snapshot/resource 与 Runtime slot/binding/session/execution、storage/read lease、channel/delivery/schedule 保留各自语义；通用 receipt/work 行按 namespace 和 scope 分型，不合并独立权威或 fencing。

Broker 和 Spring 使用同一个 `db/managed-schema/V1__managed_schema.sql`。空 catalog 才初始化；已有 catalog 必须先验证恰好 32 张目标表、无额外 view、MySQL InnoDB，以及列、生成列、主键/索引/check/FK，再允许 baseline/migrate。history-only catalog 被拒绝；旧 Flyway SQL 移到 classpath 外的 archive，legacy schema 初始化入口移除，不是原地升级旧库。

Store SQL 切换到 typed ma_* 行，`ManagedSchemaJdbcTemplate` 统一 map 读回的字节身份与 H2 binary 参数适配，不改写 SQL 文本。`ManagedReceipts` 固定 namespace/tenant/scope/key digest，并读回比较原始身份以拒绝 digest 碰撞；actor scope 与 Session command scope 分开。journal/资源引用/投影/head 的原事务与 Runtime、operation claim、storage owner/read lease 仍分别保留。

`ManagedSnapshotStore` 以冻结 descriptor 构建 versioned page/manifest，按 100 items/128 KiB 目标切页，带原 body resource refs 和 scoped、签名、过期 cursor；构建和读取持有 SnapshotReadLease。投影 collector 每批 32，先标记 retention candidate，再在锁 head 的事务复核 active refs、recovery protected 和 read lease；只收集 orphan MYSQL_INLINE 投影正文并留下 tombstone，不进行外部对象 I/O。活动 Session 的孤立投影资源也可回收，但不等于全部 Session 资源均可删除。

## 边界与风险

- 仅 fresh database；不包含旧库数据迁移、生产流量切换或在线缩表。保留旧 endpoint/库，新 Session 才进入新环境；回滚也必须保全新库已接受的数据。
- 32 是该 branch 的业务表契约，不含 Flyway history，不覆盖 DataAgent 的 da_qwen_session_* 数据域。
- 分页构建仍读取快照 item 集合，目标 page bytes 不等于整次构建内存硬上限或单个超大 item 拒绝；容量需真实压测。
- 不能从通用 operation/receipt 行推断 UNKNOWN 可重放、外部对象已删除或全部恢复已生产验证。
